# CLAUDE.md

File give Claude Code (claude.ai/code) guidance for work with code in this repo.

## Working practices

**No tracker.** Linear is off until Hamerti say otherwise, so no ticket gate on product work. What want writing down go in the `.md` beside it — a plan note for a feature, a line in the repo's own doc for a decision that outlive the conversation.

**Housekeeping take no issue.** CLAUDE.md, plan note, tooling config — thing changing how we work, not what ship. Issue there = noise.

**Minor update take no issue either.** Tooltip wording, copy tweak, one-line prompt change. Several small thing landing in one PR = one issue at most, never one each.

**Description over ~1000 character open with `## TLDR for human`, closed by `---`.** One line per thing worked on, even when only one. Shorter description need none.

**Status:** start → `In Progress`. After that, leave it — GitHub integration move issue to `In Review` on PR open and `Done` on merge. **Exception: work pushed straight to `main`.** No PR = nothing for integration to read, so set `Done` yourself.

**PR body say what changed.** No issue id to carry while there is no tracker, so the description is the whole record: one line per thing worked on, and the reasoning wherever a reader would ask why.

**PR nobody need review carry `no-review` label.** Copy tweak, doc, prompt wording, config. Add at open (`gh pr create --label no-review`), since review fire on open. Anything touching behaviour = no label.

**Default road = work → PR → stop.** Greptile review every PR on open, so spawn no reviewer session. Open ready, not draft — Greptile skip draft, so a draft sit unreviewed till somebody ping `@greptile review` by hand.

**This repo belong to Hamerti** — `github.com/Hamertingo/hz`, X `@Hamerti015`. Upstream `monorepo-labs/dray` stay as the `upstream` remote, to read history from and never to push to.

Nothing to create, so nothing to name at the end — say what got left undone instead.

**Don't commit unprompted.** Stage + describe change, then wait — even when finished and passing. Asked = approval for that commit only, not ones after. Same for `git push`, branches, anything rewriting history.

**Always write commit message with `caveman-commit` skill.** Invoke it, don't imitate — skill carry format and it can change under you. Every commit here, amend included.

**Comment sparingly.** ~10% of lines, only where code cannot speak for itself:

- Write _why_, not _what_. `// bump seq` on `self.seq += 1` = noise; "the session layer must number synthesized events through this same counter or seq develops gaps" = not noise.
- Good reasons: non-obvious wire-format fact, invariant future edit could silently break, why simpler-looking alternative rejected, deliberate omission.
- No restate type signature, no banner separators (`// ---- helpers ----`), no doc comment on every field of obvious struct.
- One dense sentence beat three-paragraph doc comment.

**Write plainly.** Everywhere — chat replies, comments, docs, commit messages, plan files. Short sentences, active voice, no clutter, no over-explain, no under-explain where detail matter. Skip fancy words. Cut any word doing no work.

**Stay out of files being actively edited.** User say they work on something → review and advise, don't rewrite. `todo!()` or missing match arm = work in progress, not defect.

**`///` doc comments show on hover, so add one to every `pub fn` and any non-obvious private fn** — one line, same "why not what" bar. Skip trivial helpers/getters where name say all.

## What this is

`hz` = Tauri 2 desktop app wrapping a coding-agent CLI in a chat UI. Spawn the MiniMax Code CLI (`mcode`) as a child process and speak **ACP** to it — JSON-RPC 2.0 over stdio — parsing each line into typed Rust enums and forwarding to React as Tauri events.

**One agent, and it ships with the app.** `mcode` is vendored into the bundle ([scripts/vendor-agent.sh](apps/desktop/scripts/vendor-agent.sh)) and resolved before anything on the reader's `PATH` ([binpath.rs](apps/desktop/src-tauri/src/binpath.rs)). What was five harnesses with five dialects is one ACP peer: [harness/mcode/](apps/desktop/src-tauri/src/harness/mcode/). A session some older build wrote for another CLI still **reads** — see `Harness::Other` — and nothing spawns for it.

## Repo layout

pnpm workspace, two apps plus the CLI and its wire crate.

```
apps/desktop/   the Tauri app — everything below this section describe it
apps/web/       marketing site: Next.js App Router, Tailwind 4, deploy Vercel
apps/cli/       the `hz` CLI: creates and lists sessions in the running app over a socket
crates/hz-proto/  the wire types that CLI and app share
```

Root `package.json` carry **no dependencies** — name, `packageManager`, `pnpm --filter` aliases only. Keep it that way: dep at root install into root `node_modules`, which both apps resolve through, so version drift there show up as one app mysteriously working.

Two things repo-wide on purpose. Release pipeline = desktop's alone but live in root `.github/workflows`, so paths carry `apps/desktop/` prefix and `tauri-action` need `projectPath`. And `pnpm-lock.yaml` single for whole workspace, why `pnpm install` run at root and nowhere else.

`apps/web` share design language with app but **no code** — no build step reach across, no import cross line. First component genuinely wanted in both = reason to create `packages/ui`, nothing before.

## Design direction

hz keep to one visual language — one radius scale, one yellow, filled buttons carry shadow and chrome don't, shortcuts live in real tooltips and never on `title`. Window is glass (macOS vibrancy) with body's fill the only hole in it, and the titlebar row is what user drag window by.

**Rules, rejected alternatives and the reasoning all live in [DESIGN.md](apps/desktop/DESIGN.md)** — read it before restyling anything, changing window chrome, or reworking a panel, card, row or button. Two things there fail *silently* and cost an afternoon each: vibrancy's `body` specificity, and window drag needing both an explicit capability and `data-tauri-drag-region="deep"`.

## Commands

Use **pnpm**, not npm. `tauri.conf.json` hardcode `pnpm dev` / `pnpm build` as before-commands.

**Every app command run from its own package dir.** Workspace root hold no deps, only thin `pnpm --filter` aliases (`pnpm app`, `pnpm web`). Anything else — `cargo`, `vitest`, `tauri build` — want real cwd, because relative paths in `tauri.conf.json`, `.cargo/config.toml` and `install.sh` all resolve against it.

```bash
cd apps/desktop && pnpm tauri dev
```

That = real entry point. `pnpm tauri` = shim ([scripts/tauri.mjs](apps/desktop/scripts/tauri.mjs)) merging `tauri.dev.conf.json` into `dev` subcommand only, so dev app carry own name and icon and `build` untouched.

**Shim also pick dev port, and it only side that can.** Vite and Tauri have to agree on one, and both start from here — so shim ask the OS for a free one (`listen(0)`), hand it to Vite as `HZ_DEV_PORT` and to Tauri as second `--config` carrying `build.devUrl`. Fixed 1420 was hard failure before, which = one worktree's dev build refusing to start because another's already running. `strictPort: true` **stay** on Vite side: port already known free, and Vite wandering off it leave Tauri loading URL nothing serve.

- `pnpm dev` — frontend only, port 1420 unless `HZ_DEV_PORT` say otherwise. `invoke` do nothing in plain browser, so only useful for pure-CSS/layout work.
- `pnpm build` — `tsc && vite build`. `pnpm tauri build` for bundled app — **run [scripts/vendor-agent.sh](apps/desktop/scripts/vendor-agent.sh) first**, or the bundle ships without its agent.
- `cd apps/desktop/src-tauri && cargo test` — Rust tests (parser + mapper + event-model compatibility, plus git and file index). Single test: `cargo test every_update_in_the_capture_is_named`.
- `cd apps/desktop/src-tauri && cargo check` — fast type check, no linking whole app.
- `pnpm test` — frontend tests (vitest, node environment, no DOM). Scoped to pure logic where being wrong invisible on screen: [mcode.test.ts](apps/desktop/src/lib/mcode.test.ts) for the model/effort/stance rules, [todo.ts](apps/desktop/src/lib/todo.ts) for reading a plan off a capture, composer's caret arithmetic ([slash.ts](apps/desktop/src/lib/slash.ts), [mention.ts](apps/desktop/src/lib/mention.ts), [highlight.ts](apps/desktop/src/lib/highlight.ts)); and [theme.ts](apps/desktop/src/lib/theme.ts)'s coercion. Components not tested — no DOM here.
- `pnpm lint` — biome, **lint only** (no formatter: every file here is shaped by hand and a formatter's first run would rewrite all of them). The rule set is stated in [biome.jsonc](apps/desktop/biome.jsonc) rather than borrowed: `recommended` is off, and each rule left off has its reason written there. It runs in CI (`.github/workflows/app.yml`) with the type-check, the vitest suite, the app's `cargo test` and **`cargo clippy --all-targets -- -D warnings`** — none of which had a gate before. `--all-targets` is what finds the warnings in test code, which was most of them the day clippy went in (nine, all fixed rather than allowed). **There is deliberately no `cargo fmt --check`**, for the reason there is no biome formatter: this tree is shaped by hand and rustfmt's first run rewrites 319 files. Measured, not assumed.

## Architecture: the event pipeline

Messages flow one way out to CLI and one way back in; return path = what most Rust code exist to serve.

1. **`useSessions`** ([useSessions.ts](apps/desktop/src/hooks/useSessions.ts)) call `invoke("send_msg", {...})` with camelCase keys (`sessionId`, `isNewSession`); Tauri map them onto snake_case params in [lib.rs](apps/desktop/src-tauri/src/lib.rs). Frontend mint session UUID with `crypto.randomUUID()` — **and mcode mints its own**, a second id (`mvs_…`) that hz records on the index entry's `thread_id`. The two are joined there; neither is derivable from the other, and nothing about a session can be known before its spawn.
2. **`SessionManager`** ([session.rs](apps/desktop/src-tauri/src/session.rs)) own `Mutex<HashMap<String, Session>>`. On send: spawn process for new session, reuse live one when present, re-open the CLI's own session when the id is known but the process is gone. New sessions written to index before spawn, so one failing to start still visible, and created `SessionIndexItem` returned to frontend — `Some` on creation, `None` on resume.
3. **`mcode::init`** ([harness/mcode/mcode.rs](apps/desktop/src-tauri/src/harness/mcode/mcode.rs)) spawn `mcode acp` and handshake it: `initialize` with our client capabilities (`fs` and `terminal` both **declined** — advertising either invites requests this build cannot serve, and an unanswered one blocks the agent's turn), then `session/new`, `session/resume` or `session/fork`. Settings are applied **after** that, because none of them rides the spawn: model first (its reply states that model's effort ladder, which the effort below is judged against), then effort, then the stance.
4. Two `tokio::spawn` tasks drain stdout and stderr. Each non-empty stdout line go through [rpc.rs](apps/desktop/src-tauri/src/harness/mcode/rpc.rs)'s `accept` — which sorts a request from a notification from a response **structurally**, on whether it carries an id and a method — then `parser` → `Mapper::map` → the read loop's **`Coalescer`** → `app.emit("agent_event", &agent_event)`, with copy pushed onto `Session.events` and appended to session's JSONL. An agent **request** is answered from the read loop rather than mapped. **One demux per line, never two**: `accept` *settles* a waiter, and `settle` removes it, so a second look at the same response finds none and files a legitimate reply as a stray. The loop did exactly that once, and the prompt's answer is read ahead of the demux for the same reason — nothing waits on it.
   - **The coalescer holds one block's text deltas for a frame and merges them**, because a burst of them is most of the wire: one small turn is 262 lines and **203 of those are deltas** (133 thinking, 70 message), each of which otherwise costs a serialize, an IPC message and a React render. `COALESCE` is 16ms — a frame, and the number the agent's own TUI reasons with — and the timer is **anchored to the first delta of the run**, not to the read that just arrived, or a model streaming steadily would push the deadline ahead of itself forever and never draw. Anything that is not a text delta of the same block flushes what is held first, so nothing overtakes the row it belongs to; the merged event keeps the first one's `id` and `seq` (the ordering key only moves forward) and the newest `ts`. Three flush sites, and each is a bug if dropped: before a non-mergeable event, on a frame boundary with no line behind it, and at stdout's end.
5. **`useSessions`** listen for `"agent_event"`, route deltas into `streamingContentBlock` and everything else onto session's `events`. `Chat.tsx` render both.

**Finding the binary.** [binpath.rs](apps/desktop/src-tauri/src/binpath.rs) resolve `mcode` to an absolute path, cached in `OnceLock`; both spawn sites go through it. **The copy inside the bundle leads** — `<app>/Contents/Resources/mcode/bin/mcode`, a launcher the vendoring script writes — or a machine with an older `mcode` installed would run *that* instead of the one this build was tested against. Never `Command::new("mcode")`: a bundled `.app` launched from Finder or Dock inherit launchd's `PATH` (`/usr/bin:/bin:/usr/sbin:/sbin`), which hold no `mcode` however installed, so a bare name work under `pnpm tauri dev` and fail in the bundle with no events arriving at all. Where no bundle copy exists (dev), resolution escalate by cost: inherited `PATH`, then known install dirs (`~/.minimax-code`, `~/.local/bin`, `~/.bun/bin`, `~/.npm-global/bin`, Homebrew, globbed nvm version dirs), then `$SHELL -l -c 'command -v mcode'`. `-l` load-bearing — without it zsh read `.zshrc` only and miss `PATH` exported from `.zprofile`. `git` need none of this.

**Worktrees.** mcode has no `-w` at all, so **hz makes the tree**: resolve the base (`git::default_base`, the repo's own default branch), `git worktree add --no-track -B` at `<project>/.claude/worktrees/<name>` on branch `worktree-<name>`, then spawn the child *into* it with no worktree argument. That is the whole reason `Capabilities::creates_own_worktree` exists and is false here: `Session::init` refuses a worktree name it was not told about, because a session that silently ran in the project root instead of its tree is the failure worth a refusal. Two consequences the composer draws: the branch picker is hidden in worktree mode (the fork point is resolved, not chosen), and the tree already exists and is clean at send time, so its baseline snapshot is exact.

## The normalized event model

Both harnesses map onto one vocabulary in [events/events.rs](apps/desktop/src-tauri/src/events/events.rs), so the frontend and on-disk log never see raw wire format. Adding a harness = writing one mapper. Per-harness code sits under `harness/<name>/` with a seam: `parser.rs` (wire → typed events), `mapper.rs` (those → `AgentEvent`). Module entry files are named after their directory (`events/events.rs`), not `mod.rs`, declared with `#[path]`.

Two rules the whole design rests on:

- **`seq` is the ordering key, not `ts`.** ACP stamps nothing on a line. One counter per session, and events the app synthesizes itself (the user's own prompt, which the CLI never echoes back) must be numbered through it too.
- **A prompt's `ts` is the reader's clock, not this process's.** The webview reads `new Date()` at the press, sends it as `sentAt`, and it rides the whole way to the event — so the line under a turn is the *wait* (Enter → answer), not the part of it that happened after the child was up. A cold session's first prompt waits out the whole boot, which is exactly the number that was wrong. `prompt_ts` in [events.rs](apps/desktop/src-tauri/src/events/events.rs) normalizes it to the app's own format and falls back to now for a stamp it cannot read; a queued prompt carries its stamp on the `QueuedMessage` rather than re-reading at the flush, since the boundary that released it is not something the reader did. A relayed `hz send` and `hz new` pass `None` — nobody pressed Enter.
- **Deltas are a preview; the committed event wins.** Absent deltas are the common case — mcode sends none for tool arguments at all — so consumers must render correctly without them. Deltas match on `BlockRef`; tool calls join on **tool_use id**, which is the `toolCallId` the announcement carries.

Prompts go the other way as a JSON-RPC **request** on the child's stdin ([session.rs](apps/desktop/src-tauri/src/session.rs), [rpc.rs](apps/desktop/src-tauri/src/harness/mcode/rpc.rs)), sharing the pipe with the answers we send back to the agent's own requests. `session/prompt` blocks until the turn is over, so it is sent **detached** — no waiter registered, its id remembered, and the read loop settles the turn on that id's response. Registering a waiter would tie the turn to the 30-second bound every *acknowledgement* is held to.

**`session/set_config_option` moves model and effort on the live child**, and the stance is the same call — `permissionMode`, or ACP's session *mode* for `plan`/`default`. So all three apply in place and none of them needs a respawn, which is what `Capabilities::{applies_model_in_place, applies_effort_in_place, applies_permission_in_place}` state. A refused **effort** is a notice rather than fatal — mcode declines one on a model that does not reason, and killing the child over that would make a session whose recorded level its model has since stopped taking unresumable. A refused **stance** is fatal: the stance decides what the agent may do unsupervised.

**A Stop during the boot cancels the start, because that is the only thing there is to stop.** A session is not in the manager's map until its child is up and its prompt is written — spawn, handshake and the first `session/new` all sit inside `send_msg`, the better part of ten seconds on a cold child — while the frontend marks the turn `in_progress` the moment Enter is pressed. So Stop was offered for that whole window and answered `no running session <id>`, an internal sentence for the one control a reader reaches for when a start is slow. `SessionManager.starts` records a send in flight and what the reader asked of it; a **guard's `Drop`** is what takes the id back out, because `send_msg` leaves by a dozen doors and every one of them has to. Cancellation is **cooperative**, for `download`'s reason: the spawn cannot be aborted mid-flight, so it is honoured at the seam each cold path already has — after `Session::init`, before the prompt goes out. Failing there is what puts the reader's text back in the composer, since the existing failure path already restores it. Known consequence, stated: a cancelled *new* session leaves its index row, and a worktree made before the seam leaves its tree — both visible in the sidebar, and removable from it.

**`interrupt` stops a turn and there is nothing finer.** ACP asks for it as a *notification* — `session/cancel`, which nothing answers — and the turn ends as the prompt's own response with `stopReason: "cancelled"`, so the status machine needs nothing special. **There is no per-task stop**: `stop_task` was Claude Code's control request, mcode publishes no equivalent, and the panel's per-task button is gone with it (`CanStop` is false everywhere). `StatusTracker` still hold task ids rather than a count, for the stranded-task report.

**And a held prompt no longer needs an interrupt to get out.** `session/prompt` takes one turn at a time, so a prompt typed mid-turn waits for the boundary — and the only way to release it early *was* to stop the turn, throwing away whatever the agent was part way through. mcode's own extension takes a message **into** the live turn: `mcode/session/steer` (`{sessionId, text}`, answering `{turnId, mode}`), verified present in the shipped 0.4.12, whose handler is registered unconditionally — only its *notifications* are gated on a capability the client has to advertise. So the queued bubble's `Now` steers and the turn keeps running. A refusal means there is no live turn any more; `Session::steer_queued` **puts every held message back at the front of the queue in order** and reports the reason, because a prompt that vanished into a failed call is a sentence the reader wrote and never saw again — and the turn's own end is about to deliver them anyway. Falling back to an interrupt there would stop a turn nobody asked to stop. Each steered message is logged with `send: false` first, the shape `flush_acp` uses, so the transcript draws what the reader typed.

**What can change mid-session.** Model, effort and stance apply in place; project, branch and worktree are creation-time only and the composer hides them once a session exists. That rule keeps `git checkout` from ever running under a live child.

### Fast mode

**mcode has none, and that is the whole of it here.** `serviceTier` is not a thing on this CLI and ACP carries no field for a tier — measured against 0.4.12, whose capabilities answer nothing about one. So `Capabilities::fast_mode` is `Unsupported`, [fastMode.ts](apps/desktop/src/lib/fastMode.ts) says `"none"` for the harness, and no model row draws a switch.

The enum and the frontend table are **kept, not deleted**, and they are the vocabulary a harness with a route would use: `in-place` (Claude Code's `--settings`), `on-spawn` (Codex's `serviceTier`), `at-creation` (fx's settings file) — the three routes this app used to speak. `fastNotice` and the `fast_mode_notice` event are likewise kept and still read a refusal off the session's log, scoped to the newest turn; nothing emits one today. `fast_mode` is a **bool** on the index entry and on the wire, never an enum, so an older build reading a session this one wrote cannot have its whole index fail the line on a value it cannot spell.

### Fast mode

**Three harnesses have one, each reached a different way, and `Capabilities::fast_mode` is the one statement of that** — a four-armed enum rather than a pair of bools, since "offered" and "changeable" would spell combinations nothing has. Stated twice, in [fastMode.ts](apps/desktop/src/lib/fastMode.ts) too, for the same reason `stanceFor` is. It is a **bool** on the index entry and on the wire, never an enum: every one of them is two-valued, and a variant an older build cannot spell fails the line and reads the whole index as no sessions.

### Permissions

/**The request is ACP's `session/request_permission`, and the agent blocks its turn until it is answered.** It arrives as a JSON-RPC *request* — the only line travelling into the app that expects an answer — so [rpc.rs](apps/desktop/src-tauri/src/harness/mcode/rpc.rs) sorts it out of the stream before the parser is asked anything, and an unmodelled request is **refused with a JSON-RPC error** rather than left hanging. Silence stalls the session exactly as it does on any peer protocol.

The reply is the outcome envelope the button was built with, sent back under the request's own id:

```json
{"outcome": {"outcome": "selected", "optionId": "allow_once"}}
```

**The options are the agent's.** ACP names each with an `optionId` and a `kind` (`allow_once`, `allow_always`, `reject_once`, `reject_always`), and `pending_for` turns each into a button that carries the id back untouched — so a decision hz never composes is one it can never compose wrongly. An option kind this build cannot spell is **dropped**, not drawn generically: an unspellable grant offered as an ordinary Allow would decide more than the reader asked for. A request offering no refusal gets one added, as ACP's own `cancelled` outcome, because a card with no way to say no cannot be answered honestly.

- **A cancelled request is not a request.** `control_cancel_request` — the agent taking a question back — drops the entry and mints `PermissionDecided { automatic: true }`, **writing no reply**: the request is already withdrawn, and a reply to it is one more line for a turn that has moved on.
- The card renders outside the turn stack from `buildTranscript`'s `pendingAsks`. Neither `permission_requested` nor `questions_asked` belong in `RENDERS` — they draw no row, so counting one miscounts collapse.
- **The pane that owns the composer draws them above it, and the transcript draws them only where there is no composer.** The agent stopping mid-turn is the one moment the reader has to act, and the transcript may be scrolled anywhere — so the cards sit where the typing is. [PendingAskPanel](apps/desktop/src/components/chat/PendingAskPanel.tsx) takes the whole list rather than the newest, because two requests can be open at once and the transcript's copy is not drawn for that pane; an unfocused split pane keeps its own copy, since it has no composer to sit beside. `pendingAsksOf` is split out of `buildTranscript` so the composer's copy costs a scan of the events rather than a second walk, and **both callers read that one rule** — a card answered at one surface and not the other would offer buttons that can no longer answer anything. `useLingeringCards` moved out of `Chat` for the same reason: one beat, not two running side by side.
- **Never persisted** — request, decision and questions alike. Only the child that asked can answer and no child survives a restart, so a replayed one is a card whose buttons cannot work.

**mcode asks no questions.** `AskUserQuestion` was Claude Code's, riding `can_use_tool`; ACP's capabilities name no elicitation and no dialog, so `answer_questions` **refuses** rather than pretending — a questions card has nothing that could have raised it. [QuestionRequest](apps/desktop/src/components/chat/QuestionRequest.tsx) is kept for the day some harness asks; nothing draws it today.

**Two denials mean different things.** `PermissionRequested` → `PermissionDecided` is a question the user answered; `PermissionDenied` is the agent reporting a refusal with no question possible. Both render as nothing — approval is visible in the tool running, refusal in its error.

**A tool call with no result is only _pending_ while something could still produce one.** `buildTranscript` takes `live` (session `busy`) and files an `ABANDONED` stand-in into `resultByCallId` for every call the log leaves open, so collapsed row, group header and shimmer all read pending-ness from one map. `user_message` also abandons everything open before it. Marks are applied after the walk and only where no real result exists, since a background subagent can report back after its turn. It works only because `handleSelectSessionIndexItem` returns early for a session already in memory — make it always refetch and an open card disappears mid-flight with the agent still blocked behind it. **Loaded transcripts are evicted** (`evictSessions` in [useSessions.ts](apps/desktop/src/hooks/useSessions.ts)) on archive, on settle, and after ten minutes unviewed — never the selected session, never one mid-turn, never one holding a card, for that same reason.

### Streaming and previews

**A tool call arrives whole, one update after it announces itself.** mcode's `tool_call` carries a name, a title and a kind and **no arguments at all** — the `rawInput` lands on the `tool_call_update` behind it, as one complete object. So there is no partial-JSON preview on this wire: [mapper.rs](apps/desktop/src-tauri/src/harness/mcode/mapper.rs) remembers the announcement and **commits the row on the update that has something to draw**, rather than drawing a header and filling it in.

Two consequences that are easy to get wrong. A call that ends **without** ever carrying an input is committed by its own end, or a refused or cancelled tool leaves no trace on screen. And the dozens of bare `{toolCallId}` updates a real turn carries (80 of them in `todowrite.jsonl`) are skipped: an update that says nothing draws nothing.

**There is no partial-JSON preview on this wire, and the machinery for one is gone.** `mapper.rs` calls its own `stream` only with `BlockType::Text` (`:117`) and `BlockType::Thinking` (`:133`) — never `ToolUse` — so the preview component that keyed off a `tool_use` streaming block could not be reached, and neither could the reader it fed. `lib/streaming.ts`, its test, `StreamingToolCall.tsx` and the `input_delta` branch that would have fed them were removed rather than left standing "for a wire that might". The composer's attachment path names a file in prose because mcode expands no `@mention` (`Capabilities::expands_at_mentions` false), so the mention form is never reached either.

### Subagents

**A delegated run is a row under the session that spawned it, and its conversation opens in the main column** — [SidebarSubagentRow](apps/desktop/src/components/Sidebar.tsx) and [SubagentChat](apps/desktop/src/components/SubagentChat.tsx). It was a `Subagents` tab in the right pane, which made work the agent was already doing a place the reader had to go looking for; the sidebar already nested spawned *sessions* under their parent, so the child of a delegation takes the same rail.

- **The two kinds of child are different, and the row says so.** A spawned session has an index entry, a branch, a composer and a context menu. A delegated run has none of them, so its row draws the avatar and a status word and nothing else — no drag, no fork, no settle. The avatar leads because it is what tells the two apart at a glance and it carries the two facts the row would otherwise need a second line for: which agent this is, and whether it is still going.
- **Membership is the pushed roster, narrowed to what this run watched work.** `subagent_delegations` carries one session's roster and the listener files it by session id, so `delegationsBySession` holds every live session's — which is what the sidebar reads, per parent. It is narrowed through `watchableChildren`: **mcode's roster can name children from before this app started**, because they live in the agent's own store — so a session resumed after a restart reports its whole family back, and one new child used to drag every earlier subagent onto the screen at once. A child is kept from the moment it is seen going, and kept afterwards, so the run the reader watched finish is still there to open. It is **live-only and unpersisted**, so a run's row is gone after a restart, along with the child it named; what stays is the spawning call in the transcript, whose `SubagentRow` opens the same view. `sessionRows` takes it as `subagentsOf`, optional: the ⌘⇧↑/↓ walk passes none, because the selection moves between sessions and a subagent is not one.
- **A session's subagent rows fold away** (`foldSubagents`): open while anything is still running, folded once none is, and the reader's own click pins it either way — held in memory, like the crew's own hide, since what is folded differs from one conversation to the next. **The fold is applied through `subagentsOf`, never in the walk**: a folded session simply answers with no members, so it has no subagent children at all and the rails, the guides below it and the keyboard walk stay right without knowing the fold exists. The row keeps a chevron saying how many are held, since a folded group is the one place that count cannot be read off the rows.
- **Rows come out of the same walk as the sessions**, one level down and ahead of the sessions that session spawned — a subagent is work happening *in* this session, where a spawned session is somewhere else the work went. One walk because the rails are one tree: `guides` counts both species, or the parent's line would stop at its last spawned session while a subagent still hung below it.
- **The column is the main chat pointed at a child, and the composer goes with it.** [SubagentChat](apps/desktop/src/components/SubagentChat.tsx) renders `Chat` itself, handed the parent's own record with the child's id and events swapped in — same rows, same rail, same backfill — because a second renderer drifts from the first the day either moves. What makes it read-only is what it is *not* given: no composer, since a delegated child cannot be prompted, and `active={false}`, the branch an unfocused split pane takes, so none of the chat's chords are bound from a view that cannot act on them. It draws no bar of its own — the window header names the subagent instead, the way it names a session — and the arrow beside that name is the way back. The transcript hides rather than unmounts behind the view, so its scroll position survives.
- **Three accounts of one run meet there**, and none can be derived from another: the roster says what it is and whether it is going, the spawning call says what it was asked (the brief), and `session_delegation_messages` is the work itself. A run the roster no longer holds — every run in a transcript replayed after a restart — draws the brief and nothing else, which is [runBrief](apps/desktop/src/lib/subagent.ts)'s whole job.
- **The transcript's own `SubagentRow` opens the same view**, resolving run → child through `memberIdOf`, which stays a guess until the call's result names `sub_session_id`.

### Turn snapshots

**Two snapshots, not the working tree.** `git diff` reports everything uncommitted, including what was already dirty. `snapshot_tree` captures the tree at send time and the turn's **closing snapshot** is frozen onto `turn_completed.head` by `read_stdout`. Freezing the end is as load-bearing as snapshotting the start — head left at "now" and an idle session absorbs whatever later touches the checkout, so the pair stops saying anything about the turn. **The pair feeds two things and they must agree**: `turnChangedTree` reads the two ids to light the pane toggle's git glyph, and the Diff tab's **Turn** sub-tab diffs them. A glyph that lit for a turn the tab then could not show would be the lie the toggle's own rule forbids.

Snapshot = **temp-index `write-tree`**: copy the index to a temp file, `git add -A` through `GIT_INDEX_FILE`, `write-tree`. Real index, working tree and stash untouched, and copying rather than starting empty keeps it at ~18ms since the copy carries git's stat cache. `--git-path index` finds it, which is not `.git/index` for a worktree session.

Comparing *content* rather than replaying edits is why `Bash` moves and reformats show up, several `Edit`s collapse into one diff, and a mid-turn commit is invisible — `Edit` carries only the fragment it replaced and `Write` never reports what it overwrote. Cost: the snapshot describes the *tree*, so anything else writing during the turn is attributed to it.

The baseline rides on `user_message.baseline`, the closing head on `turn_completed.head`. `changeRange` pairs the newest baseline with the newest head *after* it, and leaves head open only while nothing closed the turn, so a turn that never closed degrades to diff-against-now. **Only the newest prompt's snapshot is ever used.** `None` is ordinary and reads as nothing to show. **A worktree session's first prompt is the exception** — no tree yet, so the baseline comes from `base_ref_tree`.

- **Panes hide, they don't unmount.** The `active` prop is the other half: a hidden `ChangesView` must not keep snapshotting on every event, and `active`'s place in the effect deps triggers the catch-up read on reopen.
- **Reads are cached across mounts, keyed by tree id** ([useChanges](apps/desktop/src/hooks/useChanges.ts)) — a new snapshot is a new key, so an entry can only be stale by being unreachable and eviction is a size cap, not invalidation. Change sets are counted (12); file contents are budgeted by **bytes**, or a turn touching more files than the cap evicts rows while they are still mounted. A fresh read whose `base`/`head` match keeps the **old object**, which is what lets `FileRow`'s `memo` survive a re-render on every session event.
- **Two `cat-file` passes per file, and the split is about memory.** `--batch` is one spawn but drains stdout whole, so a 2GB blob is read in before `MAX_BLOB` could reject it; `--batch-check` returns headers only. Input is NUL-delimited (`-z`), since a rev embeds a path and a path may contain a newline. Both parsers always answer exactly as many entries as asked for, or one file's contents render under another's name.
- **Every `git diff` here ends in `--`**, or a working-tree file *named* like a sha makes it die with "ambiguous argument". Covered by test.

**Filtering `cargo test` rewrites generated TS.** ts-rs regenerates `src/types/events.ts` from whatever exports ran, so `cargo test git::` leaves only git's types and breaks the frontend build. **Always follow a filtered run with a bare `cargo test`.**

### Indicators and failed turns

- **Thinking blocks arrive with their text** — `agent_thought_chunk` carries the words, where Claude Code sent `thinking: ""` — so `reasoning` is a real renderable block here and *is* counted in `RENDERS`. A harness that redacted its reasoning would send empty text; `Reasoning::encrypted` is that flag.
- **A failed turn draws the agent's own sentence, never `stop_reason`.** mcode reports `refused`, `max_tokens` and `max_turn_requests`, and each becomes a sentence the reader can act on; `Turn failed` is the fallback for an errored turn with no text at all.
- **A dropped tool row keeps its pending-ness honest.** `buildTranscript` takes `live` (session `busy`) and files an `ABANDONED` stand-in into `resultByCallId` for every call the log leaves open, so collapsed row, group header and shimmer all read pending-ness from one map. `user_message` also abandons everything open before it — and that matters more here than it did on a line-oriented harness: the announcement carries no arguments, so a call killed between its announcement and its input has nothing else to mark it.
- **The working indicator is driven by `model_request_started`**, not "this turn has drawn nothing yet", which only ever described the turn's first wait. Three exits clear it, all needed: a `block_start` that is not thinking, `turn_completed`, and any `session_status` off `in_progress` — the last covers interrupt or a dead child. Per-session and nowhere else, since both driving events are unpersisted.
- **Retry takes the indicator over.** A retry event draws its own row with the working one suppressed. There is no closing event, so it clears on "the retry is the newest event", gated on `busy`. mcode emits none on any capture yet.

**Git.** [git.rs](apps/desktop/src-tauri/src/git.rs) and [github.rs](apps/desktop/src-tauri/src/github.rs) are the only places the app shells out to anything but `claude`. `checkout_branch` validates the name against branches git just listed — injection is not the risk, but a name starting with `-` parses as a flag. It runs when the user picks a branch, not at send, and `dirty` is re-read at pick time.

**`-w` worktrees do not fork from the checked-out branch.** The CLI resolves the repo's default branch, fetches `origin/<it>` and passes that to `git worktree add --no-track -B`, so the fork point is `origin/main` whatever is checked out, and a failed fetch falls back to local `HEAD`. The `-w` flag surface exposes no base ref, hence the composer hides the branch picker in worktree mode and shows the resolved base.

**Models are the agent's own answer.** [mcode/models.rs](apps/desktop/src-tauri/src/harness/mcode/models.rs) reads them off a session's `configOptions` — 41 rows on the captured machine, across a managed account and every BYOK provider configured — so a model the vendor ships after this build is pickable with no hz release. Each row's **label is the agent's too** (`MiniMax-M3 · thinking`), because only the CLI knows which variants a model has.

**And a reseller's catalog names a model `publisher/model`, which is a path rather than a name.** `publisherless` in [model.ts](apps/desktop/src/lib/model.ts) takes the last segment off before anything reads it — `meta/muse-spark-1.3` draws as `Muse Spark 1.3`, `zai-org/GLM-5.3` as `GLM 5.3` — which is what every one of those gateways answers as the row's own `name`, and is the only spelling under which the brand table finds a mark: nothing keys off `zai-org` or `xai`. It happens in `modelSlug`, so the label, the brand table and the search all see the same name. **Presentation only** — `Model.id` and `Model.arg` keep the full ref, which is what a pick sends.

**The ACP `session/list` exists and is deliberately not consumed.** `ListSessionsRequest` (`cwd?`, `cursor?`) would enumerate the agent's own sessions, and the answer to what hz should do with them is *nothing good*: importing one means a session with no project, no worktree and no role — every field the sidebar and the index are built on — and reconciling the other way means deleting data out of a store hz does not own. The index is the app's record; the agent's store is the agent's. What is worth reading off the agent is what it *answers* — models, modes, commands — and that is where the app already stands.

**There is no list before a session, so a session's own reply is what the picker draws from.** `models::remember_configs` is the funnel: the agent states the whole list on every `session/new`, `session/resume`, `session/fork` and `set_config_option`, so the composer's park has already answered the question before the reader opens the picker — by the handshake it was going to run anyway — and `all()` is a cache hit, trusted ten minutes. **The read waits for that park** (`modelsWaiting` in [useSessions.ts](apps/desktop/src/hooks/useSessions.ts), and it waits on the project list first, since until that lands there is no target to park for). Without the wait the read went out on the first frame, which booted a **second** child beside the park on the same CPU and left a session of its own in mcode's store **every launch**. `all()`'s own probe is left for the one case nothing else covers — a picker opened with no session anywhere, which is the provider screen on a cold app with no project attached — and **that** probe is what leaves a session in mcode's own store, which the reader will see in their TUI history. Rare path now; the launch path before. Stated in the module, not hidden here.

- **`DEFAULT_MODEL_FOR` names no model**, and that is the answer rather than a gap: mcode is multi-provider, so any constant here could name one the reader has no key for. The unset sentinel is what carries "name none of ours" — the spawn omits `--model` and the CLI's own settings decide.
- **Effort is per model and only the active one's ladder is ever stated.** One reading fills `efforts` on the row it is running and leaves the others empty, which the picker reads as "no levels" — the safe direction, since a level offered for a model that refuses it is a button whose press does nothing. Switching model restates the ladder.
- **A rung this app cannot spell is dropped, not rounded to its neighbour.** mcode's own catalog carries `minimal` on some models and [`Effort`] has no variant for it, so the lowest rung goes missing rather than a neighbour being sent in its place.
- **A model and hz's ids are one namespace.** `find_model` refuses another harness's alias, so a pick recorded by a build that ran one cannot be carried onto an mcode spawn — the backend refuses it and the picker repairs to the sentinel.

**A rung is a persisted enum, and `ultra` never reach disk as itself.** An older build reading a level it cannot spell fail that line, and the index parse as one `Vec` — so one `ultra` session read as **no sessions at all** in a release build sharing `~/.hz`. Measured, not feared. `encode_effort`/`decode_effort` in [store.rs](apps/desktop/src-tauri/src/store.rs) are the only two places that know: `ultra` go down as **`max`** — a real level that build can run, one rung below — with the truth beside it in `effortAbove`, which its `unknown` flatten carry back untouched. Decode honour that field **only while `effort` is still `max`**, since an older build rewriting the entry write its own level there and leave the forward field standing; reading it then would put the session back on a level the reader just left. Same bargain `Harness::Other` make, same ordering rule — protection ship *before* the value, never after.

**`effort_above` is a `String` and must stay one.** Typed as `Effort` it recreate the very bug it fix, one build later: the next rung a newer hz write there fail *this* build's line and take the index down. A string hold a level nobody here has heard of, so `carries_unreadable_level` **carry it through whole**. It is dropped only when the reader move the effort off the stand-in.

## What the agent costs, measured

**A cold child costs ~6.5 seconds before the first token, and it is CPU, not network — and that is the *cold* number.** Spawn to `initialize` answered is 2.7–3.4s and the *first* `session/new` on that child another 1.8–3.7s (once 12.7s, see below). **Re-measured warm** — same shipped bundle, bytes in the page cache — the same handshake is **1.0s for `initialize`, then 0.02s for every `session/new` after the first on that child**: three sessions in three different `cwd`s on one child, each under 0.06s, which is where "one child, many sessions" comes from and what the park and the picker's seed below are both built on. The spread is worth stating because it is a 6× one and nothing in the code changes between them: what moved was the page cache and the machine's load, not the bundle. Measured on the shipped launcher, against `deepseek-v4.1-flash` and `minimax-m3` alike — **the model barely moves this**: first-token was 2.16s against 2.28s, so the choice of default is about what a token costs, not about the wait. Where the boot goes: the process sits at 87–112% CPU with RSS climbing 278→426MB and **no sockets open at all**, against 0.45s for `mcode --version` — so it is V8 evaluating `dist/`, which is 98 files and 29MB of JS rather than one file. A `--cpu-prof` of a warm boot splits it **23% V8 compiling ESM, 3.6% filesystem, the other 73% the bundle's own startup code running** — so "merge the chunks into one file" buys per-module overhead and not one byte of the compile or the execution: the only lever there is shipping less code on the ACP path. `NODE_COMPILE_CACHE` writes **0 bytes** here and changes nothing (the bundle is ESM, and the pinned Node 26 has no compile cache for it), so the compile is paid in full at every launch rather than only the first. **hz still gives each session a child of its own** — `HZ_SESSION_ID` is fixed at spawn, so the agent's own identity is per process — and that is why the price is per session: the agent *could* serve many, and hz does not ask it to. So a reader reports the *first* message being slow and the second being instant, which is exactly the shape of a cost paid once per child.

**The boot can be hidden, and `prepare_session` does.** The process comes up on its own after `spawn`; nothing has to be written to it. Measured: `initialize` answers in **2.87s** cold against **0.01s** on a child left alone for four seconds. So the frontend mints the session id when the composer acquires a project and calls `prepare_session`, and [mcode.rs](apps/desktop/src-tauri/src/harness/mcode/mcode.rs) parks that child until `Session::init` adopts it. Two things make it legal rather than clever:

- **The id has to be named before the session exists**, because `spawn` is where `HZ_SESSION_ID` is fixed and the hz CLI reads it as the default session for `hz issue link` for the rest of that child's life. The composer mints one and **the send reuses it** — a second mint would orphan the parked process and pay the boot anyway. That is the whole reason `preparedRef` exists.
- **The matching rule cannot move to Rust either, and that is not a design debt.** ACP's `session/new` takes no client-chosen id — `cwd`, `additionalDirectories`, `mcpServers`, `_meta` is the whole request, v1 and v2 — so the agent's session id is always the agent's, and `HZ_SESSION_ID` is fixed *at spawn*, so the id hz's own child carries has to exist before the park does. Somebody must name it before there is anything to park, and the only caller that knows which session the reader is about to start is the frontend. **One slot, not a pool**: a parked child is ~400MB resident, and the composer parks for the project it is pointed at — three at once would be a gigabyte held for a convenience nobody switches fast enough to want.
- **It parks no *record*: no index entry, no session row.** The handshake it holds is the agent's side of one; hz's own side is created exactly where it always was, so `send_msg` writes the index entry and spawns its own child when nothing is parked. The unclaimed case is therefore the old path, a reader who types and closes the composer leaves a process to be reaped (after two minutes) rather than a session of theirs, and a failure here costs seconds instead of the send. A mismatch on either half — a worktree session asks for a tree the park was not made for — falls back to the spawn, which is the right answer for one prompt.
- **`session/new` is hidden by this too, and it is the reason the park holds a *session* rather than a bare process.** The park runs the whole handshake, so the agent's own answers are on the wire before the reader's first prompt — the command list the composer's `/` menu draws arrives while they are still typing, and `session/new` is issued then rather than after Enter. This bullet said the opposite until the code was read against it: "a request, not a boot, so idling does not pre-pay it" described a park that only booted a process, and the park has not worked that way since. What is left on the clock is the *first* `session/new` on a cold child — 1.07s, 1.76s, 3.65s, once 12.71s — which is a page-cache and load number rather than a code one, and 0.02s measured warm. **`init` prints its three phases** (`[mcode timings] spawn … open … settings …`, stderr, one line per session start), which is the whole reason that line exists: the twelve seconds were unattributable, and the transcript just looked slow. `spawn` reads near zero on an adopted child, which is the parked-session win stated as a number.

**Most of the wire is preview, and it was costing a render each.** One small turn is 262 lines and 203 of them are text deltas — the read loop's `Coalescer` now merges a block's run into one event per frame, so what crosses to the webview is a dozen events rather than two hundred. Deltas are dropped from the retained copies either way ([`ingest`](apps/desktop/src-tauri/src/session.rs) lists them with the usage updates), since the committed `assistant_text`/`reasoning` repeats the whole block at its close — so the log was never the cost, the emit was.

**A session's title used to cost more than the session.** `spawn_title_generation` ran *before* `Session::init`, so two copies of the same 28MB runtime booted at once and the reader's own turn waited behind both — and it named `minimax/MiniMax-M2.7-highspeed`, a model on the managed account hz never signs in to, so it failed every time with "managed OAuth Bearer not synced for provider \"minimax\"" after 5.09s. It now spawns after the handshake and names no model, which is the reader's own provider.

**`apps/agent` is a complete tree now, and the claim that nothing can be built from it is out of date.** It was brought in to be owned, and `release/extraction.json` names 31 `packageRoots` — **all 31 present with a readable manifest** (re-checked; the paragraph here used to name 7 as absent, which is what `build.mjs` would have failed on with `Missing workspace source`). So the source tree is no longer the obstacle: `apps/agent/scripts/build.mjs` exists, the tree has `node_modules`, and `dist/` is **gitignored** — which means a rebuild is a local artifact rather than a 55MB diff, and a *durable* build fix has to be a change to the build configuration itself. What ships is that build: `vendor-agent.sh` stages it into `src-tauri/resources/agent/{bin,hz-agent,app}`, with the pinned node beside the launcher, and `binpath` resolves `resources/agent/bin/hz-agent`. **The build has not actually been run here since the roots were restored**, so treat "can be built" as *unblocked* rather than *proven* — the first thing a pruning pass should do is run it and diff the boot against the bundle that ships today.

**What that closure check did prove, for the day it can be used.** Following `dist/metafile.json` from the ACP entry point reaches 5.545 files and 92% of the chunk bytes. **`packages/tui/src/tui/` — 258 files, 3.0MB — is zero of them**: the only importer is the interactive `launcher` path. `host/`, `headless/`, `review/`, `analytics/`, `plugin/`, `types/` and `provider/` are likewise zero for ACP. What *is* in the closure is `acp/`, `runtime/`, `application/`, `local-runtime(-v2)`, `agent-*`, `config`, `shared`, and `third_party/pi-mono` (whose *interactive* mode rides in through `coding-agent/src/index.ts`, so pruning our `tui/` alone would not remove it).

## The inbox

**Three tabs and one frame, and the tabs are not views of the inbox — they are the pages.** [InboxTabs](apps/desktop/src/components/InboxTabs.tsx) is drawn by all three surfaces it switches between: **All** is the inbox's own merged list ([InboxView](apps/desktop/src/components/InboxView.tsx), ⌘⇧I), **GitHub** is [PrsView](apps/desktop/src/components/PrsView.tsx) and **Linear** is [IssuesView](apps/desktop/src/components/IssuesView.tsx), each with its own search, sort, filters, refresh and detail pane. Pressing a tab is *the page changing* — `App`'s `selectInboxPage`, one `setPage` — which is why the row is a node the shell hands down rather than a control any one of them owns: three copies would be three rows that can disagree.

That is also the whole answer to "the GitHub tab needs the pull-requests filters": there is nothing to copy, because the tab *is* that page. The sidebar rows those two pages used to have are gone; both keep their ⌘I / ⌘⇧L chords, their palette rows and their own pane, and a row click anywhere in them behaves exactly as it did.

- **The tab row is the plugins page's own control, counts and all** — ghost buttons whose active one takes `--sidebar-selected`, no track, and a count in a smaller tabular face. **One place reads those numbers**: `App` calls [useInbox](apps/desktop/src/hooks/useInbox.ts), which owns both halves' reads and hands the rows *and* the counts to whichever of the three pages is up, because a number read in three places is three answers. Both logos are `aria-hidden`, since the word beside them is the name.
- **All three surfaces wear one header frame** — `flex flex-col gap-2.5 border-b border-border px-4 py-3`, the source row first and the page's own controls under it, with the rule beneath both. Not a rule between them: the row is navigation and what follows narrows the page. The issues page was the one that drew its controls without one, which read as a page that had lost its heading.
- **The shell reads both halves at launch, not on arrival.** `useInbox(prsCwds)` is called by `App` and never gated on a page, so the tracker round trip and one `gh` listing per repository have already been paid for by the time anybody presses a tab; `usePrList` reads once per key and polls nothing, so this is a launch cost and not a poll. It is also where the counts come from, which is the other half of why it lives up there.
- **`all` is prefetched too, by [prefetchPrList](apps/desktop/src/hooks/usePrList.ts)**, fired from an effect in `App` keyed on the joined repository paths. The state a reader switches to is the one they *wait* on — the page reads a listing per repository, and a listing is a `gh` spawn — so the one they reach for after the default is read into the same cache the page reads, and pressing it is then a filter over rows already in hand. **`merged` and `closed` are deliberately not prefetched**: four states per repository is four spawns per repository at launch, so those two still wait, and the Refresh button is what re-asks.
- **Both caches are trusted for an hour, and that is what makes the launch read worth making.** A window measured in seconds would spend it and make the reader wait on arrival anyway. The trade is stated in both hooks: an answer left on screen overnight is asked for again rather than believed, `Refresh` is the way to ask sooner, and a write throws it away outright (`invalidate`, `forgetIssues`). The sidebar's marks poll on their own clock, so a pull request that changed still surfaces there first.
- **The merged list is the only place the two trackers are read together**, and it is [inbox.ts](apps/desktop/src/lib/inbox.ts) that does it — pure and tested: the merge, the reason a row wears, the group it lands in. It reuses the pull-requests page's own three groups and its `isWaiting`/`isAuthored`, because a second vocabulary for one question is how two lists that answer it start disagreeing.
- **Both reads are the pages' own hooks** (`useIssues`, `usePrList`), so the caches, the generations and the debounces are shared rather than duplicated: the shell's launch read is the same cache the two pages draw a tab press later, and the merged list costs no call of its own.
- **A reason is a word first and a colour second**, and `null` is the ordinary answer: a draft's own glyph, an issue's state glyph and a pull request nobody has to act on all draw nothing at the row's right edge. The chip is only for what wants the reader or will move on its own — conflict, failing checks, a requested change, an approval to merge, an urgent issue. Checks still running are the sidebar's arc, one fact in one shape.
- **An issue's only claim is priority.** Everything the issues page reads is already assigned to the reader, so "yours" is not news there; `urgent` is, and it is the one signal Linear gives that outranks the queue.
- **The merged list has its own filter row and the pages keep theirs** ([inboxFilters.ts](apps/desktop/src/lib/inboxFilters.ts)): a search box over everything a row says, and a menu of Repository, Project, Time and "Waiting on you only". Local and never a round trip, because both halves arrive whole — the opposite of the pull-requests page, whose search has to be the host's. A stamp nothing can parse is **kept** by the time filter: a narrowing must not become a way to lose a row nothing is known about.
- **A note replaces the empty sentence.** A tracker that could not be read says nothing about whether work is in flight, so "Nothing is in flight" under a banner naming the failure is a claim that banner has just contradicted. A narrowing with nothing left in it says "Nothing matches that." instead.
- **The sidebar's Inbox row is lit on all three pages** (`inboxActive = inboxOpen || issuesOpen || prsOpen`). They are one destination in that column, and lit on the inbox alone a reader who had just opened an issue would see nothing saying where they are or how to get back.
- **The Linear tab is where the key field is when nothing is connected** — because that tab is the issues page, which has drawn that form since it was written. It draws the tab row above the ask as well, or a setup state would be the one screen in the app with no way off it.

## The pull-requests page

**The GitHub tab of the inbox, and a main-column view in its own right — not a session.** [PrsView](apps/desktop/src/components/PrsView.tsx), ⌘⇧L, wired exactly like the issues page: opening it keeps the selection but drops the sidebar *highlight*, the right pane's session tabs are hidden while it is up (`pageOpen` covers every page), and `goToSession` closes it. Its detail is the **same `PrPanel`** the session's tab draws, mounted beside it and given an `only` number, so a page and a tab cannot describe one pull request two ways. `tabs` is the inbox's row, drawn at the top of the header so all three surfaces wear it.

**The page and the tab answer different questions, and that is why both exist.** The tab is "where did *this branch's* work land" — usually one row, led by readiness so the reader can merge and move on. The page is "what is open in this repository", which is the question when the branch in front of them has no pull request at all, when they want to know what else is in flight, or when somebody has asked them for a review.

- **Per repository, not workspace-wide.** A listing is one `gh` call per repo; the sidebar's marks span projects because a mark is one query per repo and a row needs one glyph, where a page would be a listing per repo per refresh merged here. The repository is the session's own checkout, so switching sessions switches the listing, and the header names which one.
- **Three groups, and an empty one is not drawn**: Waiting on you, Yours, Others. A row in two goes to the first that claims it — your own PR that somebody then asked you to review is waiting on you, which is the thing to do. `viewer` null (`gh` would not say who we are) claims nothing for the reader and files everything under Others, which is the honest answer rather than a guess.
- **The state filter and the search are GitHub's, the involvement filter is ours.** `gh pr list --state` and `--search` page through a repository the client can never hold; answering "is this mine" server-side would be a second and third spawn per refresh, so `viewer_login` is one cached call and the grouping happens in [prList.ts](apps/desktop/src/lib/prList.ts), pure and tested.
- **The row is `PrListItem`, not `PullRequest`.** Fifty rows asking for fifty comment trees and check lists is a cost nobody scrolls past; a row carries the tip commit's checks folded to one word (failing outranks running — the red row is the one to open), and the detail read fills in the rest through the same `prs_for_branch` the tab uses.
- **A read that lands late is dropped** by a per-key sequence number, because the search box types faster than `gh` answers — the same guard the panel's own hook makes for a different reason.
- **The row is two lines and a card.** The split is which facts belong beside the title, and DESIGN.md's own entry says what went where and why — the one part of this page that is a judgement rather than a mechanic.
- **The header is a search box and three buttons** — Sort, Filters, Refresh. The segment pills that carried state and involvement are gone; both are submenus of Filters, which counts what is off its default. `h-7` is the row's one height, so the search, the three controls and the pills they replaced all sit on the same line.
- **`labels` rides the listing row** (`PrListItem.labels`), because the label filter is the one narrowing the client cannot delegate: `gh pr list --label` would be a spawn per tick against labels the listing already holds. Read from `gh`'s own `labels` field, with a nameless one dropped — a dot with nothing beside it is not a label. The facets the menu offers (`authorFacets`, `labelFacets`) are read off the rows rather than asked for, for the same reason.
- **A filter group's value is matched, not the group's absence.** `matchesLabels` wants **every** ticked label on the row — three boxes ticked is one narrowing, and "any of these" is the other control.
- **A failed repository is checked *before* the cache in `merged`, and that ordering is the whole of it.** A stored failure outranks whatever the cache holds for that key — the entry it holds is the last good answer — so looking the cache up first counted the repository as one that had answered, `misses` stayed at zero, and the "N of M repositories could not be read" sentence could not draw at all.
- **A failure is let go the moment a read succeeds, and nothing is cached beside one.** `failed.delete(page)` on the way out of the success path, and no empty answer written on the way out of the failure — both halves of one bug. An empty answer written by a failed read is *fresh* for the whole window, so a transient timeout was believed until the window ran out and no read was attempted in the meantime; and a failure kept after a later success outlives the blip that caused it, because `merged` checks failures first. It read as a project permanently having no GitHub repository — one network hiccup, no way back but relaunch. `Refresh` forces past the cache either way, which is what makes it recoverable by hand if it ever does stick.
- **The reason that sentence carries is `describe`'d, not `String`'d.** A refusal that crossed the bridge is a tagged object, and `String` on one is `[object Object]` — the trap [asUnavailable](apps/desktop/src/hooks/usePrList.ts) exists for, one expression over.

## Actions

**The GitHub page's second sub-tab: the repository's CI, laid out the way GitHub lays it out.** [RunsView](apps/desktop/src/components/RunsView.tsx) is the list, mounted by [PrsView](apps/desktop/src/components/PrsView.tsx) beside the pull request list and hidden rather than unmounted; [RunDetail](apps/desktop/src/components/RunDetail.tsx) is the pane. Both bodies stay mounted so a sub-tab costs neither its scroll position or its filters, and only the one on screen reads.

**Re-running is the one write, and it is the reader's own press.** CI is where a retry is the whole answer — a flake, a runner that died, a dependency that was briefly gone — and the button says which of the two it will do: a run with something red gets `Re-run failed jobs` (`--failed`), which is what a reader who watched a job go red is asking for; a run with nothing red gets `Re-run all jobs`. **Cancelling and dispatching are still out**, for the older reason: neither has the "same thing, once more" shape, and both are decisions with a dialogue attached on GitHub's own page. Nothing is confirmed, and the pane re-reads before the list does, so a row cannot go on calling a run failed while the pane asks for it again.

- **The detail is one extra spawn, for the run that was asked about.** `gh run view --json jobs` carries the jobs and their steps, and thirty of those in a listing would be thirty spawns for a pane that shows one. **The step list is the whole reason the pane exists**: the row says a run failed, and the jobs are where it says which step did it.
- **One run at a time, where the pull request pane holds several.** Comparing two attempts at one fix is why that strip exists; a run is read at one moment and answered once, so a pick replaces the strip rather than adding to it, and the way back is the row that was clicked.
- **A job's log is the job's, and the toggle is on the job's row.** The wire cannot attribute a line to a step — a step with a `name:` is titled in the log by its *command* — so a per-step disclosure opened the same log under every row the reader tried.
- **The log's step column is useless and the group marker is the join.** `gh` answers `UNKNOWN STEP` for every line of a real run, so a line belongs to a *job* by the log's first column and to nothing narrower. The log is flat — every group opens and closes at depth zero, so an action's internal groups are siblings of the step that opened them — which is why `logGroups` splits on the headings rather than walking a tree.
- **The `##[error]` lines are lifted above the log and name the failing step.** The runner's own sentence is one line in four hundred inside a box that scrolls; the band says which step it came from too, which is one field away in the job's step list.
- **The log is a numbered stream, and a shut group shows the number of its first line.** That is GitHub's own device and the reason the numbers exist: a folded `2 Runner Image Provisioner` followed by `4 Run actions/checkout@v4` says it holds lines 2 and 3 without being opened. `logGroups` carries each block's `at`, the drawn number is `hidden + at + 1` — the tail drops the front, so a number is a line's number **in the whole log**, never in what happens to be drawn. The search answers flat, keeping each hit's own number.
- **A step's log is not shown, and that is a fact about the wire rather than a choice.** GitHub's own job log puts each step's output under that step — and it can, because its backend attributes every line. What the CLI exports cannot: `gh run view --log`'s step column reads `UNKNOWN STEP` on every line (measured, and pinned by test), and a step with a `name:` is titled in the log by its **command** (`Run ssh …`). So a step's output cannot be lifted out, and a disclosure per step opened the *same* log under every row the reader tried — the app draws the job's log instead, one record, with the runner's own groups as its headings.
- **Read on demand and never in the listing.** `get_run_log` answers what `gh run view --log` printed — a string, because the only structure in it is the `##[...]` markers the runner wrote into the messages — and it is the biggest thing this app asks GitHub for (~190KB for one failed release). `LOG_LINES` caps the drawn tail and says how many were left out.
- **Both reads are cached per repository and polled only while something is in flight** — 15s, gated on the page being on screen. The runs list is trusted for a minute, not the hour the pull request list keeps: a push starts a run within seconds, and a listing that believed itself for an hour would answer "nothing here" about a build that started a moment ago.
- **Fixtures are real captures, and one is read by both sides.** [gh_run_list.json](apps/desktop/src-tauri/src/fixtures/gh_run_list.json) is `gh run list --json` against this repository; [gh_run_view.json](apps/desktop/src-tauri/src/fixtures/gh_run_view.json) is a release that went red — two jobs, fourteen steps, a failure among them and one job skipped by its own `if:` with no steps; [gh_run_log.txt](apps/desktop/src-tauri/src/fixtures/gh_run_log.txt) is that run's `--log`, asserted by the Rust mapper *and* by [logs.test.ts](apps/desktop/src/lib/logs.test.ts), which imports the one file rather than committing a second capture. **The skipped job is the capture that corrected the code's own assumption**: it carries a start *and* an end, so its empty step list — not its stamps — is what says it did nothing.

## Pull requests

**A session's PR is a tab in the right pane** ([PrPanel](apps/desktop/src/components/PrPanel.tsx)), rendering readiness, checks, comments and the merge action.

**`gh`, not the REST API** — it already holds auth, enterprise host config and token refresh. Cost: the feature is absent where `gh` is missing or logged out, surfaced as one readable line. Resolved through [binpath.rs](apps/desktop/src-tauri/src/binpath.rs), returning `Option` rather than a bare-name fallback.

**A missing `gh` keeps the tab and is drawn as a setup pane, and that reverses the older rule** (DRA-258). Hiding it made the feature invisible on a machine that never had the CLI — the marks fail silently and the handoff row's Create PR only fails inside the agent's turn, so nothing anywhere said that one `brew install` puts pull requests on this screen. **The exception is exactly two states**, `no_cli` and `not_authenticated`: everything else follows the rows, so a *refresh* that failed still draws its sentence under pull requests already on screen while an error with no rows takes the tab away rather than leaving one that can only say "this went wrong".

Without `gh` **every** directory answers `NoCli`, since the first call fails before anything has looked at the checkout — so `prs_for_branch` asks `git::has_github_remote` and answers `NoRemote` where there is none, or a gh-less machine grows a PR tab on every session it has. Any remote counts, and the match is on the URL's **host** — a remote *named* `github.com-mirror` and the host `github.com.example.net` both pass a contains-check over `remote -v`, the trap `is_upload` documents next door. Hand-rolled rather than `url::Url`, which refuses `git@github.com:owner/repo` outright. An enterprise host is not `github.com` and reads as no GitHub remote, costing a prompt to somebody already on a GitHub this app cannot name.

**The pane copies and never runs.** macOS lets no app put text on another's prompt without an Accessibility grant, so the honest pair is the command with a copy on it and a terminal opened at the session's `cwd` to paste into — where a button that ran an install would be hz deciding what to execute in the reader's shell. The terminal is `OpenInButton` wearing a third hat, `TERMINAL_OPENER`: terminals alone, its own stored pick (`hz.runInTerminal` — the dir opener's holds editors and Finder too), and `Opener` gains `label`/`hint` so a control standing alone in an empty state can name the app on its face instead of in a tooltip. It needs nothing new in Rust, `open -a <terminal> <dir>` being the shape [apps.rs](apps/desktop/src-tauri/src/apps.rs)'s table already promises.

**`binpath`'s `gh` slot is therefore an `RwLock`, not a `OnceLock`** — it is the one cached answer here that caches an *absence* the reader is being asked to fix, and `recheck_gh` throws it away, so an install made on that pane's say-so is found without restarting the app. **A generation rides that**, the issue caches' own bargain: a probe already running when the reader installs `gh` would otherwise finish and publish its miss back over the answer, undoing the recheck with a reading older than it. It still answers its own caller — who asked before the install — and only the cache refuses it. The pane says so when it still finds nothing: a button that redraws the same screen reads as broken, which is the one thing a pane asking for an install cannot look like. The logged-out half has no such answer to give — `gh` has not moved, and only GitHub knows whether the login took — so it re-asks and leans on `loading` for the same promise made quieter.

**One `gh api graphql` carries the whole panel, and avatars are why it is not `gh pr list --json`.** The rollup `gh` hands back has no image on it, and `github.com/<login>.png` **404s for exactly the accounts that matter** — a GitHub App's real login ends in `[bot]` and `gh` strips it.

- **GraphQL fails with 200 and zero exit** (`{"data":null,"errors":[…]}`), so check `errors` before `data`, or "could not resolve repository" reads as a branch having no PR.
- **The rollup is heterogeneous** — `StatusContext` names itself on `context` and reports on `state`; `CheckRun` on `name` / `status`+`conclusion`, image at `checkSuite.app.logoUrl`. Tagged on `__typename` with `#[serde(other)]`. A running check has **null** conclusion where `gh` sent an empty string.
- **Every connection's `nodes` is nullable.** `Option` is load-bearing: a PR with no comments otherwise fails the whole response.
- **One branch can carry several PRs, so the backend answers with a list**, open-first then newest.
- **Inline comments live in `reviewThreads` alone** and join to reviews on `pullRequestReview{id}`. A review's `body` is top-level text only, so an empty envelope holding threads is **kept** — it is the only row naming who left them — while an empty one holding nothing is dropped unless it approves.

**Readiness is three overlapping fields read in one fixed order** ([pr.ts](apps/desktop/src/lib/pr.ts)): `state`, `mergeable`, `mergeStateStatus`. The order is the whole logic — a closed PR's merge state is stale, conflict outranks failing checks, and `UNKNOWN` means GitHub hasn't worked it out rather than no. A pure function with its own tests, not JSX conditionals.

**Polling**: 15s while something is in flight, 60s otherwise, gated on `active`, cached per `cwd + branch` for 30s. Gate on *any open PR on screen*, never *any check running* — a check that hasn't registered yet leaves the rollup empty exactly like a repo with no CI, so the tighter read polls zero times during the only window that matters. `active` is read off the stored **pick**, not `activeTab`, which derives from this hook's own answer.

**A PR appearing means a turn ending, and nothing else could see it**: the tab is hidden exactly while the answer is "no PR", so it could never self-heal. Refetch on the **falling edge of `busy`** in `App`, with the session id riding along in that ref since `busy` is the *selected* session's. Appearance also opens the pane once, through `onOpened` fired inside `load` — only the fetch knows the previous answer, and that is the whole guard. Key-guarded, so a read landing after a session switch cannot pull the pane onto a branch the reader left.

**Every write refetches**, and reaches past the pane: `onChanged` fires `prMarks.refresh`, and unlike every other write there it is **not** key-guarded, since a repo-wide answer is true whether or not the reader is still looking. **A merge that fails is checked against the PR before being reported** — `gh pr merge` can fail with the merge already through, so `merge_pr` re-reads `state` and answers `Ok` only where it comes back `MERGED`.

**No `--delete-branch`, and a Close that is deliberately its own button.** Delete-branch: a worktree session has that branch checked out, so `git branch -D` refuses it and cleanup fails after the merge already landed. Close: it used to be missing entirely, on the grounds that abandoning a pull request is a decision with a discussion attached — and the discussion is now answerable in this pane (below), so the trip to a browser was the only thing left it was buying. It is confirmed inline like the branch delete, because it is not the same act as a comment, and it leaves the branch alone: [`delete_branch`] is its own button and a close is not a cleanup.

**It writes prose, and that is a reversal.** The panel used to read and act and never say anything: no comment, no reply to a review, no review of its own, no reviewer request. What changed is where the conversation is — the reader is looking at the thread a reviewer left, and making them open a browser to answer it is a trip for nothing. What did *not* change is who composes the words: every one of these takes the reader's own text and passes it through untouched, and nothing here writes a sentence on their behalf.

- **One body, one stdin.** A comment, a reply and a review note all travel down the pipe (`--body-file -`, or `gh api graphql --input -`) rather than through argv — prose is of any length and holds anything, and an argument is neither.
- **A thread is addressed by its own node id**, which is why `PrComment.threadId` exists: a reply and a resolve are GraphQL mutations keyed on that id and on nothing else — not the PR number, not the path, not the line — and it rides the one comment that opened the thread.
- **`gh pr review` for the verdict**, GitHub's own three flags, with the body only when there is one: `--comment` with nothing to say is refused by GitHub, and that refusal is GitHub's sentence rather than ours.
- **Reviewers by login, cleaned here.** No list of the repo's collaborators is read for it — that is a point on the API for a field the reader can fill in from memory, and `gh` refuses the whole call over one bad name, so the trim and the `@` strip are what decide whether asking three people works.

**Branch name read first, rebuilt only as fallback.** `sessionBranch` takes `observed` (`work_status.branch`, git's HEAD) and it wins wherever the session still has a checkout of its own. Everything else is a **guess made at creation** and never re-read, so a `git checkout` inside the tree leaves both naming the wrong branch and the PR tab fails **closed**. `observed` null is a resting state. **`worktreeRemoved` is the one case `observed` loses** — a relocated session's checkout is shared, so HEAD there never answers "where does this session's work land"; `relocate_session_to_project` sets that flag beside clearing `worktree_name`. One function, and `SessionHeader` takes the result as a **prop**. Sidebar rows still read the guess, deliberately: marks are one `gh` per repo, where a per-row branch read is one `git` spawn per row.

**The hook lives in `App`, not the panel** — the tab row must know whether an open PR exists *before* that tab is shown, so its first read is **not** gated on `active`; only the poll is. The sidebar's mark stands in while the panel's own read is out (`hasPrTab = prTabVisible(…) || (loading && mark)`), and once the read answers the panel's answer governs.

**Sidebar marks** ([usePrMarks](apps/desktop/src/hooks/usePrMarks.ts)) ask `pr_marks` once per **distinct repo** among visible sessions, since `gh` costs better part of a second. `QUERY_MARKS` carries `number headRefName isDraft`, the tip commit's rollup **state**, and `mergeable mergeStateStatus` on the open half for the ready-to-merge notice — nothing else, since a row draws one glyph.

- **`PrChecksState` folds GitHub's five-way `StatusState` into `Running` / `Failing` / `Clear`**, unrecognised words reading as `Clear` — the safe direction. Running is a spinner in the timestamp slot; failing turns the PR glyph red and `prStateLabel` says so too, since red-green is what this palette can least afford to make load-bearing. **Passing draws nothing.** Red only while open or draft. The field is `checks_state`, since `checks` is already the list of individual `PrCheck`. The glyph table is shared with the panel ([PrStateIcon](apps/desktop/src/components/PrStateIcon.tsx)).
- **Matching lives in the frontend** — the backend answers a list, not a map, because which branch a session lands on is the frontend's own rule.

**The marks cache is module-level per repo, fresh 120s, and a failed read changes nothing — no row written, no stamp.** Not writing keeps the last good mark on screen; not stamping stops a failed read re-certifying an answer a write just invalidated. A module `generation` counter is what makes `refreshAfterWrite`'s clear stick, since a read issued before the clear must not put its stale answer back; `inFlight` carries it too, because "a read is running" is not "a read will answer for me". The poll reads only repos holding an open PR, or a directory `gh` can never answer for takes a failing spawn every 30s forever. The archived view asks for no repos and therefore draws no check spinner — a stale glyph is an accepted trade, a stale spinner animates a claim about now.

**Marks and panel tell each other what they learned, signal only — never data** ([prSync.ts](apps/desktop/src/lib/prSync.ts)), since two caches with nothing joining them left a "Ready to merge" card on a panel still saying checks not passing. Marks emit `branchChanged` carrying **repo and branch**; the panel emits `panelRead` and the marks side asks `markDisagrees`, comparing checks *loosely* since neither fold can fill the other. A panel-triggered marks read **echoes nothing back for the branch that triggered it**, or the pair spawn `gh` at each other forever.

## The repo view

**The main column is the transcript and nothing else.** Diff, Browser and Files are tabs of the right pane ([RightPanel](apps/desktop/src/components/RightPanel.tsx)) — see _The files view_ below and _The browser_ — so the column has no tab row of its own, and picking a view never hides the composer. Accelerators are ⌘⌥1/⌘⌥2/⌘⌥3, named per *view* rather than per slot, since a rebinding names the view and not its position in the row; the bare ⌘ digits belong to the split view's panes. The pane's tab is per session and **not persisted**, and `showPanelTab` is the one way to arrive on one: the pane may be closed, and a tab set on a hidden pane is a change nobody sees.

**The pane has two sizes, and that is what makes a two-pane view fit in it.** Wide (`⌘⌥E`, or the button leading its row's far end) it takes the column and the transcript is hidden behind it; narrow it sits beside the transcript at the width the reader dragged. Diff's file list and Files' tree want room a 512px pane does not have next to a conversation, and `flex-1` is where it comes from. Three things hold it together:

- **`panelExpanded` is app-wide where `panelOpen` and the tab pick are per session.** Those two are about a session's *content* — a pane opened on one session's PR was blank beside the next — where this is about how the reader is looking at something, and switching sessions to glance at another does not ask for the room back.
- **`panelWide` is `panelExpanded && panelShown`**, never the flag alone: a page owns the column, so it collapses the pane without clearing the flag and the pane comes back wide on the way out.
- **Three readings have to follow it.** The pane stops publishing its width (`pane: open && !wide ? "panel" : undefined`) or `Sidebar` reads it as a pane bidding for the whole window; `chatShown` is `!pageOpen && !panelWide`, which is what `Chat` and `SplitView` take as `active` — a transcript nobody can see must not follow the stream, since a `scrollTop` written against a `display: none` element lands at zero; and `gridShown` gains `!panelWide`, or ⌘W closes a split pane behind a transcript nobody can see either.

Cost, stated: the window's header goes with the column, so the session's name is off screen while wide — the pane's own row is the only one left, and it carries the drag region. The composer goes too, the same bargain the pages make. Two things have to be handed over with it: `AppShell`'s `columnHidden` is `display: none` rather than an unmount, so the transcript keeps its scroll position and its backfilled turns across a trip in and out; and the **collapsed sidebar's toggle rides the pane's row as `lead`**, because a collapsed sidebar renders nothing and the traffic lights plus the only way back to it both land on whatever reaches the window's left edge.

**There is one diff, and the turn leads it.** The pane's Diff tab renders [ChangesView](apps/desktop/src/components/changes/ChangesView.tsx) — Turn, Uncommitted, Branch, History — where the main column used to hold it. **Turn** is the newest prompt's snapshot against its turn's closing one, which is the pair the toggle's git glyph is read off; the other three read off HEAD and the branch, which is a wider question than one turn. `defaultSubTab` opens on Turn when it has files, and only once *every* read has answered — the turn's included, which never runs at all for a session with no baseline, so "not answered" and "nothing to answer with" are told apart before the row is latched. The pane's own reads are `ChangesView`'s, run off `revision` and off becoming the tab on screen, so the frame's one Refresh button is absent on Diff.

The panel's Diff tab is mounted the same way the rest of the pane's bodies are — `TabBody`, so the transcript **hides, not unmounts** and scroll position, follow pin and highlighted diffs survive a page; and keyed by session, so a selection, a sub-tab and an open commit reset with it.

- **`head_tree` answers `None` for one thing only: not a repository.** A repo with an **unborn** branch answers the **empty tree** instead, the honest baseline there. `null` alone still says two things — "no repo" and "not asked yet" — so `useHeadTree` carries `settled` and the empty state waits on it.
- **The uncommitted list is the HEAD tree against a live snapshot** (`changes_since(cwd, headTree, None)`). A commit moves HEAD → a new tree id → the cache key rolls onto the new baseline by itself. **Nothing invalidates anything.**
- **Commit SHAs pass `is_tree_id` and every diff path takes them unchanged** (≤64 hex), so a commit's own diff is `useChanges(cwd, commit.parent ?? EMPTY_TREE, commit.sha)`. A root commit's parent is `None` and `EMPTY_TREE` (`4b825dc…`) stands in, so the first commit in history opens like any other.
- **The selected file is derived, never stored** (`find(path) ?? files[0]`), so a file that stops being changed can't leave the pane pointing at nothing.

**The view reads, with one exception, and the rest is not "not yet".** The conversation next door is where work gets made and committed, so a second place to write commits is a second way to do what the reader is already asking the agent for. No checkbox, no message box, no push button, no fetch, no pull. **Undo is the exception, and it is the inverse of that rule rather than a hole in it** — nothing else in the app can take a turn back: asking the agent costs another turn, is non-deterministic, and is itself work the reader has to supervise, where an undo is exact, instant, and the first thing anyone reaches for when they watch a turn go wrong. What keeps it from being the arbitrary `discard` this rule was written against is that it is **scoped to one turn's own range** and takes nothing else.

**`undo_turn` restores a turn's range and refuses anything touched since** ([git.rs](apps/desktop/src-tauri/src/git.rs)). It takes the two snapshot ids the Turn sub-tab is already drawn from — no new state, no journal, no per-file bookkeeping:

- **Writes only the turn's paths.** The pair of tree ids names exactly what that turn touched, so a file the reader had already dirtied before the prompt sits in both trees at the same content and is not in the range at all. `git restore --source=<baseline>` with **no `--staged`**, so the index stays where the reader put it — a restore that staged itself would put their next commit out of step with their working tree. A path the baseline does not hold is one the turn *created* (an addition, or a rename's new name) and is removed with `remove_file` rather than git, since `restore` wants a path its source has.
- **Refuses the whole turn if any of its files moved since.** The turn's closing snapshot is a fixed tree, so `changes_since(head, None)` is exactly "what has changed since this turn ended", and a path in both lists is a hand edit, a second session or a rebase. Restoring over one of those takes work nobody asked to lose and there is no safe partial answer: the files are one turn's work, not a set to pick from. So it names them and writes nothing. MonoCode's `foreign_touched`, arrived at with machinery hz already had.
- **Leaves empty directories behind**, and that is a deliberate stop rather than an unfinished edge: deciding which empty directories were the turn's is a guess, and git does not track them either way.

The control is on the **Turn** sub-tab alone — the range it names — and the question takes the sub-tab row instead of a dialog: it is one decision about the pane the reader is looking at, and a modal over a 288px column covers the thing being decided.

## The files view

**A third tab beside Diff and Browser, and it reads for the same reason the repo view does.** A tree down one side, an editor's tab strip and a code pane down the other. No editing: the Docs panel edits markdown because a doc is the *reader's*, where code is the agent's and this view's whole promise is that it changes nothing. Design and what was left out are in [FILES-PLAN.md](apps/desktop/FILES-PLAN.md).

**Two commands and one generalisation.** `list_dir` and `read_file` join `files.rs` beside the `@` picker's index, and `watch_docs` takes a **scope**.

- **Order is VS Code's** — directories first, then case-insensitive by name. `.git`, `.svn`, `.hg`, `.DS_Store` and `Thumbs.db` are dropped, which is VS Code's `files.exclude` defaults and nothing else: `node_modules` and `target` list like any directory, **dimmed rather than hidden**, since a tree that hides what is on disk is lying about it.
- **`ignored` is `git check-ignore --stdin -z`, one spawn per listing.** Nested `.gitignore`s, `info/exclude` and the user's global ignore in one answer, which the `ignore` crate already in the lock file cannot give. Exit 1 means "none of them" and is an answer; only a non-repository or a git that will not run leaves every flag down. **The input is written from its own task** — git streams its answer as it reads, so filling both pipes before draining stdout is a deadlock on a big enough directory.
- **`isDir` is read off the link's *target*.** A symlinked directory expands like any other; a broken link lists as a file rather than as a folder that answers nothing.
- **`read_file` is `read_doc`'s three checks at a 4MB cap**, with images answered first as a `data:` URL — the asset protocol is scoped to the attachments directory and stays so, so a file anywhere else has no URL the webview can fetch. The cap is four times the doc panel's because a lockfile is the file most likely opened here and the renderer already goes plain text past 100KB, so a big one costs scrolling, not freezing. SVG is an image here though `attachments.rs`'s table calls it a file: that table is the *model's*, and the API refusing an SVG says nothing about a webview.
- **`watch_docs` takes a scope and `WATCH` is a map.** The Docs panel passes `"docs"` and this view `"files"`. Without it the two silently take each other's watch away on every open, since the command replaces a scope's set outright; `doc_changed` stays shared, each listener already filtering on its own open set. It is also now **`#[tauri::command(async)]` over a synchronous body**: a plain command runs on the **main thread**, and this one builds an FSEvents watcher and drops the scope's previous one, a drop that joins that watcher's thread. Re-arming is every session switch since this view arrived, so the freeze it bought was one met while doing nothing unusual.

**`useOpenFiles` is `useDocs` without the draft half** — per session, module-level, `useSyncExternalStore`d, in memory only. The `opened` counter is what brings the pane's Files tab forward, for the docs panel's reason: reopening a file already on screen leaves the list unchanged, so only a count of clicks can say the reader asked. **`reveal` is a second counter and it is not redundant** — `line` alone cannot scroll, since clicking one link twice asks to be taken back to a line the pane is already sitting on.

- **The store speaks absolute paths, the tree relative ones.** A chat link can open a file from outside `cwd` entirely; the tree stays rooted at the session's directory and the header draws an outside file's path whole.
- **Reads adopt the file silently, always.** Nothing is compared and nothing can be lost, because nothing here edits — so an agent rewriting what the reader is looking at should move the text under them. `doc_changed`, the turn ending and the header's refresh all land in one function.

**The tree relists on the turn ending, and nothing polls.** Every *expanded* directory, one `list_dir` each, gated on the view being the one on screen. Expanding caches until that relist, so collapsing and reopening is free. **Rows are `flattenTree`'s flat list** ([fileTree.ts](apps/desktop/src/lib/fileTree.ts), pure and tested) because the keyboard works on a list: ↑/↓ are one step through an array where a nested render would have to walk a shape the DOM only implies.

**Every row is `memo`ized and the click handler is one stable function, and that pair is load-bearing.** This view re-renders on every session event — a streaming turn is one per delta — so a tree with a few hundred rows open otherwise reconciles all of them at the speed an agent types, which is how a view that only *reads* manages to freeze the window. An inline arrow per row defeats the memo entirely, so `activate` is a `useCallback` and `FilesView`'s `openRelative` above it is too. Both change only when the reader expands something or a relist lands, which is when the rows have to be reconciled anyway. **The cursor takes real focus with it**, which is what makes Enter honest — every row is a button, so the browser activates the focused one, and a cursor drawn beside a focus that stayed behind would open whichever row was clicked last. Enter is therefore **absent** from the key handler: handling it there too toggles a directory open and shut in one press. Not virtualised, deliberately — a tree that large is the reader's own doing and the Diff view's list draws the same way.

**The filter box is the `@` picker's index, so it is already built and already watched.** An empty box draws the **tree**, never a ranked list of everything — that is what an empty filter means here. The tree is **hidden, not unmounted**, while a query is up: the expanded set is what the reader built and clearing the box has to give it back. Escape clears and puts focus back on the tree **next frame**, since the tree is `display: none` until the clear commits and focusing that does nothing at all, silently.

**Two tabs with one basename get their parent appended** (`index.ts — changes`), computed in `tabLabels` over the whole list — a name only stops being unambiguous when a second file arrives, and the tab that has to change is the one already on screen. Closing the active tab activates its left-hand neighbour, or the right-hand one at the start. ⌘⇧←/→ step the strip, `skipInTextField` for the filter box; ⌘W closes the active tab, through `tab.close` in `App` rather than a binding here — see _Closing with ⌘W_.

**The viewer is `CodeView`'s `File`, full height, inside the library's `Virtualizer`.** Same shared Shiki, same worker pool, same `useHighlighter` gate with a plain `<pre>` meanwhile. The `Virtualizer` is the scroll container and its presence alone is what makes `File` a `VirtualizedFile` (`useFileInstance` reads the context), so only the rows in and around the viewport exist — measured on an 8452-line lockfile in Safari, 400 rows in the DOM against 16904, and a tab switch painting in ~56ms where it took 480–900ms (DRA-238). `overflow: "scroll"` is load-bearing there: it is the library's uniform-row path, nothing measured per line, and the default 20px metric is exactly the `--diffs-line-height` its rows draw at — set that variable anywhere and `metrics.lineHeight` must follow. **A line a link named may not be in the DOM yet**, so the mark scrolls the pane through `getLinePosition` when its row is absent, and the post-render that follows marks it; the plain `scrollIntoView` still serves a row already drawn. **The line a link named is marked through `onPostRender` plus `unsafeCSS`** — `[data-line-index="line-1"]` inside the host's shadow root, scrolled to centre once and given `data-target`, painted from the library's own `unsafe` layer the way `DiffPane` overrides its gutter. Zero-based on the wire, one-based to the reader; a line past the end marks nothing, which is the right answer for a stale reference.

**A chat link no longer leaves the app.** `openPath` sends markdown to the Docs panel and everything else here; **⌘-click is what still reaches the reader's own editor**, line and all — the same "out there, not here" the issue rows and the link dialog already mean by it. `ChangesView`'s file rows are left alone: a diff and a file are different answers.

**One row, not two: the Open button rides the tab strip and there is no filename header.** The tabs already name the file, so a header under them said it twice — the reading the Docs panel's chip strip takes. **A tab carries no `title` either**: the full path on one drew a native tooltip, which is the app's own rule broken (chrome is a real tooltip or nothing) and read as a directory hanging off the cursor on a tab the reader was passing over. `tabLabels` appends the parent where a basename stops being unambiguous, which was the only moment the rest of the path was worth saying. The close cross keeps a real tooltip, and names ⌘W on the **active** tab alone — the chord closes whichever tab is active, so a background cross naming it would promise a key that closes a different file. **The button is `OpenInButton` wearing a second hat.** The split button the right panel hands a *directory* to now takes an [`Opener`](apps/desktop/src/lib/openWith.ts) — the key a pick is stored under, which apps are listed, which one stands in for a missing pick, and what opening even *means*. Directory and file differ on all four, and Finder most of all: it **reveals** a file and opens a directory. One control for both, or the reader would have two places to say which editor they use and they would disagree — and the file half has to resolve exactly as `openFile` does, or the button names one app while a ⌘-click in the transcript reaches another.

**The list's side and width are the reader's, in local storage** (`hz.filesListSide`, `hz.filesListWidth`). **It opens on the right**, against every other list in the app: the sidebar already holds the left edge, so a tree there puts two lists back to back with the code squeezed between them. The switch is one icon button beside the filter; the width is a drag handle, the first in the app, and it **writes on pointerup alone** — the value moves on every frame and only the last one is a preference. `setPointerCapture` is load-bearing: without it the pointer leaves the strip on the first frame and every move after that is delivered to the code pane.

## Spaces

**Membership is a tag on the project and that is the whole record** — `Project.space` in [projects.rs](apps/desktop/src-tauri/src/projects.rs), no spaces file, no id, no ordering. `#[serde(default)]` is load-bearing: the projects file is rewritten whole, so an entry written before the field existed failing to parse is *every* project gone.

**A space nobody has filled yet has nowhere to live in `projects.json`, so existence is a union.** A made space is declared in local storage (`SPACE_LIST_KEY`) and `spaceNames` reads the two together — the reader's list plus every name a project carries. A tag whose name was never declared still counts, or a project filed on another machine would read as filed nowhere. Rename writes both halves and the reader's own pick; remove takes the name out of the list and clears the tag from its projects, which is why it asks first. **Projects and sessions are untouched either way** — a space is a way of looking at them, so losing one costs the view and never the work.

**Switching space narrows what is drawn and nothing else.** Every session in every space keeps running; one finishing elsewhere simply says nothing until the reader comes back. The rules are [space.ts](apps/desktop/src/lib/space.ts), pure and tested, and the narrowing lands in **one place** — `visibleSessions` in [App.tsx](apps/desktop/src/App.tsx), which is what the sidebar draws, what ⌘⇧↑/↓ walks and what the PR marks and the ready notice read — so a hidden session cannot come back through a side door.

**What is *on screen* is reconciled by one effect, never at the switch.** The sidebar filters itself, but the composer's project and the open transcript do not — and switching is only one of the ways a session leaves the space it was in: filing a project elsewhere, detaching it, or a stale notification opening a session move the same boundary. So `App` states the invariant once — what is showing must be in the space — rather than listing the ways it stops being, each of which was its own bug. The project is judged first and independently, since **a space holding nothing is ordinary** and a stale pick still sends: the picker draws "Attach project" while `send_msg` runs happily in the project the reader walked away from, hence `handleSelectProject(null)`. A session whose project neither the index nor the loaded snapshot can name is **left alone** — that is "cannot tell", not "elsewhere". It is a `useLayoutEffect`: an ordinary one runs after paint, so a switch drew one frame of the transcript being switched away from, which is nothing to the reader and everything to the room watching them share the screen. Notices are the one thing dropped at the switch itself, since a card raised a moment earlier opens a transcript the reader just put away — and they are dropped by the *announce* rule, not the screen one.

**Rename and remove are one Rust call, `retag_space`.** The declared list and the tags are two records of one fact, so a loop of per-project writes with the list updated up front left half-renamed tags beside a list claiming otherwise. One read, one edit, one write under the lock; the local record follows only once it lands. Retagging a space no project carries writes **nothing** — that is the ordinary path for renaming one nobody has filled.

**Notifications answer to the space; the dock badge does not.** `announce` drops both channels for a session filed elsewhere, since both name the session out loud and a personal one named over a shared screen is what spaces exist to stop. The badge counts every session deliberately: it names nothing, and a number that lies about work waiting is worse than one that admits another space exists.

**Every card asks `canAnnounce` first, not just `announce`.** The two worktree notices are raised outside it, land after an `await`, and carry the session's **title** — so the reader can be in another space by the time one arrives. The dialog route beside them is deliberately unguarded: the reader pressed a button and is owed its answer. `usePrReady` needs no guard, reading `visibleSessions`, which is already narrowed.

**A session that cannot be attributed is refused while a space is up**, not let through — `allowedInSpace`, shared by `announce` and by the notice sweep, since a card and a banner say the same sentence out loud. The index holds one side of the archived split at a time and a new session's entry lands after its first events, so "not in the index" is not "not filed elsewhere"; the loaded snapshot is the only other place a `projectPath` can come from. Cost, stated: a settled session in the *active* space stays quiet while the reader is on the live list. **The opposite direction governs the screen**, above — refusing to announce costs a notice, refusing to draw costs a transcript already open.

**The active space is read at the event, never held.** `announce` runs from a listener registered once, so a captured copy would be the space the app launched in for the rest of the run — hence `SPACE_KEY` and `readLocalStorage`, the same bargain `cycledModels` makes with the hidden models.

**Switching takes the screen with it**: the project filter resets, the composer moves to a project the new space holds, and a transcript from outside it is closed. Each only where it actually falls outside — a space holding both changes nothing but the list.

**The switcher sits in the sidebar's titlebar strip and is drawn whether or not a space exists** — it is the one place in the app that says spaces are a thing, and a control appearing only once you have found the setting can only be found by someone who did not need it. Its **New space** item opens Settings' Spaces tab with the field already up rather than growing a second way to make one.

**That tab is two lists, and the split is what each is for**: the projects list files a project into a space it already has, and the spaces list is where one is made, renamed or removed. Creating from inside a project's picker put the one thing that changes every other row inside the row least likely to be opened. The projects list draws **every** project whatever space is up — narrowed by the active space it would hide exactly the rows somebody opens it to move.

## Issues

**The surface says "issue", the implementation says Linear.** Vocabulary in [issues/issues.rs](apps/desktop/src-tauri/src/issues/issues.rs), wire in [linear.rs](apps/desktop/src-tauri/src/issues/linear.rs). A second tracker is a module plus a variant on `IssueTracker`, which is why `IssueRef` carries a tracker while there is only one. The connection is workspace-wide — no project ↔ team mapping. **Every user-facing string is collected in [COPY-ISSUES.md](apps/desktop/COPY-ISSUES.md)**; reword there and here together.

### Credentials

**The key lives in `~/.hz/credentials.json` at `0600`, the account cache in `settings.json`.** Read together: credentials say whether a key exists, settings say whose it is, and a cached account with no key behind it reads as **disconnected** — the key *is* the connection.

- **Own file, not a field on `settings.json`**, for two reasons that both bite: settings are rewritten by every toggle and read on a launch path where a parse failure falls back to defaults, which would silently *forget* the key; and `get_settings` hands that struct to the frontend, which a credential must never ride along with.
- **Mode rides the *create*, on the temp file** — not set after the write, not on the final file after the rename. `fs::write` creates at the process umask, so every other order leaves a window where the key is world-readable, where `OpenOptions::mode` plus `create_new` leaves none. Pinned by test; the failure is otherwise silent.
- Keychain was tried and retreated from — macOS ties the grant to the exact binary, so every rebuild is a new authorization dialog. Cost: the key is readable by anything running as the user, in a directory that is `0700` and already holds every transcript.
- **Validated before saved**, and `verify` also answers identity. **A write to either side forgets every cached issue** (`forgetIssues()`), since every cached answer was read with the old key — the `not_connected` failure the empty state is drawn from included.

### Tags and links

**A tag carries the title itself** — `#DRA-53 Add issue tracker integration`, everywhere: picked from the composer's `#` menu, typed by hand, or appended by the CLI's `--issue` (`tag_text` in Rust, `issueTag` in [issue.ts](apps/desktop/src/lib/issue.ts), pinned both sides). The title being *in the text* is what makes the feature cheap and what keeps the composer's overlay in register with the textarea underneath. Descriptions are not injected: the agent has the tracker's own MCP server and can fetch what it wants, where a pasted description is stale the moment somebody edits the issue.

- **Resolution is best effort, always.** Unreachable Linear, a revoked key, an identifier that doesn't exist — all leave the tag as text, record no link, say nothing. A send must never fail because the tracker is down.
- **Best effort stops short of losing a named issue.** A tag the reader typed is already in the prompt; one arriving through `--issue` is not, and dropping it left the model with no mention of the work at all while **answering identically to success**. So a named issue that resolves to nothing is appended bare (`#DRA-53`) and linked bare.
- **A tag in prose is a mention, and a mention links nothing.** `ExpandedTags` answers two lists: `mentioned` (rides `user_message`, so the tag draws as a button) and `linked` (written onto the session). Only a caller naming an issue outright — `hz new --issue`, `hz issue link` — puts anything in the second. Every `#DRA-53` used to link, so "this is unrelated to #DRA-53" filed the session under DRA-53 forever.
- **One tagging rule per side of the bridge.** Everything the app sends tags in prompt *text*, so `send_msg` always passes an empty issue list; the CLI's `--issue` names them outright. Both merge inside `expand_tags`.
- **Send answers with links as written, every path** — created, live, queued, resumed — as a whole list, not a delta, since re-tagging *replaces* an entry. Without it the Issue tab draws old links until reselect or restart.
- **Tag shape is stated twice and tested twice.** Rust `issue_tags`/`parse_identifier` decide what gets *linked*; [issue.ts](apps/desktop/src/lib/issue.ts)'s `parseIdentifier`/`highlightSegments` decide what gets *painted*, and neither can call the other. Rule: team key plus number, `#` must open a word, bracketing punctuation counts as opening it. `#fff` and markdown headings stay prose, both directions pinned.
- **A link is a copy, not a pointer.** `IssueRef` holds identifier, title, url and tracker id, so the sidebar and prompt need no network call. It goes stale, which is the right way round; re-tagging **replaces** the entry rather than appending.
- **Link and unlink match on tracker id *or* identifier, within a tracker** — a resolved link carries Linear's UUID, a blind one carries the identifier itself. **Detail is read by UUID first, identifier as fallback**, since identifiers are not stable across a team move; not the other way round, because the identifier is the *only* thing a blind link carries (`is_stable_id`).
- **A fork inherits links; a relayed message carries none.**

**`hz issue link` writes down what it is given and asks the tracker nothing.** A link is a local record, so needing reachable Linear and a stored key meant it could fail for reasons unrelated to what it records — and the caller is an agent that just read the issue through the tracker's MCP, so it already holds the title and url. Hence `IssueInput { identifier, title?, url? }` and `--title`/`--url`. Absent metadata is ordinary. **Several identifiers plus `--title`/`--url` is a refusal**, since one title applied to all is a wrong link that reads exactly like a right one.

**The session id is optional, and `$HZ_SESSION_ID` is why.** Claude Code's Bash guard refuses any command naming an env var inside a worktree-isolated session, **silently** — the agent reads the refusal, carries on, and the issue is never linked. So the CLI resolves the session itself off `parent_session_id()` and the documented call carries no `$` at all. Shape tells a session from an issue (uuid vs letter-leading team key), so positionals are **one `Vec`** split in one function — clap refuses a non-required positional above a required one. The old `<session> <ISSUE>...` form still parses and must, since it shipped.

### Reading Linear

**The panel reads Linear's API with the stored key. MCP is nowhere near it.** Two channels answering two questions: the key fills *this app's* screens, MCP lets the *agent* read the same issue in its own turn. That is why the connect form says MCP out loud, once. A live `claude mcp list` check existed in the panel and was removed — readers open that panel to read the issue, not audit their tooling.

**Caching** ([issue.ts](apps/desktop/src/lib/issue.ts)). Lists are cached module-level on the whole query, capped at 12, 60s freshness; opened issues separately by identifier, capped at 24. A failed read changes nothing. One **generation counter** over every issue cache, bumped whenever the answer to "who are we, what may we read" changes; a read that started under an older generation is refused rather than written, since the damaging half is not a stale row but a **stamp** that suppresses the read which would correct it. `useSyncExternalStore`d, so a hook holding an answer read under an old key re-reads. Refresh **forgets then bumps** — bumping alone must never gate the cache, or every later visit refetches for the rest of the session. Cached answers are picked **during render**, not in an effect, or one frame of the previous issue's description sits under the new issue's title. A cache short-circuit must clear `loading` itself, since a cancelled read never reaches its own `finally`.

**The composer's `#` picker reads that same cache, and the sharing is what makes it quick.** It asks the question the issues page opens with — `assigned`, unsettled — so a second `#` inside the freshness window opens with no round trip at all. Two rules hold it together. **It reads to `ISSUE_LIST_LIMIT`, not to the 25 rows it draws**, since the key is the *query* and carries no depth: a shallower read would file a truncated answer under the key the page paints from, so the cap is applied at the `slice` and nowhere else. And **a keystroke paints before it reads** — `filterIssues` narrows the cached assigned list locally so the menu moves on the frame the character lands in, with the server's answer replacing it when it arrives. That local match is deliberately weaker than Linear's, which reads descriptions too, so it is only ever allowed to under-match: a row it misses appears a moment late rather than going missing.

**A cold `#` draws placeholder rows rather than nothing**, since with no cache and no index there is a round trip between the keypress and the first row — the state the other two pickers never sit in. `PickerMenu` takes `loading` and reads it **only where it holds no rows**: a list already painted from cache is what the reader wants, not placeholders over it. The composer's key block follows the **rows** rather than the menu being drawn — `% rowCount` is a division by zero on an empty list, and Enter would otherwise be swallowed by a pick that can only land on nothing, so Enter sends while placeholders are up. The empty state's "Press ⏎ to send" legend still follows the **menu**, and deliberately: the legend would be true there, but a send hint under an open picker reads as belonging to the list.

### Uploads

Linear puts uploads *in* the description's markdown, pointing at `uploads.linear.app`, so there is no attachment list to build — override `img` and `a` on that one `Markdown` and leave every other link alone. They sit behind the same auth the API does, so the webview cannot fetch them: `<img src>` resolves to 401 and the browser draws its own broken box. `fetch_issue_asset` puts the key on that request and hands back a `data:` URL.

- **Host checked exactly, and scheme with it.** A description is text somebody else wrote and it names the URL this fetch is handed, so without the check an issue could name any host and have the app post the credential to it. Compared on **parsed host**, never a prefix — `uploads.linear.app.evil.test` passes `starts_with`. Wrong scheme is rejected, not upgraded. Stated twice (Rust `is_upload` decides where the key goes, [IssuePanel](apps/desktop/src/components/IssuePanel.tsx) what is drawn as an asset), pinned on the Rust side.
- **Size capped before the body is read, and the body streamed to that cap.** `content_length` is a courtesy — a server may send none or lie — and `.bytes()` drains the whole body first, so the chunk loop is what actually enforces the cap.

### The issues page

**The Linear tab of the inbox, and a main-column view in its own right — not a session.** Opening it **keeps selection** but drops the sidebar *highlight*, since a lit row would name a session nowhere on screen; **the Inbox row stays lit**, which is how the reader knows where they are. The page hides rather than unmounts, so filters and scroll survive the trip. It draws whether or not a tracker is connected: its own empty state is where connecting is offered — and when nothing is connected it is *only* that form, with the tab row above it so the screen has a way off. Disconnect lives in settings, whose row only draws when something is connected. `tabs` is the inbox's row, drawn above whichever of the two bodies is up.

- **The right pane is hidden while the page is up, and the preference kept**: `panelShown = panelOpen && !pageOpen`. Everything that draws or reads reads `panelShown`; `panelOpen` stays the standing preference.
- **`SessionHeader` takes `standIn`** and `App` passes `"Issues"`, or the header sits at "New session" over a list of issues.
- **Clicking a row opens it in the pane beside the list**, off the same key the list was read with, in the same `RightPanel` frame. The picked issue is held as a whole row, not an identifier, so the pane is complete before its own detail read lands. `useSessionIssues` serves both, since a page pick is a one-element link list.
- **Every route to a session goes through `goToSession`**, which closes the page then navigates. Two buttons closed the page and the chords beside them did not, which made ⌘N and ⌘⇧↑/↓ read as inert.
- **⌘E only ever closes there**, and the guard lives on the chord, not only in `handleTogglePanel` — ⌘E binds **raw** `togglePanel`, so a guard in that function alone lets the chord sail past into a pane not on screen. Same for ⌘⌥1/⌘⌥2.
- **Panel tab `issue`, hidden with no link.** Rows are drawn from the session's own `IssueRef`s, so the tab exists the moment something links one. **Linking is the agent's**, through `hz issue link`. The description is drawn here where the PR panel leaves the PR body out, and the difference is who wrote it.
- **No Start button** — it would create a session, so it must name a project, and the page is workspace-wide. Tagging with `#` in the composer already starts work against an issue from a place that knows the project.

**hz writes exactly two fields, and only from the opened issue's header** — status and priority, through `update_issue` over Linear's `issueUpdate`. Nothing else: no comment, no attachment, no assignee, no label. **The `hz` CLI writes nothing at all**, and [SKILL.md](apps/cli/skill/SKILL.md) says so out loud, because an agent assuming otherwise tells the user their issue moved when nothing of the sort happened.

The two menus live on `IssueRow`'s header in [IssuePanel](apps/desktop/src/components/IssuePanel.tsx), so the session's Issue tab and the Issues page get them from one component. **A status menu is drawn from `IssueDetail.states`, the issue's own *team* workflow, which rides the read the panel already makes** — a menu that has to fetch before it can open is a menu that opens empty. Sorted by kind and *then* `position`: Linear only makes position meaningful within one state type, so a single sort on it lists Done above Todo. No states means no menu, just the glyph.

**`None` means leave it and `Some(None)` means clear it**, which is why priority crosses as `Option<IssuePriority>` rather than a number — "no priority" is a level a reader can pick and it goes down the wire as `0`. **`issueUpdate` answers `success: false` at 200 with no `errors`** for a write it understood and refused, so that field is checked; without it the panel re-reads, finds nothing moved, and silently redraws what was already there. The mutation's own `issue` echo is deliberately unread — the panel draws a whole `IssueDetail`, and asking for that field set back would be a fourth copy of it in `linear.rs`.

**A write is the one moment every cached answer about issues stops being true**, so `update` calls `forgetIssues()` and then puts the freshly-read detail back — *after* the generation bump, or the guard that makes the clearing stick refuses it. `useIssueList` subscribes to that generation for the same reason: without it the row beside the panel keeps saying "Backlog" under a heading the issue has just left. Failure reports through the panel's existing banner; nothing is optimistic.

**⌘-click on an issue row opens it in the tracker**, on the panel's rows and the page's list alike — the same modifier the transcript's link dialog uses to mean "out there, not here". A shortcut, not the affordance: the row's own button is that.

## Opening the working directory

**A split button in the right panel's tab row** ([OpenInButton](apps/desktop/src/components/OpenInButton.tsx)) hands the session's `cwd` to an installed app; the left half opens in the app picked last, the chevron changes it. Detection is [apps.rs](apps/desktop/src-tauri/src/apps.rs), macOS only — everything else answers an empty list. It sits in the tab row because the directory belongs to the *session*, not to one tab's answer about it.

- **Detection is `read_dir` over known dirs, matched on bundle file name exactly.** `/Applications`, `/Applications/Utilities`, `/Applications/Setapp`, `/System/Applications`, `/System/Applications/Utilities`, `~/Applications`; first dir wins, so a machine-wide install outranks a user's copy. **Exact, never substring** — `Cloudflare WARP.app` is not `Warp.app`, and a contains-check lists it as a terminal that then ignores the directory handed to it. `resolve` is split from `detect` so order is testable with nothing spawned.
- **The table is the guarantee, not `CFBundleDocumentTypes`.** `open -a` names the app outright rather than asking Launch Services to rank a handler, so it reaches apps declaring nothing — MacVim declares no folder type and opens one fine.
- **Address is the bundle path, never the bundle id.** `open -b` hands the id to Launch Services, which picks whichever copy it indexed. Names are no good either, since two builds of one editor differ by path alone.
- **Finder is the file default, and it *reveals*.** Every failure lands there too, so the worst a click does is what the link did before the setting existed. `pickFileOpener` therefore falls back to Finder, not the first editor — a transcript row has nowhere to put an error sentence, so a failure must be a working link.

### File links

**Three surfaces, one component.** [FileLink](apps/desktop/src/components/chat/FileLink.tsx) draws a tool row's filename, the reader's own `@mention`, and an absolute path an agent wrote into a sentence. The last is drawn the way the mention is — `@name:12` in mention colour, full path on the tooltip (`FilePathSpan` in [Markdown.tsx](apps/desktop/src/components/chat/Markdown.tsx)) — where a link the agent *wrote* as `[label](/path)` keeps its label and Streamdown's anchor look. It is a span with `role="link"`, never a button or anchor, because the tool row's copy sits *inside* the row's expand button — a second interactive element there is invalid markup and a click toggles the row instead. `stopPropagation` on click **and** on key.

**Mentions resolve against the session cwd**, joined in [filePath.ts](apps/desktop/src/lib/filePath.ts) onto [ChatCwdContext](apps/desktop/src/hooks/useChatCwd.ts)'s value — context, not a prop, since the only reader is four components below `Chat`. No cwd means the mention stays inert coloured text; resolving against wherever the app happens to run opens the *wrong* file. **A fork records the parent's cwd on every copied prompt** for the same reason — a fork carries the conversation into a *different* tree. `repoint_events` sets `user_message.cwd` with `get_or_insert`, not a plain set, so a fork of a fork keeps the *first* ancestor to record one.

**Paths in prose are a rehype pass, after sanitize and before harden** (`rehypeFilePaths` in [markdownPlugins.ts](apps/desktop/src/lib/markdownPlugins.ts)). After sanitize or it strips what the pass adds; before harden or the href is already rewritten. **Second plugin list, not a flag** — an issue description or PR comment names paths from somebody else's checkout, so `linkFilePaths` is on `AssistantMessage` alone.

- **Relative paths are marked too, as written, and resolved in `FilePathSpan` against the chat session's cwd** — the pass has no working directory, and resolving against wherever the app runs opens the wrong file. Same `findPromptPaths` the bubble reads, so the two surfaces link the same words; no cwd leaves the run inert mention-coloured text, a mention's own resting state.
- **A markdown link whose href names a file, absolute or relative, is *converted*, not descended into** (`anchorToFile`), keeping the anchor's children, and checked **before** `NOT_PROSE` — a link that is not converted is left whole, so a path inside a real link's label stays plain rather than nesting two links.

**The match rule is written to under-match** ([findFilePaths](apps/desktop/src/lib/filePath.ts)). A path must *open* a word, hold two segments, and carry no `//` — the letter-then-slash rule keeps `https://host/a/b` and `and/or` out, the two-segment rule keeps `/compact` out. `pre` and `a` are skipped in the walk. Nothing asks whether the file exists, so an over-match costs a dead click, not an error.

- **A path holding a space is dropped, not halved** — a half is a *real* path that can exist and open the wrong directory. The read runs forward to **end of line**, not one word.
- **"Whitespace" is the same set on both sides**: the match stops on `\s`, the forward read resumes on `[^\S\r\n]`, so tabs and non-breaking spaces break a path exactly as spaces do (`&nbsp;` in agent HTML is ordinary input).
- **Trailing `:12`, `:12:5`, `:L12`, `#L12` are stripped from the *path* before it is judged, and kept on the *match*.** The app's own harness prompt asks for `file_path:line_number`, so the whole reference is one link — a link stopping at the filename with `:12` dangling beside it in plain text read as half-converted (DRA-180). After punctuation stripping, before `isFilePath`, so `/a:12` is still refused rather than conjured into a path. The line rides `FilePathMatch.line` → `Segment.line` / `data-line` → `FileLink` → `openFile`, where `lineUrl` in [openWith.ts](apps/desktop/src/lib/openWith.ts) asks a known editor through its own URL scheme (`open -a <bundle> -- vscode://file/…:12`, verified against Cursor). An editor with no known scheme opens the file as before; Finder reveals and a line means nothing there.
- **The word straight after a break decides it wherever it can**: one holding a slash means the match was a truncation, one *opening* with a slash is a path of its own. Only past that word does the shape of the match matter — a match whose last segment holds a dot stops reading at one word, one without reads to end of line. The dot is a **guess**, so it only ever stops the read early, never accepts a match outright.

## Transcription

**Dictation is local, and the engine is somebody else's.** [transcribe-cpp](https://crates.io/crates/transcribe-cpp) run the GGUF model, `cpal` capture, `rubato` resample. **The engine is not Handy** and the two must not be credited as one thing: `transcribe-cpp`/`transcribe-cpp-sys` live at `handy-computer/transcribe.cpp` under their own notice (`Copyright (c) 2026 The transcribe.cpp authors`), where the [Handy](https://github.com/cjpais/Handy) app is `cjpais/Handy` under `Copyright (c) 2025 CJ Pais`. Two entries in [THIRD-PARTY-LICENSES.md](THIRD-PARTY-LICENSES.md), and a claim that one notice covers both name the wrong holder. **The only Handy files in this tree are the two dictation sounds.** Nothing tracks Handy releases because nothing is vendored from it; the engine update through Cargo like any dep. Handy's *app* code deliberately not taken: global hotkey, text injection, tray, history — hz own the composer, so the words have nowhere to travel.

**No model ship with the app, and first press download nothing.** Weight is 218MB–886MB; pulling that on a press meant to start talking = not a thing to do to somebody. `start_transcription` answer `false` where no model ready, `stop_transcription` answer `NeedsModel`, and frontend open Settings on the Transcription tab. That the whole first-run flow.

**Backend is a *build-time* choice.** `Cargo.toml` turn `metal` on under `cfg(target_os = "macos")` and off elsewhere, so `Backend::Auto` resolve to GPU on Apple Silicon and CPU everywhere else. Nothing at runtime can change it — why there is no accelerator setting. **cmake is now a build dependency**; `transcribe-cpp` drive it through the `cmake` crate.

**Weights come from HuggingFace, pinned to a revision.** [catalog.rs](apps/desktop/src-tauri/src/transcription/catalog.rs) = the list, compiled in. Not `blob.handy.computer`, which is Handy's own CDN — same files, but their bandwidth is not ours to spend. `resolve/<revision>`, never `resolve/main`, or the bytes move out from under the `sha256` and every download fail verification at once. Catalog change = manual edit; nothing tell us when a better model land.

**Recommendation read the arch, where Handy's is editorial.** Their `recommended_rank` is a static catalog field and nothing there probe hardware. `recommended()` answer Parakeet Unified EN on Apple Silicon and Canary 180M elsewhere. Suggestion only — every model stay selectable.

- **Installed = present at the catalog's exact size.** Hash is checked once, before a fresh download is renamed into place, never on the settings read — hashing 700MB every open is felt. A truncated GGUF **load far enough to produce garbage** rather than erroring, which is the failure the size check exist for.
- **Download land via `.part` + rename**, so the real path only ever hold a file that already passed verification. A killed process leave a `.part` and nothing [`is_installed`] would believe.
- **Progress is an event, not a return value** — a download outlive the dialog that started it, so closing settings must not cancel it and reopening must find it running. Emitted every ~4MB; one event per chunk = thousands of round trips for a bar that redraw at screen resolution.
- **The loaded `Session` is cached across dictations** and dropped on model switch or delete. Loading is seconds; a session dropped per recording put that on every press. `Session` is owned and `Send` (hold `Arc<ModelInner>`), so it cache directly with no self-referential struct.
- **The load start on the press and the model leave after ten idle minutes.** `warm_selected` run from `start_transcription` alone — the reader talk for the whole load, so it usually land before they press stop. It used to run at launch and on every model change too, which kept 731MB of Parakeet resident for a reader who never dictated (measured: the main process sat at 819MB). `Engine::touch` on every warm and transcribe bump a use counter and spawn a sleeper for `IDLE_UNLOAD`; a sleeper waking to a moved counter exit, one waking to its own empty the slot. **Check and clear under the `loaded` lock, and no `generation` bump**: split, a press slip between the two; bumped, a transcribe that took its token a moment earlier refuse to load and bail with "model changed", where an empty slot under a live token just reload. So the first dictation after a quiet spell may wait on a load, and every one inside the window is instant. **A warm load run with the lock released and install under a generation token, taken by `warm_selected` before it spawn**, and **one loader mutex both warm and transcribe queue on**, or a press and its stop a second later pull the same several hundred megabytes twice. `unload` take neither, so switch and delete stay instant while a load run. — held across the load it would stall the `unload` a switch or delete is waiting on, and installed blind it would put a deleted model back after that unload cleared it.
- **Device is stored by *name*, never cpal's enumeration index.** Handy store the index; it shift on USB replug and silently start naming a different device. An unplugged stored device fall back to the system default rather than refusing to record.
- **Audio must be 16kHz mono `f32`.** No device offer that. Convert once at the end, never per callback — the audio callback is a realtime thread where allocating risk a dropout, and a dropout is a word the reader has to notice is missing. Stereo **average** both sides rather than taking channel 0, since a mic wired to one side alone record silence otherwise.
- **A denied microphone is *silence*, not an error, and that cost a whole round.** macOS open the stream, fire every callback and fill each one with zeros. First build transcribed those zeros to `""` and did nothing — reading exactly like a broken model, with no log line anywhere. Two things fix it and **both** are needed: `tauri-plugin-macos-permissions` raise the real prompt on `start_transcription`, and `Recording::finish` answer `None` where every sample is under `SILENCE_PEAK`. Verified by probe: 192000 samples, peak `0.000000`.
- **Every way dictation can fail is a *message*.** `TranscribeOutcome` carry `NoAudio`, `Empty` and `Failed` beside `Text`/`NeedsModel` precisely so none of them can collapse back into "nothing happened". A silent failure here is indistinguishable from the feature not existing. `Failed` was an `Err(String)` and is the one that escaped the rule; its message is `{:#}`, since `to_string` on an `anyhow` chain print the outermost context alone and every model failure read as the bare words "transcription failed".
- **The audio outlive the run, and that is what make a failure survivable.** Samples used to go into the engine **by value**, so a failed run drop them and the only cure was saying the whole thing again — ten minutes of speech gone to a model that could not load. Every stop now park a 16-bit WAV in `~/.hz/recordings/` ([recordings.rs](apps/desktop/src-tauri/src/transcription/recordings.rs)) *before* the model is even resolved, at any length, and the file is deleted the moment the model answer. `Failed` and `NeedsModel` carry the path, `retry_transcription` read it back through the **same** `transcribe_audio` a stop use, and `DictateControl` draw Retry and Show beside the mic while one is held.
  - **Deletion is on the model answering, not on words arriving.** `Empty` is a verdict — the model read the audio and found nothing in it — so it clear the file like `Text` do. Only a run that could not answer keeps one.
  - **Saving is best effort and the path is `Option`.** A full disk must not take down a dictation that would otherwise work, so a failed write log and carry on; `audio_path: None` is the one failure with nothing to retry, and the message say so.
  - **`recordings::read` refuse any path outside the directory.** The path arrive from the frontend and this command open a file and feed it to a model, so the directory is the only thing saying which files it may.
  - **16-bit PCM, not the captured `f32`.** Half the size of something reaching hundreds of megabytes, playable by anything the reader open it with, and the quantization sit ~96dB below what an ASR model read. Chunks are walked rather than a 44-byte header assumed: a header read at the wrong offset yield audio that transcribe to *nonsense* instead of failing.
  - Unclaimed recordings are pruned after 7 days, on write — the one moment something is definitely being added. Nothing else sweep them.
- **Struct-variant fields need `rename_all` on the *variant*.** The container's rename name variants; a struct variant's own fields stay snake case without it and cross the bridge as `audio_path`, which read as `undefined` and fail nothing.
- **Two files gate the mic, and each fail differently.** `NSMicrophoneUsageDescription` in [Info.plist](apps/desktop/src-tauri/Info.plist): macOS **kill** a process reaching for the mic without one rather than refusing it, so its absence present as the app vanishing on first press. `com.apple.security.device.audio-input` in [Entitlements.plist](apps/desktop/src-tauri/Entitlements.plist): Tauri's bundler sign **every** build with the hardened runtime, ad-hoc `-` included, and under it TCC refuse before the prompt stage — no dialog, no row in Privacy & Security, `check_microphone_permission` just answer false. The plist key being present prove nothing about this one; `codesign -d --entitlements - hz.app` is what to read. `tauri-build` embed that file into the dev binary's `__TEXT,__info_plist` section too, so the string *is* there under `tauri dev` — read it with `otool -X -s __TEXT __info_plist`, remembering the words come out little-endian.
- **Dictation cannot raise its permission prompt under `pnpm tauri dev`, and the reason is not the plist.** The dev binary is a bare Mach-O, not a bundle, so TCC attribute its request to the nearest **responsible ancestor** — walk `ppid` and it land on whichever GUI app started the chain. Running Claude Code inside hz, that is `/Applications/hz.app`, whose *shipped* plist carry no microphone key, so the request is refused **silently, no prompt**. Two ways it break: a detached launch (`nohup`, `&`) reparent to `launchd` and leave **no** responsible app at all; an attached one inherit an app that may not declare the key. **Test dictation from a bundle** — `pnpm tauri build --debug --bundles app` — which is its own responsible process and prompt properly. Same shape as the notification banner's `is_dev()` guard, different mechanism.
- **Engine is fine; suspect capture first.** Parakeet transcribed a `say`-generated WAV word-perfect on the first try. When dictation "doesn't work", probe the microphone before the model — a standalone `cargo run` reading `/tmp/tts.wav` settle it in a minute.
- **The mic hear the speakers, so recording mute them.** One toggle, `muteWhileRecording`, on by default. Moved through `osascript`'s `set volume output muted`, since that is the documented way at the *system* output where CoreAudio want a device lookup plus a property write per channel. Four thing it rest on: the prior mute state live in a **module static**, not on the `Recording`, since a recording dropped rather than stopped must still put the sound back; a second mute **keep the first reading**, or the machine get restored to our own `true` and stay silent for good; restore put back **what it found**, never a flat unmute, since a reader already muted before they spoke stay that way; and restore **clear the record only once the machine is actually back**, since taking it first mean one failed `osascript` drop the only thing that know what to restore and every later stop find nothing to do. Quit is the other end of that record's life, so `RunEvent::Exit` in [lib.rs](apps/desktop/src-tauri/src/lib.rs) restore synchronously — quitting mid-recording is otherwise the one ordinary way to leave a machine silent. Best effort throughout — no output device answer `missing value`, which fail the parse and leave the machine alone. Mute land **after** `Recording::start`, so a refusal never touch it, and restore land the moment the mic close, not once the model finish. **The start tone is swallowed while muted and that is deliberate** — a reader asking for silence while they talk get it, and the visualizer appearing is what say the mic is live. **Lower-the-volume was built and cut**: a three-way picker where the honest answer is one switch.
- **The composer take focus when the words land** ([composerFocus.ts](apps/desktop/src/lib/composerFocus.ts)). One module-level element registered by `ChatInput`'s own `ref`, same gap `useDraft` name and same fix: the recorder live in `App` and the mic button live in `ComposerToolbar`, so neither can reach the textarea through props. Only where the reader is still on the session they spoke into — a dictation outlive the screen it began on, and focusing a composer holding somebody else's draft is worse than not focusing. The caret is **left where it was**, since a draft grow at the end.
- **Transcript append to the draft, so `useDraft` is now a `useSyncExternalStore`.** The controls reach `ChatInput` as an opaque `ReactNode` — same gap `useAttachments` name, same fix. `appendToDraft` join with a space unless the draft already end in whitespace, so dictating after typing continue the sentence and never eat it.
- **The destination session is pinned when recording *starts*, never read at the end.** The recorder is app-wide and a recording outlives the screen it began on, so handing `onText` the live `selectedSessionId` filed the words under whichever session happened to be selected when the model finished — dictate in A, switch to B, the sentence lands in B's draft, silently. `useRecorder` take a `target` and copy it on `start`. Switching away therefore **does not** cancel: the recording run on and the text is waiting in the draft it was spoken into.
- **One recorder, process-wide.** `TranscriptionState.recording` is a single `Mutex<Option<Recording>>` and `start_transcription` replace whatever is there, so two live streams cannot exist — both would fill buffers and only one could be read. The frontend state is global too, so a second session show the *same* recording rather than offering a new one.
- **Transcribing redraw the stop button, spinner in place of the tick.** Same filled circle, same place — the state after a press should say the app is working on what was asked, not that the control went away. A `span` carrying `buttonVariants`, not a disabled `Button`, since `disabled` dim the fill to half for a state lasting under a second.
- **Dictation is two sounds: Handy's own marimba pair**, copied under its MIT licence to `src/assets/dictate-{start,stop}.wav` and played frontend-side ([sound.ts](apps/desktop/src/lib/sound.ts), one `play(url)` shared with the notification and celebration clips) — no `rodio`, no Tauri resource, since the recorder's state already live there. `start` play **after** the refusals, or the tone announce a microphone that was never opened. `stop` play when the **words land**, not when the microphone close: the wait between the two is what the reader is listening for the end of. Only on `Text` — the other outcomes say their own piece, and the tone would be claiming something arrived. **Cancel is silent**, matching Handy, which ship no third sound. The elements are kept and rewound rather than rebuilt, since a fresh `Audio` decode on first play and put the tone behind the press.
- **Stop and cancel are two controls, never one.** They mean opposite things about the words just spoken. Handy get away with one key because it type into whatever window has focus; here the transcript land in a draft the reader can see, so throwing it away has to be deliberate. Escape also cancel, **ahead of every other Escape** in `ChatInput`, since recording is the only state holding a device open.
- **Send moved out of the textarea row onto the control row.** It spanned the whole card height beside the text before, which left nowhere for dictation. Now: text take the card's full width, and one row under it carry the toolbar left, dictate and send right.
- **The level is polled, not pushed** — `transcription_level` answer the loudest sample since it was last asked, ~20fps. A level is only interesting *now*, so a missed reading should be a dropped frame rather than a queued event arriving late. Written from the audio thread as an `AtomicU32` holding `f32` bits, never a lock the realtime callback could block on.
- **The visualizer is an envelope, not a spectrum.** One float cross the bridge and a fixed centre-weighted shape spread it across nine bars. Handy draw a real FFT, which want the whole buffer frontend-side; this tell the reader the one thing they need, which is that the mic is hearing them. **No `Loader2` anywhere here.** Its glyph is not centred in its own box, so rotating it trace a small orbit and read as a wobble at 14px. [Spinner](apps/desktop/src/components/ui/spinner.tsx) is ours: one circle concentric with the viewBox, `pathLength`-normalized so the gap is a share of the ring rather than `2πr` recomputed per size, and `animate-spin` on the **`svg`** — an SVG child's `transform-origin` resolve against the viewport, so a spin on the `circle` swing it around the top-left corner. Downloading draw its percentage over the bar it already has.
- **⌘D alone dictate**, through `useHotkey`'s `platformOnly`. `meta` normally accept either accelerator, which cost nothing for a chord no platform assign — but ⌃D is delete-forward in every macOS text field, including the composer this shortcut is for.
- **A finished download select itself where nothing is selected**, never replacing a working choice — a reader adding a second model to compare has not asked to switch to it. **A *cancelled* one select nothing at all**, and that need saying because a cancel answer `Ok` like a success: `download` return `Downloaded::{Installed,Cancelled}` so the caller can tell them apart. Without it a cancel pointed the setting at a file never written — the tab drew a tick beside a model the composer kept refusing to dictate with.
- **Deleting a model is confirmed in the row, not in a dialog** — a modal take the whole window over a file Download get back. **The actions sit on the bars' row, not the title's, and that is what make the confirmation cheap.** Beside the title they shared a line with prose that had to give up width for them, so anything wider than an icon re-wrapped the description and moved every row below — which forced an absolutely-drawn question over an `invisible` bin, and before that a reserved slot spending the widest state's width in all four. The bars are fixed-width and give up nothing, so the buttons grow into the gap and the whole problem go away. One `confirming` id in the parent, never a flag per row, or two rows ask at once where one press was made; picking any row clear it.
- **Dictation cannot be looked at under `tauri dev` at all**, so a composer demo page carried the controls for a while and was deleted once it had answered — see _Demo pages_ for the shape to rebuild it in. Testing the real thing want a bundle: `pnpm tauri build --debug --bundles app`.
- **The model list is a `radiogroup` and the whole row is the control.** A "Use" button beside a row that already look selectable was two ways to do one thing. Only an *installed, unselected* row is clickable — a row that look clickable and answer nothing is worse than a plain one, and a several-hundred-megabyte download is too big to trigger by clicking a row, so Download keep its own button. Buttons inside the row `stopPropagation`, or deleting a model select it on the way down.
- **`languages` is a phrase, not a count.** "4 languages" tell a French speaker nothing about whether the model is for them, so few languages get **named** (Canary's four) and twenty-eight or a hundred stay a number. Compiled into the catalog, since that is where the judgement belong. **A counted phrase link to the model's Hugging Face page; a named one link nowhere** — which-28 is a question only a count leave open, and "English, German, Spanish, French" have nowhere to send anybody. The row tell the two apart with `/^\d+ languages$/` rather than a second catalog field free to disagree with the first. Expanding the list in the row was the rejected alternative: long, and stale the moment the model gain a language.
- **`speed` and `accuracy` are Handy's catalog scores, copied not measured**, 1–100 and relative to each other — no benchmark was run here, and numbers that look measured would be worse than none. Drawn as bars for that reason: a figure invite a precision that is not there. (Handy's own UI draw neither today; the fields are in its `catalog.json`.)
- **Dropping a catalog entry orphan its file.** `installed_ids` only answer for ids the catalog still name, so a downloaded model whose entry is removed become several hundred megabytes with no row to delete it from. Nothing sweep the models directory.
- **Download cancel is cooperative, checked between chunks.** Aborting the task would drop a half-written file and a live hasher mid-flight; between chunks is the one place it can delete its own `.part` on the way out. The cancelled id live in a module `HashSet` and is **removed** rather than set false, so "cancelled" and "running" are one question. A cancel emit a closing progress event with **no** error, since it is what the reader asked for.

## Automations

**Prompts that run themselves, on a clock — and there is no daemon.** [automations.rs](apps/desktop/src-tauri/src/automations.rs) keeps `~/.hz/automations.json` of `{name, prompt, projectPath, model, everyMinutes, nextRunAt}` and a 30s poll started from `setup` beside the socket. An automation runs while hz is open and not otherwise. The alternative is a launch agent: a second thing installed on the reader's machine, a second thing to keep in step with the bundle, and a prompt that would run with every surface that could show the result closed — which is how a reader finds out about work by reading a diff they did not expect.

- **Missed runs are skipped, not caught up.** `after_a_run` measures the next time from **now** in whole intervals, never `old + interval`. A week closed is one run, not a hundred and sixty-eight: catching up would be a queue of prompts about a repository that has moved on, each one spawning a session.
- **The claim is the exactly-once.** Read, decide and advance happen under one hold of the store's lock, so two polls a second apart cannot both find the same automation due. **The spawn comes after the claim and never before** — a run that fails to start has still had its run taken, where spawning first would re-run every failing automation on every poll for as long as the failure lasted.
- **One number, not a cron string.** Nothing in this app can edit an expression, and every schedule anybody actually wants is "every N". The floor is 15 minutes, because every run is a session and a worktree.
- **A stamp this build cannot read counts as due**, which is the safe direction: the alternative is an automation that silently never runs again.
- **An unattended run takes the default stance**, and that is a decision rather than an oversight. This is the one session in the app that starts with nobody in the room, so a stance letting it write unsupervised would be an escalation the reader never agreed to at the moment they were not looking. Cost, stated: a run that writes stops at its first write and waits behind the sidebar's yellow mark — a run that happened, not one that quietly did something else.
- **The row reaches the sidebar by event.** Nothing the reader did asked for the session, so `run` emits `session_created` itself.

## Handing work back

**The composer hides a row of canned prompts behind itself.** [HandoffRow](apps/desktop/src/components/composer/HandoffRow.tsx) sits above the composer card, clipped to a sliver, open on hover: Commit, Create PR.

**Every button sends a prompt** through `handleSendMsg`, so there is no confirm dialog and no error surface — whatever goes wrong reports in the transcript like any other tool failure. The agent is not deterministic, so every button is a **suggestion, not a command**.

**Prompts are a few words** — `"commit your changes"`, `"create a PR"`. A longer prompt is a spec competing with the repo's own instructions. Pinned by test (≤5 words).

**Hidden, not contextually visible, and that is the whole shape.** A turn touching files is most turns, so a row drawn on "there are changes" is a row drawn always. A settled checkout draws nothing at all, and that is the ordinary answer.

**Which buttons exist is [handoff.ts](apps/desktop/src/lib/handoff.ts), pure and tested.** Dirty tree → Commit. Create PR is hidden on the default branch, where no remote resolves one, where the branch already has a PR (from `usePrMarks.prFor`, not a fourth git call), and where it holds nothing new. That last check reads `ahead_of_base`, **not** `ahead`: `ahead` counts against *upstream*, so a fully pushed branch reads zero — the exact state a branch is in when its PR gets opened. `ahead_of_base` counts `origin/<default>..HEAD`, since a local `main` can be stale or absent in a worktree. `None` means "couldn't tell" and counts as something, since over-offering costs one click where under-offering removes the action.

**One backend command, not three stitched.** `work_status` = `dirty`, `branch`, `upstream`, `ahead`, `default_branch`, `ahead_of_base`, so the row can't draw one button from one snapshot beside another from a different one. `default_branch` arrives **stripped of remote**. Infallible: a non-repo answers defaults. **Read on the falling edge of a turn and on arriving at a session, nothing else** — polling for an editor in another window is several `git` spawns a second to catch something rare.

## Deleting a worktree

**Nobody else cleans these up.** Sweep never removes worktrees created with `--worktree`, and `-p` runs have no exit prompt — and `-p` is exactly how hz spawns.

**Unlocking is a required step, not a defensive one.** A `-p` run leaves its creation lock in place (v2.1.239: the tree still carries `locked claude session <name> (pid N start <date>)` and `git worktree remove --force` refuses it, exit 128). [remove_worktree](apps/desktop/src-tauri/src/git.rs) unlocks first, and that string is what the pid check parses. Reading the reason rather than unlocking blind is the point: a **live pid** means another session is working in that directory now, and it is the only thing that refuses this. `kill(pid, 0)` answers it, `EPERM` counting as alive. **Canonicalize both sides of the lock lookup** — git prints real paths, so `/var/…` comes back `/private/var/…` and a plain `==` finds no record, which reads as "not locked".

Order is load-bearing at both ends: unlock before remove because the lock refuses it, `branch -D` after remove because git refuses a branch some worktree has checked out. The path guard sits ahead of all of it and keys on **shape, not index** — a direct child of `<project>/.claude/worktrees/` or nothing, so an empty worktree name resolving to the project root can never reach a delete.

**Sessions survive.** Removal rewrites the index entry — `cwd` and `project_path` both to the project root, `worktree_name` cleared — and `cwd` is the load-bearing half, since `send_msg` reads it off the index. **The project root, not `project_path` as recorded**: an older `hz new` filed sessions under the *caller's* own worktree, so a flat `cwd = project_path` landed the session in a checkout another live session was working in — and the startup backfill could never heal that, since the result exists. `project_root_of` is the one statement of that rule and both paths take it. The CLI meets us there: it resumes in the directory Claude was launched from, and `--resume <id>` falls back to scanning `~/.claude/projects` for `<id>.jsonl`.

**`branch` stays and `worktree_removed` goes on, and that is what keeps the PR tab alive.** The field holds `worktree-<name>`, the branch the work landed on. Clearing it took the tab off every worktree session the moment the reader settled it; keeping it and nothing else still lost the tab, since `sessionBranch` prefers observed HEAD. So the flag decides which wins. `#[serde(default)]`, so an entry predating it reads as tree-still-there. Trees settled before the flag existed need `backfill_removed_worktrees`, one startup pass recognising relocation by its shape — **and the same pass repairs a `cwd` that is simply gone**, which the shape rule cannot see: a tree removed by anything but hz's own delete leaves the entry pointing inside it, and every `git` and `gh` spawned there fails with ENOENT before the binary is reached. That is why the PR panel said "could not run gh" on a session whose sidebar mark, read in the project root, was fine. `surviving_root` moves both `cwd` and `project_path` to the first root on disk, and **a managed worktree is never that root even where it is the recorded project and still there** — `hz new` used to file a session under the *caller's* own worktree, and that caller is usually a live session, so believing `project_path` would put two sessions in one checkout. So the `/.claude/worktrees/` prefix of `project_path` is tried first, the recorded project only where it names no worktree, then the prefix of `cwd`. **`<name>` has to be a *direct* child there**, the same reading `is_managed_worktree` takes before deleting one — without it an ordinary repo sitting anywhere below such a segment reads as a worktree and its sessions get moved to an ancestor that is not their repo. **No surviving root means no rewrite**, since a project on an unmounted drive reads exactly like a deleted one. The backfill runs at launch, so `gh()` refuses a missing `cwd` in its own words before the spawn — a tree removed while the app is up has no pass coming until the next one.

**"Unpushed" means no other ref holds it, not "no remote holds it"** — `rev-list HEAD --not --remotes` reports a whole history at risk in a repo with no remote. Now `--not --exclude=<branch> --branches --remotes --tags`. Two spelling traps, both failing silently to zero: `--exclude` applies to the **next** ref-enumerating option only, and its glob is relative to `refs/heads`. A squash-merged PR still counts. Over-warning is the safe direction.

**Already-gone trees ask nothing** — disposition is read *before* deciding whether to ask. **Delete takes the tree with it, no second question**, folded into `SessionManager::delete` best-effort; a failed removal there orphans the tree, and `git worktree remove` by hand is the recovery.

## Orchestration

**One agent can fan work out into several sessions**, each with its own worktree and sidebar row. Three commands: create, list, send.

**And so can the reader, without an agent in the loop.** Shift-click in the model picker adds a model to a fan-out set instead of picking one, and a send with two or more creates one session and one worktree per model while the reader stays in the composer — `fanOutPlan` fixes that list, [useModelFanOut](apps/desktop/src/hooks/useModelFanOut.ts) holds the set keyed by composer like the draft and the attachments, and the send runs the ordinary `is_new_session` path once per model. Every session takes a worktree and the composer's toggle is not consulted: these run at the same time, and several agents writing into one checkout overwrite each other — the same reason `hz new` always takes one. Sequential rather than `Promise.all`, because each child is ~400MB resident and the rows landing one at a time is the honest progress bar for a spawn that takes seconds. Nothing is selected afterwards, for the reason `session_created` selects nothing. **Shift has to be caught on the item's own pointer handlers**: Radix fires a bare `CustomEvent` for a menu-item select with no `detail` and no `originalEvent`, so the modifier is gone by the time `onSelect` runs — and `preventDefault` on that event is what keeps the menu open while a set is being built.

**This is the first inbound channel into the app.** Every other command travels frontend → Rust; this one travels agent → Rust → frontend, so the frontend learns about a session from an *event* rather than a return value. That inversion is the whole of what [orchestration.rs](apps/desktop/src-tauri/src/orchestration.rs) adds. The work goes through `SessionManager::send_msg`, the same function the composer reaches, so a session created this way is not a second kind of session.

**Three shipped pieces, one line of glue.** The app serves a unix socket; `hz` is a standalone CLI in its own crate; a skill documents it; and the CLI's own `AGENTS.md` (or the project's) names the capability plus install command. **The app installs nothing** — it informs, the agent does.



**The CLI is deliberately not part of the app** — it has to run on Linux later, where no hz app exists. Own crate, own `cli-v*` tag, `curl -fsSL https://www.drayhq.com/install.sh | sh`. It links neither the app nor tokio: one connect, one write, one read, exit. **Wire types live in a third crate**, `crates/hz-proto`, compiled into both sides so request shapes cannot drift — a drifted shape fails with no error and the command simply stops working. No root Cargo workspace, and this adds none: `src-tauri` has its own `.cargo/config.toml` carrying the ts-rs export path, and a workspace moves the target dir out from under it.

### Install and versioning

**`install.sh` resolves the newest `cli-v*` tag itself, and `hz update` re-runs it.** The app cannot push a CLI update — the Tauri updater swaps the `.app` bundle only. `/releases/latest/download/` is unusable because app and CLI publish into the same repo, so that URL belongs to whichever released last. Instead ask the releases API (`?per_page=100`) and take the first `tag_name` starting `cli-v`; the API answers newest-first, and `sort -V` is not portable. `HZ_VERSION` is a literal-tag override. **Failed resolution refuses, never falls back** — a rate-limited API quietly installing something ancient is the exact failure being removed. **`prerelease: false` is hard-coded in [release-cli.yml](.github/workflows/release-cli.yml)**, which is what keeps the resolver honest.

**The protocol version is checked before the request is even looked at**, and the refusal **names which half is behind** — `envelope.v < PROTOCOL_VERSION` means the CLI is behind, say `hz update`; `>` means the app is behind, say update the app. Naming the wrong half is worse than naming neither, since only one cure is runnable from an agent. **The envelope must still parse at a version the app no longer speaks** — the check is a layer *above* parse, or a v1 line answers "could not parse the request" where it should answer "run `hz update`". Both pinned by test.

**Bump rule: bump when the default the old side falls back to is undetectable.** An old app ignoring `model` runs on its own default, which the caller can see and judge; an old app ignoring `from` starts the worktree at `origin/<default>` and answers *identically to success*, so a session spawned to review unpushed work reviews none of it and reports everything fine. Wrong work that looks like right work is what earns a bump. Currently **v7**: v2 = `from`, v3 = `issues` and `LinkIssues`, v4 = `LinkIssues.identifiers` → `issues` (renamed, not extended, so two shapes cannot be confused), v5 = `Browser`, v6 = `fast` — an old app ignores it and runs at ordinary speed, which answers identically to success since nothing in the transcript says which tier served the turn — and v7 = [`Envelope::id`](crates/hz-proto/src/lib.rs).

v7 is the first bump for a field whose **absence** is the hazard rather than a wrong default, and the reasoning is worth keeping because it is the case the rule reads oddly on. An app that ignores `id` runs the request exactly as it does today and answers `ok`, so nothing is newly broken — but the CLI now *tells* a caller to retry with the id it printed, and below v7 that advice is unkeepable: the retry runs a second time and answers `ok` again. The advice is the new thing, so the advice is what the bump protects.

**One id, one answer.** [`answer_once`](apps/desktop/src-tauri/src/orchestration.rs) keys a `OnceCell<Response>` per id, so the first attempt *initialises* it and a retry **waits for that same initialisation** rather than starting its own — a map of finished answers alone would dedup only the retries that arrive after the damage is already done, and a killed CLI is precisely the case where the app is still working. The ledger is bounded (64) and evicts only **finished** cells: dropping a running one would let the next retry start a second copy of a request that is still in flight, which is the whole hazard. A request with no id dispatches exactly as it always did, so the field costs nothing to a caller that has none — and the CLI's own failure text names the id and the exact retry, since an error from after the line went out is not "it didn't happen" but "you don't know".

### The socket

**Unix socket, not an HTTP port.** `~/.hz/hz.sock` — nothing on the network reaches it, no port to collide on. Stale sockets are unlinked at bind. **Dev builds listen on `hz-dev.sock`**, which is what makes unlinking safe: one path for both builds means whichever starts last owns the channel, silently, since neither app reads a socket it no longer owns. **The child gets `HZ_ENDPOINT` injected** rather than left to the CLI's default, or a dev app's agent files its session into the release app's sidebar. That one value is also what lets the app move to a server later — a `.sock` path today, an HTTPS URL and token in a cloud build.

**The boundary is the directory's `0700`, not the socket's `0600`.** `bind` applies the process umask, so a socket lands world-writable under a permissive one and stays that way until a chmod runs a moment later — a window another local account can connect through and reach session creation unauthenticated. A directory cannot have that window, since connecting needs search permission on every dir in the path. `~/.hz` was `0755`, which also made every transcript readable by any local account. **Narrowing is best-effort, so `serve` checks rather than assumes**: a dir still group- or world-reachable → refuse to bind, naming `chmod 700`. Cost a feature, never the app — as does any `serve` error, logged and dropped in `setup()`.

**Connect fails three ways, and only one of them is about the app being up.** `NotFound` and `ConnectionRefused` are the two shapes a closed app leaves and are named outright rather than used as a fallback — a full listen backlog, an interrupted call and a timeout are all this connect failing with the app very much alive. `PermissionDenied` is its own answer and deliberately **not** stated flatly as a sandbox: the kind covers `EACCES` as well as `EPERM`, and `connect(2)` returns it for search permission on a path component too, neither of which escalation fixes. The cure is named in two places — the error and [SKILL.md](apps/cli/skill/SKILL.md) — so reword them together; rewording the error alone leaves the doc answering a sentence nothing emits.



### Sharing `~/.hz` between builds

**An older build doesn't merely lose a write, it downgrades the schema.** The index is rewritten whole, so a build reading it round-trips every entry through *its own* struct and silently drops every field it cannot represent — a released build beside a dev one erased `thread_id` from every session a newer harness wrote, and resume then answered "this session has no Codex thread" for work still perfectly alive. A file lock fixes none of this. `SessionIndexItem.unknown` (`#[serde(flatten)]`) is what fixes it, and it protects only versions carrying it, so it goes in **before** the field it saves, never after.

**An unknown *variant* is a different failure, and flatten covers none of it.** A value serde cannot spell fails the line, and the index parses as one `Vec`, so a failed line is the whole file — a dev build writing `"harness":"pi"` made a released app read 256 real sessions as none. **`Harness` is fixed by carrying the spelling**: `Harness::Other(&'static str)` holds the name verbatim and `wire_name` writes it back unchanged. A placeholder would be **worse than a crash** — it parses fine, then silently rewrites the harness of every session it doesn't recognise. `Harness::ALL` excludes it and `names_a_cli()` answers false. **`ApprovalPolicy` and `SessionStatus` stay unfixed, deliberately**: neither can carry a string, since both must resolve to something real to spawn with, and `ApprovalPolicy` falling back to `Auto` makes a session **freer than the reader asked**. Per-entry tolerance is no good either, since "fail its own entry" can only mean *drop* it, and a dropped entry is a **deleted** one on the next whole-file write.

### Creating sessions

**Spawned sessions always take a worktree, and no flag turns it off** — three issues in one checkout overwrite each other. `--no-worktree` and `--worktree-name` both existed and were removed; the agent has no basis for picking a name and a supplied one is one more thing that collides.

**`--from` moves where the tree starts, not who owns it.** `-w` forks from `origin/<default>` whatever is checked out, so a spawned session could not see the work of the session that spawned it — which put the obvious use, *a second model reviewing what the first just did*, out of reach. `--from <session-id | branch | ref>` still makes a new worktree, based at that point. Sharing a live checkout stays out of scope.

- **Mechanism: hz makes the tree itself.** [create_worktree](apps/desktop/src-tauri/src/git.rs) runs `git worktree add --no-track -B worktree-<name> <path> <base>` and the child spawns **into** that directory with no `-w` at all. So the tree exists before the child does — a real `snapshot_tree` baseline rather than `base_ref_tree`'s approximation — and carries no lock.
- **Session ids resolve through [`session_branch`](apps/desktop/src-tauri/src/store.rs), the same reading `sessionBranch` in [pr.ts](apps/desktop/src/lib/pr.ts) takes.** Two readers, neither can call the other, so the rule is stated and tested twice; what it must not become is two *different* rules. Id is tried before ref, since a v7 uuid is no branch name anybody types.

**A second opinion is the app's own `--from`, and it needs a seed rather than a ref.** The Diff tab's turn offers a review by another model ([SecondOpinionAction](apps/desktop/src/components/changes/SecondOpinionAction.tsx)): a session of its own, in its own worktree, seeded from that turn's closing snapshot. **The seed is a tree, not a ref, and that is the whole of `seed_tree`** — `--from` carries committed work only, so a reviewer opened from a ref would read a tree from *before* the turn, find nothing wrong with it, and say so, which is the "wrong work that looks like right work" this codebase keeps paying for. [`git::commit_tree`](apps/desktop/src-tauri/src/git.rs) pins the snapshot to a commit with **no ref of its own** — the worktree's branch is the only thing pointing at it — so nothing in the reader's history moves and nothing they can see changes. The identity is fixed rather than read from config, since a repo with no `user.email` would otherwise fail the whole spawn. `parent_session_id` rides along so the sidebar nests the row beside the work it is about, and the new session is **deliberately not selected**, the bargain `session_created` makes: the reader is mid-review of a transcript, and being thrown into a session that is still booting is a worse answer than a row appearing. The prompt is [lib/secondOpinion.ts](apps/desktop/src/lib/secondOpinion.ts) — the request, the agent's *own* account of what it did (marked as a claim rather than evidence, since that is the thing worth a second look), and the instruction to check rather than redo. The changed files are deliberately absent: the reviewer has the checkout and can diff for itself, and a list copied out of the other session is the copy that is stale by the time it is read.

**Model, effort, harness and permission mode inherit from the parent**, each overridable by flag. No parent means Rust's own default, since the composer's remembered pick lives in frontend localStorage; `ModelId::default()` cannot serve, being `Unknown`.

- **Model and effort both stop at the harness boundary.** The model half is obvious; the effort half is not — two harnesses' ladders share every name (`low`…`max`) and a CLI accepts whatever is passed, so a parent's `high` used to land silently on a child whose own default was `medium`. With one harness left this is dormant rather than gone: the fields stay on the index and a second harness would bring it back.
- **Whether to inherit at all is the agent's question and lives in [SKILL.md](apps/cli/skill/SKILL.md) alone.** A parent on Fable, or above its harness's own default effort, wants the user's answer before fanning out. Restating it in `system_prompt.md` would be a second copy on the app's release train.

**Depth cap 2, walked not stored.** A spawned session may spawn; its children may not. Walk `parent_session_id` up the index at create time with a cycle guard, rather than storing a `depth` free to disagree with the chain it describes.

**The CLI resolves the project as the main worktree, and `--show-toplevel` cannot do it** — the caller is almost always an agent standing *inside* a linked worktree, where that command answers the tree, not the repo, and the app rightly takes the caller's value over its own guess. The result was sessions whose Changes, commits and PR all read a directory that doesn't exist. The first record of `git worktree list --porcelain` is the main worktree wherever you run it; a bare repo answers `None`. Not `-z`, which wants git 2.36. **Projects are deliberately not attached**, since `add_project` bumps `last_selected` and would let an agent's call quietly reorder the user's project picker.

**`hz` raises no consent card, and that is one flag**: `--allowedTools "Bash(hz:*)"`, additive, with everything else still routed through `can_use_tool`. Verified against v2.1.241, not assumed — a pattern that fails to match fails *silently*, as an unexpected card. **Test with a command that mutates**: a read-only one like `echo` is auto-allowed whatever the rule says, so it reports success for a pattern matching nothing.

**The child gets `PATH` put back.** A bundled `.app` inherits launchd's `PATH`, so `hz` installed to `~/.local/bin` is not there for the agent — the same trap [binpath.rs](apps/desktop/src-tauri/src/binpath.rs) solves for `claude`. Appended, not prepended.

### Skills

**The skill is embedded in the binary and written by `hz skill install`** — downloading it separately is how a skill ends up describing a different version of the CLI than the one installed. Global at `~/.claude/skills/hz/` **and** `~/.codex/skills/hz/`, both written every install, since the CLI cannot know which agent the user runs.

**Freshness rides the CLI, never the app, and the chain closes on its own.** `include_str!` binds the skill to the binary at compile time; `install.sh` runs `hz skill install`; `hz update` re-runs `install.sh`. So every CLI update rewrites the skill and an **app update does nothing to it**, which is the right way round. The skill and `PROTOCOL_VERSION` travel in the *same binary*, so a skill describing the wrong protocol is impossible without the CLI also being wrong. **The skill teaches how to cure a refusal, never which flag needs which version** — enumerating those ages badly and the agent cannot check versions anyway.

**hz appends no rules to a prompt here.** mcode reads the project's own `AGENTS.md` and its own settings, and ACP's `session/new` has no field for a system prompt, so there is nothing for hz to inject — and one less way for the transcript to differ from what the model was told. [title.rs](apps/desktop/src-tauri/src/title.rs)'s `strip_hz_rules` is kept as the seam a harness with a preamble would need.



### Relaying messages

**`hz send` goes both ways, and that is one command not two.** A child reporting up and a parent handing a child context are the same operation. The message arrives as an ordinary prompt and *starts a turn*, so it wakes an idle agent; a target mid-turn queues it. Unrestricted to parent/child pairs on purpose — an id is an address. **Send passes the target's own recorded model/effort/permission back in**, which is what makes it inert: `send_msg` finds no change, so nothing respawns. A message must not reconfigure the session it arrives at.

**A relayed message names its sender twice, and neither copy does the other's job.** `user_message.from` = `MessageSender { session_id, title }`, set only by `send_message` and persisted so attribution survives replay; the prompt text carries `[message from the hz session "title" (id)]` as well. Both are built from one lookup in `attribute`, so the two cannot name different sessions.

**The transcript has no business parsing it back out.** Not for forgery — `from_session_id` comes from `HZ_SESSION_ID` in the child env, so the **field is no more authentic than the prose**. Refused because a parse *fails silently*: a title holding a bracket, a reworded prefix or another harness's shape each break the regex and leave a relayed message drawn as the user's own. The bubble instead **rebuilds** the exact string `attribute` builds ([stripSenderPrefix](apps/desktop/src/lib/relay.ts)) and drops it only on `startsWith`, so drift fails by leaving the line **drawn**, never by eating the sentence after it. The log is untouched.

**A sender can outlive the session it names, so selection rolls back on an empty read.** Leaving a dead id selected looks harmless and isn't: `selectedSession` goes null while `selectedSessionId` still holds it, and `centered`/`isNewTask` both derive from that null — so the reader gets a *new task* composer while `handleSendMsg` still finds the id and resumes a session that is gone. `handleSelectSessionIndexItem` restores the previous pick and says "Session not found", which also covers a stale sidebar row.

**Two refs, answering different questions.** `selectedSessionIdRef` mirrors state, so it is a **render behind** and a read landing in that gap still sees itself as current. `selectionRequestRef` is written at *call* time and claimed at every site selection moves, and the rollback fires only where it still names this read. The rollback target likewise cannot be "whatever is selected", since selection is optimistic until its own read lands — hence `restorable` is the previous pick *only if loaded in `sessions`*, else `null`. Validity is judged **at rollback, not at capture, off `sessionsRef`**, since the closure's `sessions` is the render's copy and the rollback runs after an `await`. General rule: **state read across an await must come from a ref, not a closure.**

### The sidebar

**`session_created` carries an index item, never a `SessionSnapshot`.** The frontend's `agent_event` listener writes into sessions it already holds and *drops* events for ids it doesn't, so a snapshot would start a transcript in memory that later events could miss. An index item leaves the transcript unread until the row is clicked. `session_status` and `session_title` still land, since both write by id into maps the sidebar reads. **The row appears and is deliberately not selected** — the user is mid-conversation in the session that spawned it. The listener sits in a `[]` effect, so it needs `showArchivedRef`.

**Nesting is `sortSessions`** in [Sidebar.tsx](apps/desktop/src/components/Sidebar.tsx), exported and shared with ⌘⇧↑/↓ so the order stepped is the order drawn. **Walk depth-first, not one pass over roots** — the depth cap allows a spawned session to spawn, and a single pass emitted neither the grandchild nor anything below it, so rows vanished. A `seen` set means a cycle costs a strange order rather than a hung sidebar.

**Each project's run splits again by state** — Needs attention, Completed, Idle, in that order. **Mid-turn is not a state of its own**: the row already says so where its timestamp would be, and a run for it moved a row twice for one piece of work, out on send and back on the turn ending. Under the project heading, never over it: "what is happening" is asked of one repo at a time, and a workspace-wide attention run would leave every project heading below it describing only what is left. **A nest takes the strongest state anything in it holds**, so a child blocked on a question carries its parent up rather than the run that says "these want you" missing the only session in it that does. `asking` is read ahead of the backend's status, which still says `in_progress` and is right to. Live status falls back to the item's own field, which is what carries a `completed` across a restart. **The settled list passes no live reading at all** and collapses back to one run per project — it is a history, not a worklist — and **draws no Pinned group either**, since a pin is what the reader keeps in reach while they work and every row over there is done with. **Where both marked runs are a single row they share one break** — a run of one row between two breaks reads as a heading rather than as a row, and the pair says "these want you" either way, with yellow against green telling them apart. **A project under three rows is not split at all** (`STATE_SPLIT_MIN`) — the split earns its break by making a long list quicker to scan, and there is nothing to scan in two rows. Rows, not nests: the count is what the reader sees down the left edge.

**No run names itself.** The state is already on every row in it — the yellow rail mark, the green one, the working indicator — so a heading is a second copy of what the rows say, and three of them turn a list of sessions into a list of headings. Only the project heading is drawn, on the first of its runs; the break between runs is what says one ended, which makes that spacer the whole signal — and **it needs `shrink-0`**, since a bare height in a flex column collapses to nothing once the list overflows, i.e. on exactly the long sidebar it exists for. Every row beside it is held up by its own `min-h`. `sortSessions` takes the same reading as the render, or ⌘⇧↑/↓ steps rows where they used to be.

## The browser

**Chromium embedded through CEF (cef-rs), behind the `cef` cargo feature, macOS only.** [cef.rs](apps/desktop/src-tauri/src/cef/cef.rs) owns the tabs; [automation.rs](apps/desktop/src-tauri/src/cef/automation.rs) is `hz browser`. Design and the rejected routes (screencast, WKWebView) are in DRA-155. Dev: `pnpm tauri dev --features cef` — **the shim does not pass that feature**, so a plain `pnpm app` has none of the browser commands and `invoke` answers "Command browser_open not found". The build wants cmake and **ninja** (the wrapper is configured with the Ninja generator), and the SDK is fetched by `cef-dll-sys`'s own build script: with no `CEF_PATH` it downloads the pinned build into `target/` and prints `Using downloaded CEF path:`. `scripts/cef-dev-bundle.sh` is then pointed at that extracted directory, and lays the helpers and the framework symlink beside the debug binary. **That directory is not the archive's layout**: the tarball keeps the framework under `Release/` — which is the path `chromium.rs` unpacks with `--strip-components=2` — and `cef-dll-sys` flattens it, which is the coincidence that makes the script's `$CEF_PATH/Chromium Embedded Framework.framework` the right guess. Nothing runs it for you, and a cleaned `target/` takes it away. **A dev build's profile root is `~/.hz/browser-dev`**, the same split the socket makes: Chromium holds a singleton lock on the root, so a dev build sharing the release app's failed to initialize and *exited the process* (DRA-172).

**The bundle ships the five helper apps and never the framework.** Chromium is ~330MB unpacked, and in the bundle it would ride every download and every update. [chromium.rs](apps/desktop/src-tauri/src/chromium.rs) fetches it a few seconds after the window first opens — no prompt, no opt-out — from Spotify's CDN (`cef-builds.spotifycdn.com`, the minimal tarball, arch by `consts::ARCH`), pinned to the `cef` crate's CEF version with size and sha256 of each tarball beside it. Same shape as the transcription models: tarball to `.part`, size and hash checked, only `Release/<framework>` unpacked by `/usr/bin/tar` into `<version>.part/`, renamed to `~/.hz/cef/<version>/`, everything else in that directory swept. Progress is a `chromium_status` event every 4MB; the settings row (Integrations) and the Browser tab's empty state draw `describeChromium`'s one sentence. Failure backs off through four retries and Retry wakes the wait rather than starting a second loop.

- **`paths()` finds the helpers in the bundle and the framework wherever it is** — beside them only in the dev layout, else the download. `create_tab` checks `paths()` *before* `ensure_started`, since that one remembers a failure for the life of the process: a tab asked for mid-download must answer "Chromium is still downloading (n%)", not write CEF off. `hz browser` gets the same sentence through `browser_open`.
- **The helper reads `--framework-dir-path` off its own argv.** CEF forwards the browser's `framework_dir_path` to every child under that switch, and the bundle-relative `../../..` the wrapper's loader assumes does not hold once the framework lives in `~/.hz`.
- **Signing is two halves and the bundler does one.** Tauri signs the app with no `--deep` and signs nothing `bundle.macOS.files` copied, and codesign refuses an app whose nested bundles carry no signature — so [cef-helpers.sh](apps/desktop/scripts/cef-helpers.sh) signs the helpers first, with their own [HelperEntitlements.plist](apps/desktop/src-tauri/HelperEntitlements.plist) (library validation off for the ad-hoc-signed framework, JIT for V8), and the app's [Entitlements.plist](apps/desktop/src-tauri/Entitlements.plist) carries library validation off too. [tauri.cef.conf.json](apps/desktop/src-tauri/tauri.cef.conf.json) is the overlay putting them in `Contents/Frameworks` and running that script as `beforeBundleCommand`; release.yml verifies both entitlements and the framework's *absence* after the build. Compiling the bindings needs the CEF SDK in `CEF_PATH` plus cmake and ninja, and nothing copies its framework out.
- **The hook builds nothing, and that is what keeps a release at one compile.** `tauri build --bins` already compiles `hz-helper` per target, with `MACOSX_DEPLOYMENT_TARGET` set from `minimumSystemVersion` and `custom-protocol` on — and every crate `cc` compiles fingerprints that variable, so a cargo build under any other env reruns those build scripts and rebuilds the tree above them, twice over once the CLI's build follows. That was 28 of a 31-minute release, with the cache restored and unusable.
- **To try the download route under dev**, remove the framework symlink `cef-dev-bundle.sh` leaves in `target/debug/cef/hz.app/Contents/Frameworks`; the helpers stay and the app fetches its own. **To try a signed bundle**, `pnpm tauri build --debug --features cef --bundles app --config src-tauri/tauri.cef.conf.json` — ad-hoc, but the hardened runtime and both entitlement files are real. **That bundle is not a dev build to the socket**: `is_dev()` is `tauri dev` alone, so it binds `~/.hz/hz.sock` and takes the channel from the release app until that is relaunched. Quit the release app first, or test through `hz.sock` and relaunch it after.

**Each session has its own tabs and its own profile** — `RequestContext` with `cache_path` a *direct child* of `root_cache_path` (`~/.hz/browser/<session-id>`), or CEF refuses the profile. The native view sits above the webview, so nothing in the DOM can draw over it: modals hide it (a body `pointer-events: none` observer) **only where something open lands on it** (`judgeOcclusion`: popper wrappers and dialog overlays measured against the view's rect, two frames on so the popper is placed) and **behind a JPEG of the page** captured first and drawn in its place (`browser_snapshot`, `useBrowserSnapshot`) — Radix sets that style for every menu too, a bare hide left the pane a hole for as long as any dropdown was open, and the swap to a 1x picture is visible on its own, so a menu opened elsewhere touches nothing; tooltips open `side="top"`, and a "new tab" is *pending* with no browser behind it so the pane can draw an empty state.

- **Chromium's init resets SIGCHLD to `SIG_DFL`, and `execute_process` and `initialize` both run inside `keeping_signal` for it.** That reset wipes the handler tokio reaps children through, so every later `git` spawn waited forever — and `send_msg` awaits one under the sessions lock, which made one tab opened leave every session unsendable and unstoppable until restart (DRA-166). Diagnosed by a `<defunct>` `git` under the app in `ps`; that is the shape to look for if a child wait ever hangs again.
- **Never hold the `TABS` lock across a call into CEF.** `load_url` fires `on_loading_state_change` before it returns, and that handler takes the lock. Clone the `Browser` out (`browser_of`), drop the guard, then call.
- **`do_close` returns 1 and removes the `NSView` itself.** CEF's default sends `performClose:` to the top-level window, which is hz's quit prompt, and returning 1 alone destroys nothing.
- **A hidden `NSView` drops input.** Chromium marks the widget hidden and every mouse and key event dispatched to it goes nowhere, measured with a page listener. `reveal` unhides the view off-screen for an input verb and `apply_layout` puts it back. Screenshots and `eval` work hidden; only input needs this. **The same drop takes the app's own chords when the view is hidden with focus still inside it** — hiding does not resign first responder, so ⌘E closed the panel and nothing reopened it until a click. `apply_layout` hands focus back to the `WKWebView` before hiding a view that holds it.
- `Target.createTarget` over the debug port is refused by CEF, so tabs are created through `browser_host_create_browser` only.
- **A popup is CEF's, not a tab made beside it.** `on_before_popup` rewrites the window info and client to ours and returns 0, so `window.open` answers a real window that OAuth flows post back through; cancelling and opening the URL as a fresh tab returned `null` to the page.
- **CEF can hand over a replacement browser under an id it has not closed yet**, so `on_after_created` replaces a same-id entry and `on_before_close` removes only the instance it holds (`is_same`, called with the lock released).
- **The picker's console channel is gated per tab and typed.** Any page can log the prefix; only a tab whose picker this app started is listened to, once, and only a payload shaped like `PickedElement`. A render-process binding would be the trusted channel.

**`hz browser` is agent-browser's grammar on hz's own tabs — no agent-browser binary, no MCP, no debug port.** Each browser gets a DevTools channel of its own (`send_dev_tools_message` in, a `DevToolsMessageObserver` out), so an action is a few CDP calls on the session's active tab and the session id is the only address: an agent can reach no other session's pages by construction. Pointer and key verbs use `Input.dispatch*`, since that is what a person's click does; locators and reads are one page-side script, `HELPERS_JS`, shared by `snapshot` and `find` so the two name the same element.

- **Protocol v5.** `Request::Browser` fails to parse on an older app, which reads as a broken CLI rather than an app with no browser; the bump makes it "update the hz app". **Do not install a v5 `hz` over `~/.local/bin` while the release app is what reviewers run on** — every `hz send` there is refused. Test through the dev socket: a wrapper setting `HZ_ENDPOINT=~/.hz/hz-dev.sock` in front of `apps/cli/target/debug/hz`.
- **`wait_loaded` watches for loading to *begin* before waiting for it to end.** A click's CDP reply lands before the renderer has left the page, so "not loading" answered at once is the old page, and the next verb reads the old URL. 600ms window, then assume no navigation.
- **`scroll` is `window.scrollBy`, not `mouseWheel`.** The wheel event never answers on a page with nothing to scroll, and hangs the verb for the full timeout.
- **`press Enter` carries `unmodifiedText` beside `text`.** With `text` alone the key types and does not submit a form.
- **A shot hides the view and draws the page's own still in its place, with nothing on top of it** (`browser_shooting` → `shooting` in [browser.ts](apps/desktop/src/lib/browser.ts), `Snapshot` in [BrowserPane](apps/desktop/src/components/browser/BrowserPane.tsx)). The capture lays the page out at the asked-for size and the widget doing that is the one the reader is watching, so a screenshot was a visible reflow and a snap back. It rides the **same hide and the same still** a modal uses, one more reason in `present()` rather than a second path, and only for the session being photographed. **The shutter opens before the override lands**, so what is photographed is the page as the reader last saw it and the swap is invisible. **A scrim and a camera sat on that still for a while and were deleted**: the still is the page pixel for pixel, so the freeze cannot be seen and anything drawn over it is a flash where there was none — which read as the very flicker the cover exists to remove. A screenshot is not an event the reader must be told about; they asked for it. **`SETTLE` is spent at all three edges** — after the hide, after the override goes on, after it comes off — each one a frame where the wrong thing would otherwise be on screen. And **the ack is queued on the main thread**, which is the whole of it being true: `browser_layout` hands `apply_layout` to `run_on_main_thread` and returns at once, so the pane's "the hide landed" was really "the hide was asked for" — it acked, the override went on, and the reader watched the page reflow in a view still on screen. `hiding()` is one predicate because the still, the paint callback and the layout call must agree: asked separately, a shot drew a still nothing would hide behind.
- **`browser_snapshot` is let past `CAPTURING` while the shutter is open, and that exception is what makes the cover the page rather than a blank.** The lock is held for the whole shot, so the cover asked for *inside* one would be refused — and the cover is the thing the shot hides behind. Safe exactly there: `SHUTTER_OPEN` is true only between the shutter opening and the override going on, which is the window where the page still reads the way the reader sees it. Closed before `capture`, never after, or the cover would be a picture of the very reflow being hidden.
- **The shot waits for the pane to say it is covered, and never guesses.** `browser_shutter_ready` → `SHUTTER_READY`. **An ack names the shot it is for, and a bare `Notify` was not enough**: one shot is answered twice where the pane has nothing to cover — once outright, once when the hide it asked for lands — so the spare notification sat as a stored permit and released the *next* shot before its own still was painted, putting the reflow back on screen every other capture (caught in review on #204). `SHUTTER_ACK` carries how far the pane has got and the `Notify` only wakes the waiter to look, so a late ack is a number too small to release anything; the frontend captures the number where the answer is *promised*, not where it arrives. **A pane with nothing of that session on screen answers at once**, or every screenshot taken with the browser tab shut would sit out the whole timeout for a cover it never needed. `SHUTTER` is the cap alone (700ms), and reaching it shoots anyway — which is exactly what the verb did before it covered anything. The shutter closes on the failing path too, beside the metrics override, or a timed-out capture leaves the page frozen for good.
- **`set device` names live in `DEVICES` and in `VIEWPORT_PRESETS` both**; a test holds them together. **The agent's size is capture-only and never reaches the pane** — `Emulation.setDeviceMetricsOverride` lays the page out for the capture alone, and the widget keeps the pane's size. It used to ride a `browser_viewport` event into the pane's own store so the device bar could show what the agent set; that store is what puts the stage into device-preview layout, so one sized screenshot left the reader's page centred and padded inside the pane for the rest of the session, with the bar that explains it closed by default and nothing clearing it (DRA-233). The bar is the reader's alone, and their pick still letterboxes, that being what they asked for.
- `console`/`errors` drain a per-tab buffer fed from `on_console_message`; the picker's own lines are kept out of it.

**A link in the transcript asks first.** Both the assistant's markdown links and a URL in the user's own bubble go through `openLink`, which raises [LinkDialog](apps/desktop/src/components/chat/LinkDialog.tsx): Return opens in hz, a second button opens the system browser, ⌘-click skips the question and leaves the app. One dialog for the whole app, fed by a module store, since the anchors are rendered several components below anything that could hold the state. URLs in user text are a `url` segment from `highlightSegments`, `http(s)://` only, with the sentence's trailing punctuation left outside.

## Forking a session

**A fork is one conversation carried on twice.** A sidebar row's right-click submenu: **Fork in new worktree** and **Fork here**. Both copy the whole conversation — `--fork-session` takes a session and nothing narrower — so the two differ only in *where* the copy runs.

**Fork is lazy, and that is the whole shape.** The app's half (copy the log, write an index entry) is instant; the CLI's half only happens on **spawn**. So `SessionManager::fork` writes the app's half now and leaves `fork_from` on the index entry as an instruction; the **first send** spawns `--resume <parent> --fork-session --session-id <new>` and clears it. The copied log is what the fork replays meanwhile. **`fork_from` is an instruction, not lineage**: cleared **after** spawn, so a child failing to start leaves it standing, and **before** the prompt goes out, since from there the CLI owns the session under this id. `#[serde(default)]`, or every existing session forks on its next send.

**`--fork-session` honours `--session-id`** (v2.1.246), which is what lets the frontend mint a fork's id the way it mints a new session's. Also verified: the CLI writes a fork a **complete standalone transcript** holding the parent's history, and `-w` combines with all three.

**Refused while the parent's *turn* is in flight, and nothing wider.** The CLI forks by *reading* the parent's transcript, which a live child is appending to mid-turn. An outstanding background task is not that case — it appends *after* a turn ended. The backend checks `turn_in_flight()` and the submenu disables on `in_progress`, the **same question** by construction, pinned by test. The guard was `has_outstanding_work()`, the safe-to-replace-the-child question — and since a `local_bash` task never ends, a session running a dev server could not be forked again for the rest of its life while the menu item stayed enabled. **Also refused where the parent has no conversation**, since an index entry is written before spawn.

**Fork in a new worktree is a resume whose tree doesn't exist yet**, so it needs creation's treatment inside `send_msg`: `-w`, the project root as spawn dir, `base_ref_tree` as baseline. The name is resolved against the **project**, not the parent's own. The item names the cost out loud: `claude -w` forks the *tree* from `origin/<default>`, so the copy can carry a whole conversation onto code that doesn't hold the work it was about.

**Names are resolved against the index and every `worktree-*` branch, not disk alone.** A lazy fork's tree doesn't exist until its first send, so its name lives **only in the index** until then — anything else drawing a name takes one a pending fork holds, and that fork's `-w` then fails **permanently**, since the name is on its index entry and every retry redraws it. And a settled session frees its name everywhere but `origin`, where the branch its PR landed from stays — the PR tab and sidebar marks look a session up by that branch, so a redrawn name opened onto somebody else's merged PR. `worktree_branch_names` folds local and remote-tracking branches in with one `for-each-ref`; no fetch, since a push from a linked worktree writes the tracking ref in this same repo. `resolve_unclaimed_worktree_name` reads all three, and **both** call sites use it. The pool is 32³ and every landed PR retires a name for good.

**The copied log is repointed, twice, and both are about outliving the parent.** Every event carries `session_id` and the frontend routes live events by it, so a log left alone claims to be the parent's and then grows new events under its own id. And `ImageRef.path` names a file under `~/.hz/attachments/<session-id>/`, so a verbatim copy draws pictures out of the parent's directory and goes blank the moment the parent is deleted; the attachment directory is copied beside the log and the paths rewritten. Event `id`s are deliberately **not** re-minted. `repoint_events` is split out from the copy so the rule is testable with no `~/.hz` to write into.

**`parent_session_id` inherits, because a fork is a copy and a copy sits where the original sits.** The sidebar draws a fork **beside** its source under the same parent, and the depth cap counts it at the same depth. Resetting to `None` looks tidier and is a hole — a copy surfacing top-level is free to spawn where the session it copied could not. Pinned by test.

**`restoreSessionControls` takes an *item*, not an id.** A fork opens selected, but it can't go through `handleSelectSessionIndexItem`, which reads `sessionIndexItems` and won't hold the new row until the next render — without the split the fork opens under whatever model the composer last left on.

## The agent's providers

**The agent is this repository's build, and that is what makes a patch to it real.** [apps/agent](apps/agent) is the source — MiniMax Code 0.4.12, first-party MIT, taken whole from the public `MiniMax-AI/minimax-code` tree — and [binpath](apps/desktop/src-tauri/src/binpath.rs)'s `shipped_mcode` resolves `apps/agent/bin/hz-agent` **before** anything else. That launcher runs `apps/agent/dist/cli.js` whenever the tree has its dependencies, and falls back to the staged bundle copy when it does not (a clone that only wants the app). [vendor-agent.sh](apps/desktop/scripts/vendor-agent.sh) builds the same tree into `src-tauri/resources/agent/{bin,hz-agent,app}` for a release — it used to run the vendor's own installer, which staged the vendor's code and **silently discarded every change made here**, which is the trap that made a patch under `apps/agent` dead on arrival. What that costs is in the entry below. `apps/agent` carries its own lockfile and is **excluded from the root workspace** (`!apps/agent` in [pnpm-workspace.yaml](pnpm-workspace.yaml)), so `pnpm install` runs there and nowhere else.

**A native module is built for one Node ABI, so the tree remembers which node installed it.** `better-sqlite3` is one: a module built under Node 26 (ABI 147) is refused outright by the Node 24 a launchd `PATH` reaches first — `NODE_MODULE_VERSION 147 … requires 137` — which is a Providers screen that cannot list anything. [pin-node.mjs](apps/agent/scripts/pin-node.mjs) runs as the tree's own `postinstall`, so the node that built the module is the node it writes down, and [bin/hz-agent](apps/agent/bin/hz-agent) runs *that* one rather than resolving one off `PATH`. **A release ships the runtime**: [vendor-agent.sh](apps/desktop/scripts/vendor-agent.sh) copies the pinned node in beside the launcher, so the bundle needs no node installed and no `~/.minimax-code` — it is hz's agent, on hz's data directory (`~/.hz/agent`), and uninstalling the vendor's CLI changes nothing. Cost, stated: the staged tree is ~550MB, ~145MB of which is that runtime.

**And it is renamed, because it is ours.** The workspace scope is `@hz/*`, the product is `Hz Agent`, the process title is `hz-agent`, and the launcher and bundle directory follow (`resources/agent/bin/hz-agent`). The path map is **generated**, not hand-kept — `pnpm gen:tsconfig` derives it from `release/extraction.json` and each package's `exports` — and the lockfile relinks in seconds with no registry traffic, because every one of those entries is a workspace link. **Three names stay deliberately**: `@earendil-works/pi-*` is a third-party package carried under its own notice; the licence files name who owns what, and renaming a copyright holder is not a rename; and `@minimax-ai/code` in the update machinery names the *vendor's npm package*, which is the thing that code exists to inspect. The `minimax-code` markers inside the updater and the `minimax-code/extensions` ACP namespace are left alone for the same reason — the last is a wire contract hz's own `extensions.rs` reads, so it moves only with both sides.

**And `src-tauri/target` is excluded from vitest**, in [vite.config.ts](apps/desktop/vite.config.ts) — a build copies the agent's tree in there, and it is a third-party suite written for its own runner and its own layout, so a run that picks its files up fails on missing siblings rather than on anything in this app.

**Skills arrive as commands, and the client does nothing to expand one.** A Skill reaches the wire now: [skill-commands.ts](apps/agent/packages/tui/src/tui/commands/skill-commands.ts) is the one builder the TUI's composer and the ACP advertisement both read — the advertisement used to spread a static table of ten built-ins, so an ACP client (which draws exactly what the agent publishes) offered no Skills while the terminal offered twenty-seven. **The invocation is the name**: prompting `/code-review` sends that word, the catalog this runtime contributes to the system prompt tells the model which Skill it names, and its `skill` tool loads the SKILL.md. Nothing expands anything client-side, which is why hz needed no change at all — `/skill` filters to them the moment the agent advertises them. **`input.hint` rides along too** (ACP's `UnstructuredCommandInput`), which hz had been dropping since the first capture: `/model [provider/model[#variant]]` and every Skill's `[instructions]` now draw in `SlashCommandMenu`.

**Where models come from, and the one setup step a fresh install has.** The agent ships inside the app, so there is no CLI to install and no terminal to open: [ProviderSettings](apps/desktop/src/components/settings/ProviderSettings.tsx) is the **Providers** section of Settings — named for what the reader comes here to do rather than for the thing it configures, and sitting **after Transcription** in the rail, since connecting a provider is done once and the empty model picker is what sends them there. The picker then fills with whatever those providers answer, because the model list *is* the agent's own reply ([models.rs](apps/desktop/src-tauri/src/harness/mcode/models.rs)).

**A connected card opens onto its models, each with a switch.** [ProviderModels](apps/desktop/src/components/settings/ProviderModels.tsx) — one row per model, the reader's unit rather than the wire's, so a model served in two variants is one switch and both halves move together. This is the only place a model is switched off, and what it decides is whether the composer's picker draws that row at all.

- **The stored half is the hidden one.** `hz.hiddenModels` holds the ids switched **off**, so `null` means everything is on and a model a provider starts serving later arrives **shown**. A list of what is kept would leave every new row off — a model the agent will run and the app refuses to offer. Not carried over from `modelRotation`, which held the kept half: reading that here would invert it.
- **The ids are the wire refs the picker holds** (`m:<provider>:<model>:v:<variant>`), which is why the card takes the composer's own `models` list as a prop instead of reading `provider list`. The CLI's list names a model by its bare id and says nothing about variants, so composing the two would put the two screens on different rows.
- **The row is the switch**, the bargain `WorktreeToggle` makes — a real `Switch` inside would be a button inside a button, and two hit areas where the reader sees one. Rows are not reordered when switched: a row that jumped under the cursor would move the list being read.
- **The dialog is gone.** `ModelLibraryDialog` and the picker's `Star models…` row were the same switches behind a second surface; the picker now carries only a `Refresh models` row, since the list is a read that goes stale one screen away.
- **The picker's provider headings are names, not ids.** The wire says `custom_provider:opencode-go` and nothing anywhere names it, so `lib/providerNames.ts` caches the one reading that pairs the two — `provider list`, which settings already makes — and prettifies the slug as a fallback. It is a cache and not a call of its own: a boot of the agent for a group heading is not a price a heading may carry.

The screen is **one list of gateways**, and a gateway is either connected or offering the one field that changes that. It was two groups of identically-built cards — the reader's working setup above a second group headed *add* — so the thing already done sat between them and the thing not done. Nothing here is added: the same card wears a green *Connected* chip and what it holds, or opens its key field under itself on click. **The form opens in the row, not in a dialog**, because picking a gateway *is* the click that opens it — a modal between the two is a second confirmation for one decision, and it takes the list away at the moment the row under the cursor is the thing being explained. **A preset's order does not move as things connect**: a row that jumped to the top under the reader's cursor would move the form they are typing into. A gateway hz has no preset for is a line of text until it opens, then the same card with the fuller form. The facts are one muted line (`api.commandcode.ai · OpenAI chat completions · 41 models · sk-c****9F2A`) and the state is a chip beside the name, where they were once one `·`-joined string that read a test result as a further inventory field. And **a test shows the gateway's own sentence**: it used to run through the same helper as the mutations, which writes "Saved" when its work lands, so a test reported saving a list nobody had changed and threw away the answer it had just fetched.

**MiniMax's own account is not used, not drawn, and not offered.** The CLI reports two entries for it on every machine, signed in or not — `minimax_oauth` and `minimax_api` — and `list` drops both rather than drawing a row whose only button would open a login this app has no screen for. Its four models are in every session's option list the same way, and `from_configs` drops those too: a row picked from there ends its turn with "Authentication required: Run `mcode login`". This is **not** a forward-compatibility filter — an unknown provider kind is drawn, and only the two names hz knows have no screen behind them are hidden.

**Every write goes through the CLI's `provider` subcommand, with exactly one exception.** That config file is the vendor's own and its shape is not this app's to keep, where a subcommand is a contract the vendor publishes — and it takes every field as a flag, so nothing here needs a TTY. [providers.rs](apps/desktop/src-tauri/src/harness/mcode/providers.rs) is the interface: `list --json`, `add`, `remove` and `test`.

- **The key travels in the environment, never in argv.** `--api-key-env` names a variable and the value is handed to that one child's env, because argv is readable by every process on the machine (`ps`) and an env is not. A saved provider reports whether it *has* a key, plus **the CLI's own redaction** of it (`maskedApiKey`, `sk-c****9F2A`) — four characters, which is what tells the reader whose key is on the card, and is not the secret. The app still never holds one after handing it over: a screen that drew the key would be a screen holding it.
- **Nothing inherits stdin.** Every one of those subcommands can prompt when an argument is missing, and with a null stdin a prompt is an immediate EOF rather than a hang — so a mistake in the flags costs an error instead of a child that never returns.
- **The id is the CLI's.** `provider add` mints `custom_provider:<slug>` from the name, so the call re-lists and hands back what it was actually called, rather than making the app guess a slug rule the vendor owns.
- **An empty model list means "ask the provider", and hz is the side that asks.** `provider add` has no discovery of its own — it refuses a list with no `--model` at all, "At least one --model <id> is required" — so a reader connecting a gateway would otherwise type out a catalog cURLed from the vendor's docs. `discover` reads `/models` off the base URL and the add registers everything it serves; typed ids are the fallback for a provider that publishes no list. A failure that is **not** "no list endpoint here" stops at the first URL, because walking a fallback chain past a 401 reports the last URL tried instead of the reason. The gateway's own quirks are copied, not guessed: `x-opencode-session` and `user-agent: MiniMaxCode` ride any request to `opencode.ai/zen/go`, matched exactly as the vendor's own `withOpenCodeGoHeaders` matches it.
- **A preset is one wire, and Command Code is registered on the OpenAI one — which means its Claude models are not offered.** Its provider API (`https://api.commandcode.ai/provider/v1`) answers `/v1/chat/completions`, `/v1/responses` and `/v1/messages` and **one model list for all three**: each row carries a `supported_endpoints` and Claude is `["/messages"]` alone. `mcode` takes one `--api-format` per provider and has no per-model route, so reaching both wires means two providers — two rows and two key fields for one key — and this build does not. That is a deliberate trade with a cost worth stating: **Claude is unreachable through this screen**, in exchange for a gateway list where a reader pastes one key once. `read_model_ids` is what keeps it honest: the list endpoint answers both wires, so a Claude id registered under `openai-completions` is refused at the end of its first turn rather than at the add. **The field is Command Code's own**, and a list without it keeps every model — absent means "this gateway does not say". `a_two_wire_gateway_keeps_its_claude_models_off_the_openai_wire` pins the narrowing, and `a_command_code_key_lists_its_two_wires_apart` is the ignored test against the live, public endpoint where a vendor change would show up.
- **`provider list` reports each model as an object, not an id** — `{modelId, displayName, selected}`. Read as a bare string it parses to nothing on any provider that has a model, and takes the *whole* list down with it, since the reply is one JSON value and one unreadable row is every row.
- **`provider add --use` is broken, so `defaultModel` is the one thing hz writes itself.** In 0.4.12 that flag refuses every time — "Test the saved provider configuration before activating it" — on the same provider and model `provider test` answers "Provider available" for; the check it dies on is its own, reading `result.success` off a reply that carries `ok`. It cannot simply be skipped either, because a fresh data directory is bootstrapped with `defaultModel: minimax/MiniMax-M3` — an account this app never signs in to — and until a line replaces that, `session/new` refuses outright with "Authentication required". No session, no model list, no first prompt. So `set_default_model` rewrites that one line. Two things make it safe and neither is an accident: **the file is hz's own** (`MINIMAX_DATA_DIR` is pinned to `~/.hz/agent` and nothing else writes there, so the usual two-writers objection does not apply — that is what the private directory bought), and **one line is replaced in place, never round-tripped**, because five hundred lines of the agent's own model metadata would come back reformatted and every field this app has never heard of is one it would drop. Landing is write-temp + `rename`, as the app's own stores do. `connecting_a_provider_opens_a_session` is the ignored test that pins the whole trap: it connects, asserts the line moved, and **opens a session** — the only assertion that catches a connect that looked fine.
- **An empty picker is the one state here with nowhere to go**, so it is the one that draws a way out: the model menu names the missing provider and opens this tab. Every other control has a working default; this is the one the reader has to fill in.

## A missing agent CLI

**Answered before the reader writes a prompt, and refused before a session exists.** `agent_availability` reports whether the agent can run here; the composer reads it on mount and draws the notice, and `send_msg` checks again under `if is_new_session`.

That ordering is the whole feature. The index entry lands **before** spawn on purpose, so a session failing for an unpredicted reason stays visible — but a missing CLI is predictable, and through that path it leaves an empty row pointing at an agent that can never start. Refusing earlier means nothing to delete and no retry choreography: the composer never unmounts, `useDraft` still holds the text, and retry is pressing send again.

**"Is it installed" is read off the cached path, not probed again.** `binpath::agent_available` calls the ordinary resolver and asks `is_absolute()` — a successful resolution is always absolute, and the bare-name fallback is the only relative answer it can give. Free after the first call, which matters because the *failing* call is the expensive one. With a vendored copy in the bundle the answer is always yes, and the resolver never reaches the shell probe.

**hz installs nothing** — it names MiniMax's own installer and links its quick start, off `Harness::{install_command, docs_url}`. Known cost: `binpath`'s cache never invalidates, so a CLI installed while the app runs still reads as missing until restart.

## Demo pages

**Two exist: [demo.html](apps/desktop/demo.html) for the question card and [demo-pr-empty.html](apps/desktop/demo-pr-empty.html) for the PR panel's empty states — which the machine this is developed on cannot show, `gh` being installed on all of them.** The composer demo answered what the dictation controls look like and went, and the fx tool-row demo went with fx: that is the section working rather than failing. **One page per question, never one page collecting them** — a demo is deleted the day its question is answered, and a shared page makes that a merge rather than a deletion.



**A demo is its own page, never a flag on the real one, and gone once its question is answered.** An HTML entry at the package root (`demo.html`) loading its own `main.tsx`. Vite's dev server serves any root HTML, so it is reachable under `pnpm dev`; `vite.config.ts` names no extra `rollupOptions.input`, so `pnpm build` emits `index.html` alone. Gating on a query flag was the rejected alternative: it puts demo-only branches inside production code paths. A demo mounts the **real** components with faked inputs, and any test seam built only for its sake goes with it.

**A component whose import graph reaches `@tauri-apps/api` at load time cannot be mounted in a demo page at all, and it fails as a wholly blank page with nothing in the console.** `Sidebar` is one: importing it in a demo left `#root` empty, every module served at 200, and no error in the page, the Vite output or `pageerror` — the module body simply never ran. `getCurrentWindow()` throwing is the documented half of this and it is *not* the same failure; a demo that needs such a column draws a stand-in and says so.

Two things that fail as a blank page with nothing in the dev server's output: **a demo page has to bring `App`'s own providers with it** (a control with a tooltip throws without `TooltipProvider`), and **a browser is not a webview** — `getCurrentWebview()` and `getCurrentWindow()` **throw** outside Tauri rather than rejecting, so reach for a `try` whenever an effect touches `@tauri-apps/api` synchronously. `invoke` is safe, since it rejects.

## Persistence

Everything lives under `~/.hz/` ([store.rs](apps/desktop/src-tauri/src/store.rs), [projects.rs](apps/desktop/src-tauri/src/projects.rs)).

- **`sessions/<session-id>.jsonl`** — one mapped `AgentEvent` per line, append-only. Single writer per file, so `O_APPEND` alone is enough; no lock. On resume, `next_seq_by_session_id` tail-read the last line to continue the counter. **The append is awaited inline in the read loop, and measured that is fine**: only *retained* events are written (54 of a 262-line turn — `ingest` drops deltas and usage), and one open/write/close cycle costs ~41µs, so a turn spends ~2ms here. A writer task would take that off the drain and buy a worse hazard: a queued write landing after a session is deleted would recreate the log file nothing has a session for.
- **`sessions/index.json`** — one `SessionIndexItem` per session, holding both `cwd` (where the agent runs) and `project_path` (repo root, the grouping key, so worktree sessions still list under their project). Rewritten whole, so it take a process-wide lock and land via write-temp + `rename`.
- **`attachments/<session-id>/`** — a copy of every image sent from that session, deleted with the session. Only images: non-image attachments are referenced by original path and never copied.
- **`settings.json`** — the reader's own picks, as opposed to the window's: composer defaults, the models switched off, shortcut rebindings, the app each button opens, the update channel, the declared spaces and the active one, plus analytics consent and the install id. Written only through `settings::update` — the lock and the atomic rename — and read by the frontend through one `get_preferences`/`set_preferences` pair.
  - **What stays in the webview's localStorage, and why that is not laziness**: the three the pre-paint script in `index.html` reads (`hz.theme`, `hz.mode`, `hz.fontSizes` — an async read would flash the default palette on every launch) and the ones describing *this window* rather than the reader (panel widths, what is folded, diff style, code theme, the last commands). The split, with a reason per key, is in [useLocalStorage.ts](apps/desktop/src/hooks/useLocalStorage.ts); it matters because a dev build and a released one have separate webview storage, so nothing there is shared between them.
- **`projects.json`** — attached projects and which was last selected. Own file, own lock. Paths canonicalized at attach time, or `/x/proj` and `/x/proj/` become two projects and split the sidebar's grouping.

The asymmetry is the point: appending to a private file is atomic, rewriting a shared one is not. **`cwd` on the index is authoritative on resume** — `send_msg` read it rather than trusting the caller's argument, since the project picker make the two able to disagree and resuming in the wrong directory is silent.

## Updates

**Shipping one = `apps/desktop/RELEASING.md` (gitignored, local only)** — follow it rather than reconstructing it from here. It says what to type and, more important, what to *check* after: a green tick proves nothing, since the bundler only warn when notarization fails.

**Two signatures, and conflating them is the first mistake to avoid.** The minisign keypair is the updater's own integrity check — public half in `plugins.updater.pubkey`, private half a build-time env var, and a bundle built without it is refused by every client. Apple's Developer ID signature is a different question: it is what stops macOS blocking the download, and says nothing about whether the payload is one this app published. Both set in [release.yml](.github/workflows/release.yml); only the first is needed for a local build.

**A tag's shape pick the channel**, semver does the rest. `v0.3.0` stable, `v0.3.0-beta.1` beta, and because `0.3.0-beta.1` sort *below* `0.3.0`, beta users are offered a stable release the moment it ships with no logic reproducing that rule. What the release job encode is the other half: a stable release write both manifests, a beta release only `beta.json`, so beta is a superset, not a fork.

**Manifests only ever move forward** (`promote` in [release.yml](.github/workflows/release.yml)). The beta line run *ahead* of stable for its whole life, so an unconditional `cp` let a stable hotfix overwrite `beta.json` with an older version. The guard is the same semver comparison the plugin makes, prerelease rules included, in inline node — **not `sort -V`**, which put `0.9.4-beta.2` *above* `0.9.4`. Equal versions rewrite; a missing manifest is written, never an error; a release moving nothing skip the commit.

**The channel is chosen per check, in Rust** ([updater.rs](apps/desktop/src-tauri/src/updater.rs)), so switching channels need no rebuild. It is owned by [useUpdater](apps/desktop/src/hooks/useUpdater.ts) and handed down as a prop — `useLocalStorage` is per-component, so a second copy in the dialog write a value the hook never sees, and `channel` is what re-arm the checking effect.

**Install is blocked while any session is mid-turn**, and the button waits rather than warning, since swapping the bundle relaunch the app. The check is `statusBySession` and is complete on its own, as no child survive a restart. It lives at the button, not in `install_update`.

**The last step is a launch this app make itself, never `AppHandle::restart`.** `install_update` run off the main thread, where `restart` only ask the event loop to exit and relaunch from inside Tauri's own `RunEvent::Exit` arm — *after* the callback in [lib.rs](apps/desktop/src-tauri/src/lib.rs), which end in `libc::_exit(0)` to dodge ggml-metal's atexit abort. So the relaunch was never reached and Install read as a quit that never come back (DRA-160). Nothing here may call `restart` again while that `_exit` stand.

**Launch first, exit second, and that ordering is the whole of the reporting.** `relaunch` run `open -n <bundle>` — Launch Services, so the new instance is registered, and a refusal come back as a non-zero status carrying a sentence rather than as a process already gone. Only then `app.exit(0)`. A rejected `invoke` is therefore a real answer the UI can draw, where a diverging call left nothing running to say anything at all. `-n` is load-bearing: this app is still up, and without it `open` merely activate it. **Environment survive** — `open(1)` state that an opened app inherit it "just as if you had launched the application directly through its full path" — where `argv` do not, absent `--args`, and nothing here read any. Success only mean Launch Services took the request; an instance that start and then die look identical from here.

**The two failures are tagged, never told apart by their message.** `InstallError` carry `stage`, because the cures are opposite: a swap that did not complete leave nothing to open, so the button beside the sentence is the answer, where a *relaunch* that failed left the new bundle on disk and only opening it finish the job. Telling a reader to quit and reopen for a swap that never landed send them to do nothing. **Not "changed nothing"** — the plugin move the old bundle to a temp backup before unpacking and a final rename that fail return `Err` without putting it back, so the weaker claim is the true one. An unshaped rejection read as `install`, the safe half. The sentence itself is `updateFailure` and both surfaces call it — the sidebar row **and** the Settings row, since Settings cover the sidebar and a reader who pressed the button there would otherwise get no answer at all.

**Except when the user asks.** "Check for Updates…" is a question, so it is answered either way and both answers retire after 4s. The menu item **emit to the frontend** rather than checking in Rust, because the channel lives in frontend local storage; that also mean a manual check reuse the scheduled path and its in-flight guard. The verdict is read off `check_update` resolving with no `update_status` having arrived.

## Settings

**A full-window surface with a rail, not a card** ([SettingsDialog.tsx](apps/desktop/src/components/SettingsDialog.tsx)), gear in the sidebar's titlebar strip, ⌘, from anywhere — a **toggle** now, since the chord that opens this is the one somebody presses to get back. Providers, Appearance, Spaces, Transcription, Integrations, Shortcuts, About; `SETTINGS_TABS` is set *and* order, and `SECTION_ICONS` is one glyph per entry. The group's rows sit in the pane's own capped column (`max-w-2xl`, the transcript's measure) with the section's name at the top of that column, and the pane's scroll box is keyed on the section, or a reader who scrolled Shortcuts lands in About past its heading.

**It arrives on one frame — `animated={false}` on `DialogContent`, and that is a fix rather than taste.** A card can afford to fade, because the reader keeps the app behind it; a surface that replaces the window cannot, because a fade from zero opacity *is* the app showing through it. Measured before the fix: opacity 0.11 → 1.0 over ~100ms, with the window's own header and transcript ghosting under the settings page, and the close fading back the same way. **The prop exists because overriding motion with a later class does not work**: `data-closed:animate-none` beside `data-closed:animate-out` leaves both declarations in the stylesheet and the winner is whichever Tailwind emits last, which is not the same answer for `data-open:` and `data-closed:` (`animate-none` beat `animate-in`; `animate-out` beat `animate-none` — both measured).

It is still a `DialogContent` underneath, with every half of the frame turned off. **That is not laziness — the overlay is load-bearing.** `judgeOcclusion` measures `[data-slot$="-overlay"]` against the browser view's rect to decide whether the native CEF view has to be hidden, so a full-window surface built outside the dialog is one the browser tab draws straight over. The overlay goes **transparent** (`overlayClassName` on the primitive) rather than away: a dim behind a surface that fills the window dims the surface, and the rail is see-through on purpose so the window keeps its glass down one edge. **The surface paints everything it covers, and the first pass did not.** It left the rail and the drag row see-through so the window kept its glass down that edge — right for the app's own sidebar, wrong here, because behind a full-window surface is the app: the session sidebar came up through the rail and the window's own "New session" header came up through the drag row. **Hiding the sidebar only fixed the steady state** — on the frame it opened the reader still caught both lists drawn over each other, since a subtree hidden with `visibility` keeps its boxes and layers and an engine may paint it a frame late, while `display` (which cannot be painted late) costs the column's scroll position on every trip into settings. **An opaque surface has nothing behind it to paint late, in any engine and whatever the commit ordering.** The cost, stated: no glass while settings is up, so the window is one flat page — which is what a settings window is on this platform anyway. The rail is therefore `bg-background` like the pane, and the only thing separating them is the border.

The drag row (`h-(--titlebar-h)`, `data-tauri-drag-region="deep"`) is required for the same kind of reason — this surface covers the app's own strip, and a window with nothing to drag by cannot be moved.

**Font size is three px rows writing the `--fs-*` hooks App.css already exposed** ([fontSize.ts](apps/desktop/src/lib/fontSize.ts), store in [useFontSizes.ts](apps/desktop/src/hooks/useFontSizes.ts)) — chat, code, interface; tool output and the composer are left at their own size on purpose, their hooks unwritten. Stored under `hz.fontSizes` and applied pre-paint by the same `index.html` script the theme uses, so a stored size never flashes the default. Each field keeps a draft while focused and clamps on blur, since a controlled number input clamped on change turns a typed `15` into `105`.

**Every chord has an id, and the id is what `useHotkey` takes** ([shortcuts.ts](apps/desktop/src/lib/shortcuts.ts) is the registry, [useShortcuts.ts](apps/desktop/src/hooks/useShortcuts.ts) the overrides). Keycaps draw through [ShortcutKeys](apps/desktop/src/components/ShortcutKeys.tsx) off the same store, so a tooltip cannot name a chord the key no longer fires. A test refuses two ids sharing a default; one action bound from two components under different `enabled` gates is one id (`subtab.prev`), never two. The Shortcuts tab records the next keystroke on the row, refuses a chord another id holds with that id's name, and stops the event at the button — every `useHotkey` listens on `document`, so without that the chord being recorded would also fire. A bare printable key is refused as a chord, shifted or not. Known ceiling: inside the browser pane CEF forwards a fixed key set (`cef_key` in [cef.rs](apps/desktop/src-tauri/src/cef/cef.rs)), so a chord rebound onto anything outside it works everywhere but there.

**The pane scrolled inside a fixed height while this was a card, and no longer does.** That height was the answer to a dialog that doubled on the way into Transcription and halved on the way out — a card cannot change size under the reader. A window-sized pane has nothing to keep constant, so a group scrolls against the window instead. What survives from that pass is `shrink-0` on the sections: a column flex item shrinks toward its content before the container agrees to scroll, whatever the container's height is.

**Mounted in `App`, not beside the gear that opens it** — the sidebar unmount whole when collapsed, and ⌘, is the one route into settings that survive that. Open state is not persisted and the section pick resets on close — and mounting it in `App` is also what lets a full-window dialog sit over the window's own titlebar row, the sidebar, the right panel and the main column alike. **Bodies are switched, not hidden**, against the right panel's own bargain: there is no scroll position to keep, and mounting all three would run the external-app scan on every open.

**A read a section needs is owned by the dialog, keyed on `open` — never by the section.** A body is built when the reader reaches its tab, so a read living there is a tab that is blank for as long as its children take, every visit, for a reader who opened settings to *look* at it. `useAppSettings`, `useTranscriptionSettings`, [useProviders](apps/desktop/src/hooks/useProviders.ts) and [useSourceControl](apps/desktop/src/hooks/useSourceControl.ts) all take `open` and are called by `SettingsDialog`, which outlives the visit — so the answer is there before the tab is. The sections take what those hooks return as props. **Switching bodies stays**: what it was buying is still true (no scroll position, and Integrations' app scan is not worth running on open), and the read no longer rides on it. Cost, stated: the last visit's list is what a reopen draws until the fresh one lands, which is a stale second rather than a blank one.

**Row shape = `SettingRow`**, label and control on the top line, reason full width beneath. Two rules it encodes: a description is **not optional**, since it is where "why is this off by default" lives; and a setting that cannot apply on this platform is **disabled, not hidden**, since a row that vanishes reads as a setting the app forgot and the sentence under it is the only place the reason can be said.

### Closing with ⌘W

**The macOS Window menu ships no Close Window item, and that absence is the whole feature** ([quit.rs](apps/desktop/src-tauri/src/quit.rs)). The predefined one carries ⌘W built in, and a menu key equivalent is matched before the responder chain — so the key never reached the webview and closed the app's only window instead, which arrives as `CloseRequested` and raises the quit dialog. There is one window and quitting is already confirmed, so the item buys nothing the red traffic light does not; dropping it hands ⌘W to the app. `RESERVED` in [shortcuts.ts](apps/desktop/src/lib/shortcuts.ts) no longer holds it, and a test refuses any default that list would make unrebindable.

**One id, `tab.close`, and one binding in `App`** — never a `useHotkey` per tab strip. The chain is an *ordering*: the Files tab's active file, then the Browser tab's active tab, then a split pane's session. Split across the components that own each strip it would be several ids on one chord, which the registry test refuses, or several bindings of one id firing together — and `enabled` cannot arbitrate the middle arms, where the browser sits beside a chat grid and both could answer. It is bound only where something is actually closable, since `useHotkey` claims every chord it matches. It replaced `pane.close`'s ⌘⌥W outright rather than sitting beside it: two close chords is one more than the reader has to learn.

### Theme

Full rules, rejected alternatives and the swatch/mode UI reasoning are in [DESIGN.md](apps/desktop/DESIGN.md). What must not be broken:

- **Colour is three layers, and which layer a token lives on is the whole filing system.** `:root` hold what neither theme nor mode changes, plus every **alias**; `[data-mode]` hold the ramp; `[data-theme][data-mode]` hold the palette. Aliases keep the third layer honest — `--card`, `--popover` and `--composer` all resolve to `var(--surface-card)`, so a theme cannot set one and forget another.
- **The ramp lives on `[data-mode]`, never `:root`** — the two have the same specificity, so a light document matching both would take any dark token the light block happens to miss.
- **Rules go on `body`, never on `html`.** Palette blocks are `[data-theme][data-mode]`, two attributes, so they out-specify any `html[…]` aimed at the same element and the override lose **silently**. Every new attribute hits this again.
- **An alias resolve where it is declared.** `:root { --backdrop-top: var(--background) }` resolve *at `:root`*, so a **descendant** setting its own `--background` still paint the document's — which is why `.theme-swatch` must re-declare both backdrop stops. A theme setting its own stop still wins, since palette blocks are unlayered.
- **A swatch carry its own mode, not the document's** (`hasLightMode(name) ? resolvedMode : "dark"`), or a dark-only theme in light mode match no palette block and draw something clicking it doesn't give.
- **`useTheme` is a module store, and that is not tidiness.** `useGlass` read the theme, so a per-hook copy meant the dialog set a theme its own copy knew about while the window kept the old one's behaviour, and the stale copy's `watchSystemMode` callback re-applied the old palette on the next OS colour-scheme change. One store, one watcher.
- **Transparency is a token set and vibrancy nests inside it.** Windowed is always on; fullscreen is answered by the **palette**, never the reader, since nothing sits behind a fullscreen window. [useGlass](apps/desktop/src/hooks/useGlass.ts) own both attributes and guarantee vibrancy ⊆ transparency. Neither is persisted.
- **The material blur inherit the appearance it is *given***, so a light palette on a Mac set to Dark composite over dark blur and go grey. `setTheme` fix it, app-wide — traffic lights, menu bar and native dialogs follow hz's mode. Wants `core:window:allow-set-theme` in [capabilities](apps/desktop/src-tauri/capabilities/default.json), with the same silent ACL refusal `set-badge-count` documents. **Passing `resolvedMode` unconditionally break System**, since pinning the appearance also pin what the webview report for `prefers-color-scheme` — the only thing `watchSystemMode` reads.
- **`coerceTheme` reject unknown ids and fall back to `DEFAULT_THEME`**; nothing migrate stored values. Pinned by test, and that test is what should fail if the default ever stops being that palette.

## Analytics

**Five events, hosted PostHog** ([analytics.rs](apps/desktop/src-tauri/src/analytics.rs)): `app_started`, `active_day`, `session_started`, `feature_used` and `error`. Nothing about *what the reader writes* is measured — no prompt, no path, no title. `session_started` carry harness, model, effort, permission mode and whether the session is a worktree or was spawned, read off the index entry rather than `send_msg`'s arguments, and reported **after** the index write, since everything before it can still fail and a session counted before its row exists is a start that never happened.

**`app_started` is the install and version signal, never the activity one.** People leave this app open for days, so launches undercount use badly. What a launch uniquely answer is which build is in the wild.

**`active_day` is the activity one, and nothing else answer it.** PostHog compute actives off *any* event, but the events beside this one only fire where they fire: `app_started` want a launch and `session_started` want a session being **created**, so somebody working all day in one resumed session used to fire nothing at all and the most engaged reader read as churned. Three call sites, each covering a hole the others leave. **Launch**, beside `app_started` in `setup`, is the only one guaranteed to fire — [focus.ts](apps/desktop/src/lib/focus.ts) seed itself from `document.hasFocus()` and report *changes* alone, so a window coming up already frontmost never report gaining focus and somebody who open hz, work and quit without switching app would go uncounted. **Focus gained**, through that same module's subscription and the `track_active_day` command beside `track_feature`, catch coming back to check on a session an agent is running — no prompt, and real use of an app about parallel agents. **The `send_msg` command** cover a reader who leave the app open and frontmost across a date boundary. All three share one key, so whichever get there first claim the day and the other two are no-ops — which is why none of them ask what the others did: "report this only if nothing reported today" is what the claim already is.

**The send site is the Tauri *command*, never `SessionManager::send_msg` one call down**, and that is the whole gate. The orchestration socket reach the manager directly for both of its jobs — relaying a `hz send` and starting a session `hz new` ask for — so an agent finishing at 3am would mark the day active with nobody in the room. A gate on `from.is_none()` catch only the relay half and read as if it caught both. A Tauri command is reachable from the webview alone, so getting there already mean somebody pressed send.

**`track_daily` throttle it, and it is deliberately *not* persisted.** At most one report per local day per key, per process, over a `Mutex<BTreeMap<String, String>>` of key → date. **The day is claimed inside `send`, *after* consent is read** — never at the spawn. Claiming up front look equivalent and is the shape DRA-199 already got caught by: an install launching opted **out** claim the day, send nothing, then silence itself for the rest of that day if the reader turn reporting back on. Process state consent have to remember to clear is a second place for consent to be wrong; claiming after it is asked leave nothing to clear. PostHog count distinct people per day, so one install reporting three times is still one active user — a restart re-reporting cost one event and move no number, where remembering across runs cost a file, a lock and a corruption path on the launch path. `claim_day` is split out so the throttle test need no clock and no request. Known wrinkle nobody is fixing: local date and the PostHog project's timezone disagree at the edges.

**`source` separate the two populations reporting into one project** — `"app"` in `base_properties`, `"site"` registered on the web SDK. The app carry a stable install uuid where the site is cookieless per visit, so an unfiltered "unique users" figure is the sum of two things that mean different things. `$lib` half-separate them already, but a dashboard built on a property's *absence* break the day something else stop setting one. **The one thing here that cannot be backfilled.** The site register it from `init`'s `loaded` callback rather than after `init` return, since the first pageview is captured inside `init` and a super property only ride captures made after it.

**Screen views were cut, not deferred** — which tab is open is not a question being asked, and `$pageview` would be the wrong name for it anyway: that event drive PostHog's Web Analytics product, which is clean and site-only today.

**`feature_used` is one event with the feature as a property, never an event per feature.** PostHog break one insight down by property, where a name each is a chart each to keep in step, and a feature added later then show up in the existing breakdown with no dashboard change. Reported on the feature *working*, not the control being pressed — **with one stated exception, the handoff row**, which report on the press. `handleSendMsg` catch its own failures and resolve either way, so awaiting it report identically on success and failure, and a real fix mean changing that function's contract, which the main composer path share. The question that number answer is whether a row parked behind the composer get *found*, which the press is the signal for; a send failing past there is the agent failing, and the transcript is where that show. Every other one sit at the **chokepoint every route pass through** — `transcribe_audio` rather than the two dictation commands, so a retry that finally produced words count like a stop that did; `connect_linear` after both the key and the account are down, so it report a connection rather than an attempt.

Today: `dictation` — which carry the **model id** beside it, since nothing else say whether `recommended()` is a pick people keep or which catalog entries are worth carrying — plus `fork`, `pr_merged`, `linear_connected`, `space_created`, `worktree_deleted`, `settle` / `unsettle` / `pin` / `unpin`, and `handoff_commit` / `handoff_pr`.

**`error` report *where* it broke, never *what it said*, and that rule is the whole feature.** An error string or a stack frame carry file paths, and a path carry the project, the branch and the client's name — so a property may be a closed tag (a stage, a harness, a `file:line` of our own source) and never a `String` that came out of an error. Three kinds today, one event with `kind` as a property, the same bargain `feature_used` make. **Panics** ride a `set_hook` chained to the previous hook, so abort behaviour is unchanged, and carry location and thread name, **never the payload** — a panic message is arbitrary text and `expect` is routinely handed a path to explain itself with. A `Location` is a compile-time constant naming the *build* machine, and `trim_source_path` cut the rest: `trim-paths` is the proper cure and is **not stable on the toolchain the release workflow pin**, so a registry or git-checkout path keep the part naming the crate and anything else still absolute is cut to its file name. **Parse failures** report at `harness::record_failure` — the same chokepoint as `store::record_parse_failure` one call down, which cannot name the harness — carrying `stage` and harness alone; `raw` is the whole CLI line and `detail` a serde message free to embed the value, so neither leave the machine. **Once per `<harness>/<stage>` per run**, since a wire format that moved fail every line of a live session and the second failure say nothing the first did not. **Failed update installs** report `InstallError`'s tag, a closed set, from a single point `install_update` wrap its body for. Frontend uncaught errors are deliberately out — JS messages and stack frames carry paths, and scrubbing them is its own piece of work (DRA-200).

**The four flag actions come out of `set_session_flags`, which is both buttons' one chokepoint**, and they report only where the flag **changed**: the frontend send the value it wants rather than a toggle, so `pinned: true` on an already-pinned session is a no-op and not somebody pinning it. Collected before the fields move and reported *after* the write, so a failed write report nothing. Named in the reader's vocabulary, not the field's — the row say Settle where the index say `archived`, and the question asked of the number is about the button.

**`space_created` check for the name twice, and the duplicate is the point.** A space is declared in local storage, so the only chokepoint is a `setState` updater — and React may call one twice, which would count one space as two. The report therefore sit *outside* it, judged against `spaces`, the union: re-declaring a name some project already carry as a tag is no new space to the reader, whatever the declared half of the list say. **The browser is deliberately unmeasured** — its only honest chokepoint is `create_tab`, which a page's own `window.open` reach as well as the reader do, and what that should count is an open question rather than a missing line.

**`track_feature` is the one command the frontend report through**, for the handful whose chokepoint is a click handler — the handoff row, whose `action.id` is already a closed union, so a fourth button cannot arrive nameless. It take a `String` and validate nothing: the only caller is this app's own frontend, and a permitted list there would be a second copy of one the call sites already are. Consent and the install id are still read inside `track`, so the webview cannot report anything Rust would not. The frontend side ([analytics.ts](apps/desktop/src/lib/analytics.ts)) **swallow every failure**, since the one thing worse than a missing event is a feature failing because counting it did.

**A persistent install id, and it is minted only for an install that is opted in.** A uuid **v4** on `settings.json` — not the v7 used for session ids, which embed the moment they were minted, one more thing an identifier meant to say nothing would say. `set_analytics_enabled(false)` **clear** it, so opting back in read as a new person rather than the old one resurfacing.

**Consent and the id are one decision under one hold of the lock**, which is why `ensure_install_id` live in [settings.rs](apps/desktop/src-tauri/src/settings.rs) and not in `analytics`. Both halves of that were wrong first time and both were caught in review (DRA-199):

- **Nothing caches the id in-process.** A `OnceCell` held it, and nothing invalidated it when the switch moved — so disabling and re-enabling inside one run handed back the very id the opt-out had just forgotten. A cache here is a second place for consent to be wrong; the file read it saves is small and happens a few times a session.
- **`settings::update` is the only way to change a setting, and `write` is private so that is true rather than aspirational.** `read` take no lock, so a read-modify-write in two steps can be interleaved and lose the other's field. There was a `pub write` beside `read` and seven callers pairing them — the shape that fails, and it fails **across features, not within one**: the Linear account or a transcription pick read while analytics was on, then written back after the reader opted out, restoring `analytics_enabled: true` and the install id with it. So consent could be undone by a setting that have nothing to do with it. Fixing the analytics caller alone and leaving a comment saying "use `update`" was the first attempt and it missed all six others; taking the write away is what stop the next one.
- **`update` recover from a *malformed* file and never from an *unreadable* one**, and `is_malformed` — an anyhow downcast to `serde_json::Error`, which the context chain preserve — is what tell them apart. Bytes that cannot be parsed can never be preserved, and erroring there would block every settings write until somebody deleted the file by hand, which nothing on screen say to do. Bytes that cannot be *read* are the opposite: the file may be perfectly good and merely unreachable for a moment, so writing over it would erase the Linear account, the install id and every transcription pick to change one unrelated switch. Where it does recover the fallback is `opted_out`, never `Default` — recovering must not be a route back to reporting for somebody who turned it off.
- **A failed write answer `None`**, reversing what the cached version did. With no cache, an id that did not reach disk would be re-minted on the very next event and every event arrive as a different person — no events beat a fabricated population.

**No transport plugin, and no new dependency.** `reqwest` is already here for Linear, and PostHog's capture API is one POST, so an event is a request rather than a queue with a flush interval — at single figures per session, batching would buy nothing and cost a drain on the quit path. `tauri-plugin-aptabase` came out with 282 lines of `Cargo.lock`.

### Surveys, and the one thing the POST cannot do

**`posthog-js` is in the webview, and it is there for surveys alone** ([surveys.ts](apps/desktop/src/lib/surveys.ts)). A survey is fetched and drawn client-side by that SDK and by nothing else, so with the POST as the only surface there was nothing in this app a survey could appear *in* — and no amount of targeting fixes a window with nothing to draw it. The SDK captures nothing of its own: `autocapture`, `capture_pageview`, `capture_pageleave` and session recording are all off, and every event this app reports still goes out of `analytics.rs`. **It is not a second analytics client so much as a second surface of the same consent**, which is what decides everything below.

**Targeting reads *persons*, which is the half that had nothing behind it.** `source: "app"` rides every event as an *event* property, and a survey cannot be aimed with one — so the app's install-uuid persons carried nothing at all and `source` was simply absent from the survey UI's field list. `person_profiles: "always"` plus a `$set` of [`base_properties`] is the fix, and it is why `SurveyIdentity` carries that map rather than the frontend naming the fields again. Pinned by test: dropping one from `base_properties` costs a targeting option in PostHog's UI and says nothing whatever in this tree. `identified_only` is the *site's* setting, where every visit is a new cookieless id and there is deliberately no person; here it would leave nothing to target.

**The marketing site can never draw a survey however one is aimed**, since it loads `posthog-js/dist/module.slim` and surveys are one of the four things that build drops. So the app/site split costs nothing here beyond the filter being there when it is wanted.

**Consent is read in Rust, once, and `analytics_identity` is what keeps it that way.** It answers with a key, a host, the install id and the person properties together, or with `None` — and `None` is the refusal, on all three grounds: no key compiled in, `HZ_NO_ANALYTICS`, or an install that opted out. The frontend initialises nothing on it and never reads `analytics_enabled` for itself, because **a second reader of consent is free to disagree with the first**, which is exactly what DRA-199 was already caught by once. Key and host ride along for the same reason rather than becoming a `VITE_POSTHOG_KEY` beside `POSTHOG_KEY`: two build-time variables for one project are two things that can drift, and the drift is silent.

- **`bootstrap`, never `identify`.** The POSTs have already made the install id a person; identifying into it would alias an anonymous id nobody ever used.
- **Started from [main.tsx](apps/desktop/src/main.tsx), not an effect**, the same bargain the focus subscription beside it makes — the SDK lives for the process, and StrictMode double-invokes a mount. Unconditional, since it refuses itself.
- **The settings toggle calls it again**, after the write and unconditionally: the SDK re-reads consent from Rust for itself, so the call only has to say the answer may have moved. Opting out clears the install id and opting back in mints a fresh one — a new person on purpose — so that is the one place the bootstrapped id goes stale, and it is the one place `identify` is right.

**`session_count` is on the identity, and it is what a survey is aimed with.** PostHog receives nothing that counts sessions; the index is the only place the answer lives, so `identity()` reads it. Added there rather than in `base_properties`, a `OnceLock` answering once for the life of the process where this moves with every session made. A failed read leaves the property absent, which a survey targeting a minimum reads as **not** matching — the safe direction, and the cure is opening the app again. The threshold is PostHog's to change, which is the point of it being a person property rather than a rule in this tree.

**PostHog draws the card, and hz draws nothing.** A survey is written, targeted and reworded entirely in its UI with no hz release. The cost, stated: the card is *theirs* — colours and radius are settable, the layout is not, and the byline only comes off on a paid plan, so it will not match [DESIGN.md](apps/desktop/DESIGN.md).

**A hz-drawn card was built and reverted, and the reason is worth keeping.** `getActiveMatchingSurveys` hands the questions over, `disable_surveys_automatic_display` silences PostHog's own display loop, `capture("survey sent", …)` reports back and the answers still land in the survey results view — it works, and the whole of it is in the history of DRA-257 if the stock card ever grates. What it costs is a payload this tree has to build correctly: the response key is `$survey_response` for the first question and the question's **id** or index after that, `id` being optional on the wire, and which key the results view reads has moved between PostHog versions. A wrong one loses the answer silently. That is a real price to pay for a nicer card, and it is not worth paying until the stock one has actually been seen and disliked.

**Frontend uncaught errors are still out of scope.** The SDK arriving does not change that JS messages and stack frames carry paths and that scrubbing them is its own piece of work (DRA-200).

**Nothing is stamped for us.** Aptabase's plugin put `appVersion`, `osName` and friends on every envelope itself; PostHog do not, so `base_properties` build that set once — `app_version` (from `CARGO_PKG_VERSION`, which `tauri.conf.json` hold too), `os`, `arch`, `is_debug`. **OS version is deliberately absent**: nothing in the tree knows it, and reading it mean a new dependency or spawning `sw_vers` on the launch path for a figure nobody has asked a question of. Event properties are merged **over** the base set, so a call site can correct one.

**`track` is not `async` and take no `AppHandle`**, which is what let the feature sites call it — several are synchronous commands with no handle in reach, one of them on CEF's main thread. It spawn, and consent is read *inside* the spawned half on every call, so a new call site cannot forget to ask and cannot run ahead of the persisted answer. `app_started` therefore fire from `setup` as one line that returns immediately.

**An empty key = a build that sends nothing, and that is the ordinary state.** `API_KEY` come from `option_env!("POSTHOG_KEY")`, so every local build compile with none and `pnpm tauri dev` stay out of the numbers. Checked **before** the settings read, or every event cost a file read on a build that sends nothing. `build.rs` declare `rerun-if-env-changed` for it and for `POSTHOG_HOST`, since `option_env!` resolve at compile time.

**`POSTHOG_HOST` treat the empty string as unset, and that is not defensive.** [release.yml](.github/workflows/release.yml) pass it through from a repository **variable**, which expand to `""` when undefined rather than being absent — so `Some("")` is the ordinary case for every build that has not set one, and taking it literally would post every event to `/i/v0/e/` with no host in front of it. Pinned by test. Region is worth a knob at all because the wrong one is a key that authenticates nowhere: a 401, logged, and no events.

**A non-success status is logged, not dropped.** Best effort otherwise — analytics that surfaced an error would be worse than analytics that went missing — but the two ways this silently reports nothing, a wrong key and a wrong region, both land there.

**Opt-out is read off `settings.json` on every `track`.** No in-process copy: `enabled()` is `!env_opt_out() && settings::read().analytics_enabled`, so the settings command write the file and nothing else.

**The persisted answer lives in `~/.hz/settings.json`, not local storage, and timing is the whole reason** ([settings.rs](apps/desktop/src-tauri/src/settings.rs)): `app_started` send from `setup`, before the webview exists. **Anything the frontend can read for itself belongs there, not here**, or this becomes a second settings store free to disagree with the first. `HZ_NO_ANALYTICS` win one direction only.

**`install_id` is `#[serde(default)]`, and that is load-bearing the way every field on that file is** — the settings file is rewritten whole and read on a launch path where a parse failure fall back to opted *out*, so an entry written before the field existed failing to parse would silently turn reporting off. Pinned by test.

**The read fail *closed*, and a missing file is not the same case as a broken one.** Missing or empty = fresh install, read as the default (opted in). Anything else — unparseable JSON, unreadable file, no home dir — read as opted **out**, since a file that exists and can't be understood far likelier belongs to someone who turned this off. Never an error either way: this sits on the launch path. Pinned by test, and the direction is the test worth having. `track` read consent itself before sending, so nothing can go out before the file is read.

**The marketing site report to the same project, and it is a different bargain.** [instrumentation-client.ts](apps/web/src/instrumentation-client.ts) — Next run it before hydration, which is why there is no provider and nothing mounted in the layout; a `<Script>` or a layout `useEffect` both start measuring a page view later than the page view happened. `@vercel/analytics` came out, so the site has one analytics tool rather than two that disagree.

- **Cookieless** (`persistence: "memory"`), which is what mean no consent banner — at the cost that every visit is a new person, so referrers and conversions answer and returning visitors do not. Autocapture, session recording and person profiles are all off.
- **Ingest is proxied** through `drayhq.com/ingest`, rewritten in [next.config.ts](apps/web/next.config.ts), so a content blocker see a first-party request. **Two rewrite rules, not one**: the SDK fetch its own assets from a *different* host to the one it post events to, so a single catch-all leave the script 404ing and nothing measured at all. `skipTrailingSlashRedirect` go with it, since PostHog's API care about the trailing slash Next would otherwise strip. `api_host: "/ingest"` is the other half — change one and the other stop working silently.
- **[lib/posthog.ts](apps/web/src/lib/posthog.ts) is the site's one import of the SDK, and that is not tidiness.** `posthog-js` export a default instance *per module record*, so a file importing `"posthog-js"` beside one importing the slim build get a second instance `init` was never called on, whose `capture` calls go nowhere **silently**. It also pin the slim path: 148KB against 309KB, 45KB off First Load JS, everything it drop already disabled. The deep path is no declared export, so a version bump move it — which fail as a build error rather than quietly, the acceptable direction.
- **The download click use `transport: "sendBeacon"`**, since the href is a plain off-site navigation and the default transport is a request the browser is free to cancel as the page goes.

**The dialog draw *effective* state, not stored state** — `get_settings` answer off `analytics::enabled()` with `analytics_locked` beside it, so with `HZ_NO_ANALYTICS` set the row disable itself and name the env var instead of sitting at `on` while nothing is sent. `env_opt_out()` is read in one place.

## Notifications

Three events hand a session back to the reader — it finished, it wants permission, it asked a question — and each announce itself on **exactly one channel**, chosen by where the reader is. `announce` in [useSessions](apps/desktop/src/hooks/useSessions.ts) is that split, written once and shared:

| focused | on screen | outcome |
|---|---|---|
| no | either | desktop notification |
| yes | no | in-app notice |
| yes | yes | nothing — the transcript *is* the notification |

Channels are exclusive, not additive: a card drawn for something the OS already told the reader is a second interruption for one event, and an in-app card is invisible from another app anyway.

**A fourth event ignore that table entirely: a PR turning ready to merge.** [usePrReady](apps/desktop/src/hooks/usePrReady.ts) raise an in-app card **unconditionally** and post no banner. The table's question is "has the reader seen this happen", and for the other three the answer is on screen — the turn's own output is the notification. This one has no such moment: CI report on someone else's schedule, and the panel line going from "Checks not passing" to "Ready to merge" is a silent two-word swap, so *being on the PR tab ≠ having noticed*. Nothing retire it but its own clock — no read-marking, no rail mark.

**Signal = transition, not state.** The first reading of a session is recorded silently; only a change out of it is news, since the app cannot tell a PR that turned green a second ago from one green since last week. `readyTransitions` ([pr.ts](apps/desktop/src/lib/pr.ts)) own that rule and the pruning with it — a session that stops being watched is **forgotten**, so it comes back as a first sighting. Re-seeding costs an announcement never made, where remembering `false` across an absence raise one for a PR that was ready the whole time.

**Read off the sidebar's marks, not the panel's own fetch**, since the panel's poll gate on its tab being visible and active — exactly the case with nothing to announce. So `QUERY_MARKS` carry `mergeable mergeStateStatus` on the **open half only**: a merged PR cannot become ready, and `mergeStateStatus` is computed *on being asked*. `None` there read as **unknown, not ready**.

**One ordered rule, two presentations.** `mergeVerdict` is the order; `mergeReadiness` turn it into the panel's sentence and `readyToMerge` into the one question the notice turns on — three-valued, `null` where GitHub hasn't worked it out, so `readyTransitions` hold the last reading instead of writing false over it (a merge move the base, every other open PR read UNKNOWN for a window, and settling back would read as news).

**Notices key on session *and* kind.** Keyed on session alone rested on "a session cannot both be blocked on a question and have finished a turn", which is false for the fourth kind: CI report while the agent stands still waiting for permission. `ANSWERED_BY_OPENING` spell out the three kinds opening a session answers — `pr` absent, since selecting a session ≠ looking at its PR.

**⌘G take the card without reaching for it**, acting on the **oldest** — the top one, next to expire — which make the key repeatable. The binding lives in `NoticeStack`, not `App`, so it exists only while a card does, and the cap is drawn **on** the card it acts on, which is also how the stack says which one the key takes.

**The progress bar is the timer, not a picture of one.** The store hold no `setTimeout` at all: the bar's `animationend` call `dismissNotice`. One clock means hovering pause both, so a card cannot vanish under a cursor reaching for its button, and it can't expire while the window is occluded and the animation throttled. `completed` run 10s, `asking` 15s. **A card going away ≠ the signal going away** — the `asking` one leave the session still blocked, which is fine because the yellow rail mark stays lit until the request is answered.

**Reading requires looking, so a `completed` notice on the selected session is only retired when the window has focus.** The other half is a focus listener marking it read on return, without which a session finishing in the background stay unread forever.

**The sidebar rail carry both marks and they mean different things.** Green = *unread*: the turn is over, cleared when the row is viewed. Yellow = *waiting on you*: the turn is still open and only an answer clears it, so viewing the row leave it lit. Yellow wins where both apply. The waiting set is frontend-only (`asksBySession`, request ids so `permission_decided` retire the right one) and deliberately **not** folded into `SessionStatus` — the backend report these sessions `in_progress` and is right to. Cleared when status leaves `in_progress`, which is what stop a stranded request marking a dead session as waiting forever.

**Dock badge = that same pair, counted** ([attention.ts](apps/desktop/src/lib/attention.ts), [useDockBadge.ts](apps/desktop/src/hooks/useDockBadge.ts)) — one predicate shared with the rail (`asking || status === "completed"`), so the number is a promise about what opening the window shows. It needs no clearing path of its own, and `0` goes out as `undefined`, which is what removes the badge. Counting read three sources, each covering a hole the others leave: `statusBySession` is empty at launch where the index carry `completed` from last run; the index list hold one side of the archived split at a time; and `asksBySession` is in neither. Live status wins over persisted.

Two Tauri facts. `core:window:allow-set-badge-count` is **not** in `core:default`, so it is named in [capabilities/default.json](apps/desktop/src-tauri/capabilities/default.json) — with the same failure mode as `start-dragging`: the ACL refuse and report nothing. Unlike the desktop banner, this one **does** work under `pnpm tauri dev`.

**Focus is read imperatively, never as state** ([focus.ts](apps/desktop/src/lib/focus.ts)) — the one caller that matters sits inside a Tauri listener registered once with `[]` deps, where a state value is the mount-time one forever. The source is Tauri's `onFocusChanged`, not the DOM's `blur`: a webview blur whenever focus leaves the document, which a native menu or devtools do without the user leaving the app.

### The desktop banner

**Posted from Rust, not from `tauri-plugin-notification`** ([notifications.rs](apps/desktop/src-tauri/src/notifications.rs)). The plugin cannot deliver a click on desktop and no configuration makes it: its desktop path spawn `show()` and drop the returned handle, and its `onAction` listener is wired to an event only mobile backends emit. Worth knowing because it *looks* like it works — macOS raise the app on click by itself, so the window comes forward and then sits on whatever session was already open.

`notify_session` wait on the handle, and `"default"` (the body, against `"__closed"` that dismissal and expiry both report) raise the window and emit `notification_activated` with the session id. The wait block until the reader acts or the banner ages out, hence `spawn_blocking`. **Raising the window and selecting the session are separate and both needed.**

- **A banner with no sound is delivered silently**, wrong here since this channel only fires when the reader is in another app. notify-rust call `setSound` only when `sound_name` is set at all, and the value is a trap: `""` reads like "no sound" and is the opposite, being the name that resolves to the **system default**. `asking` get **Ping**, since a question left unanswered holds the session open; `completed` take the default.
- **`preview-macos-un` is not an optional feature here — without it nothing is delivered at all.** notify-rust's default macOS backend is the deprecated `NSUserNotificationCenter`, which current macOS does not deliver for an app: measured from inside the running app, every shape timed out at exactly 2.0s while the *same code* in a plain CLI process delivered a clickable banner. `tauri-plugin-notification` post the same way and would fail identically.
- **The banner cannot work under `tauri dev`, and the guard is `is_dev()`.** `UNUserNotificationCenter` reach for the process's bundle and raise an **uncaught** `NSInternalInconsistencyException` when there isn't one, aborting the app rather than returning an error. `check_bundle` is *not* the guard to reach for — it only ask whether a bundle *identifier* exists, and the embedded `Info.plist` satisfy it right up to the frame that killed the app.
- **The bundle need a signing identity or macOS refuse permission silently.** Tauri's bundler leave the app linker-signed under a generated identifier, and with that mismatch `request_auth` return `Ok(false)` with status `NotDetermined` and **no prompt ever shown**. `bundle.macOS.signingIdentity: "-"` in [tauri.conf.json](apps/desktop/src-tauri/tauri.conf.json) fix it. This is the floor below which notifications don't work at all.
- **Permission is asked once per process, on the first banner** (`request_auth_once`). The call **block until the reader answers**, so a per-banner ask park a thread per notification behind one prompt. Nothing branch on the result: denial is silent and permanent, and the in-app notice cover the reader either way.

## Parser conventions

[parser.rs](apps/desktop/src-tauri/src/harness/mcode/parser.rs) is the file most likely to need extending, and it has firm conventions:

- `ClaudeCodeEvent` = externally-tagged enum on `type`. `SystemEvent` and `ResultEvent` nest a **second** tag on `subtype`. Adding a new CLI event = adding a variant at the correct level.
- **mcode's shapes are typed**, tagged on the wire's own `sessionUpdate` discriminator — `agent_message_chunk`, `tool_call`, `tool_call_update`, `usage_update`, `available_commands_update` — with `#[serde(other)] Unknown` on every enum. An update this build has not been taught is a line that parses and maps to nothing, never a line that costs the turn.
- Genuinely volatile payloads (`rawInput`, `rawOutput.details`) stay `serde_json::Value`, and `details` is passed through whole: each tool fills it with its own shape, so one tool's shape failing to parse must not cost the other eleven.
- Fields the CLI may omit need `#[serde(default)]`. CamelCase wire fields need an explicit rename (`toolCallId`, `rawInput`, `sessionId`).
**Outbound lines are typed too** ([rpc.rs](apps/desktop/src-tauri/src/harness/mcode/rpc.rs)) — `request`, `request_detached`, `notify`, `respond` and `respond_err` are the only ways a line leaves the app, so no call site spells an envelope by hand. Typed despite nothing here failing loudly, because **a wrongly shaped reply is ignored in silence**: ACP answers what it recognises and stays quiet otherwise, so a drifted envelope presents as a hung turn rather than as an error.

## Test fixtures

Tests use `include_str!` against real captured CLI output under `harness/<name>/fixtures/`. To add coverage, capture real output, commit it, assert against it — the probe scripts are not committed, the captures are. A shape absent from every capture (a permission request, a `thinkingEffort` ladder) gets a hand-written test pinning what the CLI's own source documents, and the fixture README says which rows those are. Fixtures are a shared asset — a frontend test needing real wire output reads the same file rather than committing a second capture.

mcode's three, all captured against `mcode acp` 0.4.12, all `>> `/`<< ` one line each, both directions:

- `live_turn.jsonl` — the whole lifecycle at its smallest: `initialize` (capabilities, including the `image: false` the composer's attach path answers to), `session/new` with its `configOptions`, one prompt writing a file and running `wc -c`. The only capture of `available_commands_update`, of `usage_update` carrying a `cost`, and of the two `modes` a session opens with.
- `resume_fork_cancel.jsonl` — the three lifecycle calls a live turn never reaches. `session/resume` answers **no `sessionId`**; `session/fork` answers a new one; `session/cancel` is a **notification**, and the turn ends as the prompt's own response with `stopReason: "cancelled"`.
- `todowrite.jsonl` — a plan, which the strip, the panel and the transcript's plan rows are drawn from. The list rides the call's `rawInput` under `todos`; the same list comes back on `rawOutput.details.todos`. It also carries **80 bare `{toolCallId}` updates**, which is the evidence for skipping an update that says nothing.

**Filtering `cargo test` rewrites generated TS.** ts-rs regenerates `src/types/events.ts` from whatever exports ran, so `cargo test git::` leaves only git's types and breaks the frontend build. **Always follow a filtered run with a bare `cargo test`.**

## Rendering code

Every surface showing code — `Edit` diffs, ranged `Read` slices, markdown fences — go through **one** Shiki highlighter, the shared instance inside `@pierre/diffs`: [DiffView](apps/desktop/src/components/chat/DiffView.tsx), [CodeView](apps/desktop/src/components/chat/CodeView.tsx), and [codePlugin.ts](apps/desktop/src/lib/codePlugin.ts) replacing `@streamdown/code`'s runtime. Sharing is not just deduplication: the stock Streamdown plugin build a *second* Shiki with its own registries, which cannot see `pierre-*` at all.

**Themes are `{light, dark}` pairs, never one name** ([codeTheme.ts](apps/desktop/src/lib/codeTheme.ts)) — the app's mode can change under a mounted view. **The shipped default is `auto`, which mean the app theme, so `codeThemePair` take one** — resolving without it drew every palette's code in Pierre's colours and switched on mode alone (DRA-183). `AUTO_THEMES` hold the map; a palette with no Shiki counterpart take the nearest, never a grey. [useCodeTheme](apps/desktop/src/hooks/useCodeTheme.ts) is `useSyncExternalStore`, not `useLocalStorage`, because several diffs are mounted at once and per-component state desync them.

Three failure modes, all presenting as _code that renders but is blank or grey_ rather than as an error:

- **A view must not mount before _its own_ language and theme are attached.** `FileDiff`/`File` kick off their own load when they hydrate without one, then drop the promise and never re-render. [useHighlighter](apps/desktop/src/hooks/useHighlighter.ts) is the single gate both views use, checking `getLoadedThemes()`/`getLoadedLanguages()` for the specific pair and language. **Do not gate on `isHighlighterLoaded()`** — it only report that an *instance* exists, so a view whose grammar is still loading mount the moment any other view warmed the highlighter.
- **Themes and grammars load independently.** Tokenizing with a theme unattached return every token with an empty style; with a *grammar* unattached it silently yield one plain-text token per line. `codePlugin` check both and report not-ready rather than caching either result — caching the plain-text fallback is what left blocks permanently grey.
- **A fence's info string is a language id, not a filename.** `getFiletypeFromFileName` map *extensions*, so it turn `typescript` and `rust` into `text` while only `ts` happens to work. Use it for paths, never a fence tag.

**Streamdown's link hardening write into prose, so we replace its rehype list** ([markdownPlugins.ts](apps/desktop/src/lib/markdownPlugins.ts)). `rehype-harden` drop an href it cannot resolve — right — then leave a literal ` [blocked]` beside the link, which lands in the reader's text as if the agent typed it. `linkBlockPolicy`/`imageBlockPolicy` = `text-only` unwrap instead. Streamdown expose no option, so the whole `rehypePlugins` list is passed, with **harden's own function taken back out of `defaultRehypePlugins`** rather than from a direct dep, which pin it to the version Streamdown itself runs.

`File` number files from 1 and expose no starting-line option, so `CodeView` rewrite the gutter in `onPostRender`, which hand back the *host* element whose rows live in its shadow root.

**Every diff side carry a content-derived `cacheKey`** (`diffSide` in [diff.ts](apps/desktop/src/lib/diff.ts)). The library fall back to the file *name* as the key and the worker pool cache highlighted lines on the key alone — so a second `Edit` to one file, or `index.ts` from another dir, reuse the first one's tokenized result and a longer diff walk off its end ("deletionLine and additionLine are null", thrown mid-render). Key = full path + length + FNV-1a of the text. **Never hand `parseDiffFromFile` a bare `{name, contents}`.**

**`+N -M` come from the library's hunks, not a hand-rolled scan.** `countChanges` sum `hunk.additionLines`/`deletionLines`, so a collapsed row can never disagree with the diff it opens. A prefix/suffix scan looks equivalent and isn't: `Edit` fragments usually arrive without a trailing newline, so the algorithm treat the boundary line as changed on both sides. Group headers carry the same figure summed over their calls, memoized on call count rather than on `calls`. These are *region* counts, not file counts.

**Where time goes, and the engine is the whole answer.** Every Shiki instance here — the shared main-thread one and each pool worker — run on **WASM Oniguruma** (`HIGHLIGHT_ENGINE` in [useHighlighter.ts](apps/desktop/src/hooks/useHighlighter.ts)), never the library's default JavaScript regex engine. `getSharedHighlighter` read the engine on first creation only, so **every creation site name it** — `warmHighlighter`, `useHighlighter`, `codePlugin`, `DiffWorkerPool` — or whichever run first decide for the rest. Measured in Safari 26.5 (the WKWebView's JavaScriptCore) through this app's own components, the JS engine tokenized at ~1ms/line (2237 lines of TS = 2.2s, a full-file diff twice that) and translated each grammar's regexes lazily on first use — ~1.9s for TypeScript, paid **separately** by the main thread and by each worker — so a small Edit waited 1.0s, a small Read 1.8s and a 2000-line full-file diff 5.8s (DRA-235). Same code on WASM: 230ms for those lines, 150ms cold, 110ms → 1.4s for the same three. V8 hide the gap (3x, not 10x), which is why a Chromium head never showed it; **measure code rendering in Safari or the app, never in the session browser.** The binary is base64-inlined in `shiki/wasm`, so nothing is fetched. Grammar *attach* is the cheap half (~25ms for the whole `COMMON_LANGS` set) and is per language and one-off; *tokenizing* is per file and scales with the whole file, not the change. `warmHighlighter` preload a **named list** — keep it that way. Anything absent still load lazily and render *unhighlighted but readable* meanwhile. **A `File` input want a `cacheKey` like a diff side does** (`diffSide`), or the pool cache nothing for it and every remount tokenize again.

**Diff highlighting run in a worker pool** ([DiffWorkerPool.tsx](apps/desktop/src/components/DiffWorkerPool.tsx)) — without one, whole-file tokenizes ran on the main thread and expanding a row froze the app for up to a second. `FileDiff`/`File` pick the pool out of `WorkerPoolContext` themselves and fall back to the main-thread path (`isWorkingPool`) rather than erroring. Three wiring facts: the worker is built by Vite's `?worker` import (the library take a factory because it cannot know the host's bundler); `worker.format: "es"` in [vite.config.ts](apps/desktop/vite.config.ts) keep the worker's conditional `import("shiki/wasm")` from being inlined as ~600KB; and the pool's theme **override** each view's `theme` option, so `PoolThemeSync` push pair changes via `setRenderOptions`. Pool size 2, not the default 8. Markdown fences still tokenize on the main thread.

**A long session open on its newest turns and backfill the rest.** Opening an 11MB, 61-turn log measured ~700ms, and bytes were not why — what cost was mounting every collapsed turn's answer through Streamdown at once. So [Chat.tsx](apps/desktop/src/components/Chat.tsx) draw the newest `FIRST_MOUNT` turns on the first commit and mount older ones above in `MOUNT_STEP` chunks, one per macrotask ([turnWindow.ts](apps/desktop/src/lib/turnWindow.ts)). Each step grow content *above* what the reader is looking at: pinned, the bottom is re-taken; unpinned, the oldest mounted turn's node is anchored before the step and `scrollTop` moved by exactly what it moved — a height diff is wrong there, since a delta landing below the anchor would count as backfill. Not virtualised: backfill finish in well under a second and then the transcript is ordinary DOM.

**`content-visibility: auto` on each turn was tried elsewhere and rejected here.** It is the substitute for a windowing library — a dozen CSS lines on `.transcript-turn`, off for the live turn, which is what MonoCode ships. It does not fit this app: its `contain-intrinsic-block-size` placeholder is *remembered per element only once that element has been rendered*, and a turn mounted below the fold has not been, so the scroll height above the reader is an estimate until they scroll up and watch each turn resolve. hz's turns are hugely variable (a one-line answer, a five-thousand-pixel diff), its backfill already pays the mount cost in chunks, and the rail measures `offsetTop` on those turns to scroll to them. The placeholder would trade a cost already paid for drift in the two mechanisms that depend on that measurement. Measured as a shape, not benchmarked — the failure it would introduce is not one a benchmark shows.

## The command palette

**⌘K, one box over the window.** [CommandPalette](apps/desktop/src/components/CommandPalette.tsx) searches sessions, projects and spaces and runs anything the shell can do. The rows are built in `App` — the one place that holds the callbacks — through [palette.ts](apps/desktop/src/lib/palette.ts), which is pure and tested: an empty query draws everything in the order the app already draws it (the sidebar's own sort for sessions), a prefixed query puts label-starts-with above contains, and **`>` narrows to actions** — the convention every palette shares and the first thing a reader arriving from another editor tries.

- **An explicit action table, not a replay of the chords.** Dispatching a synthetic keystroke would be shorter and it lies: a chord that is `enabled: false` in the current pane fires nothing, so the row would do nothing and say nothing. Each row calls the same function its own chord calls, and a row that cannot apply is not built — which is why the three view tabs only appear with a session and off the issues page.
- **Keys are the input's.** The list is never focused, so arrows, Enter and Escape are read by the field being typed in — the composer's picker makes the same bargain, for the same reason (a list that takes focus takes the caret with it). Escape is Radix's.
- **Search is a view, and the palette is the box over the window.** `SearchView` (⌘⇧F, the sidebar's row, the palette's own `Search` action) is a page in the main column like the inbox's three: a box across the top, a scope row under it — All, Sessions, Messages, Files, Code — and one list under that, `h-8` rows of an icon, the text with the query marked, and a mono meta at the far edge. It is a page rather than a modal because the scopes and the list want the room, and because a search a reader leaves open while they work is the one they come back to. `searchHits` is pure and tested: sessions first, then messages, then names, then lines, so switching a scope never reshuffles the rows already on screen, and each kind is capped on its own (`HITS_PER_KIND`) — one word in a lockfile must not bury the session the reader wanted. The sidebar's row **opens it** and no longer becomes an input: the inline filter answered one of the four questions, and two places disagreeing about what searching means is what this replaced.
- **And the files the session runs in, which is the half a coding palette is for.** `search_content` is one `git grep -z -n -I --untracked -i -F` in the session's own `cwd`, parsed from the NUL-delimited record git answers with — one process, git's own view of the project, and no dependency added to read a tree. `--untracked` is the flag that matters here and the one the reference does not pass: the file the agent wrote a minute ago is exactly what a reader searches for and is not in the index yet, so without it the box would answer *not here* about the file on their screen. A session outside a repository finds nothing — no results rather than an error, the same bargain the log search makes. Each hit is a palette row whose label **is the line** and whose detail is `path:line`, capped at `CONTENT_ROWS` because one word in a lockfile is a thousand rows; `contentRows` is pure and tested, and the row opens the line in the session's file view. The palette also marks the query inside every row's label (`highlight`), so the reader sees which words answered.
- **It searches the sessions' own logs, not only their titles.** A row of kind `match` is a sentence found inside one, answered by [search.rs](apps/desktop/src-tauri/src/search.rs) walking `~/.hz/sessions/*.jsonl` newest-first and stopping at twenty. **`App` owns the query rather than the palette**, because that walk is a read: debounced 180ms, gated at two characters, and every answer carries the *generation* it was issued under — the answer to the previous query landing late would otherwise file its rows against words the reader has since changed.
- **A hit is a string *value* under `payload` — never a key, and never `payload.type`.** Keys make a search for `text` match every line in every log; the discriminator is a closed vocabulary, so searching it returns every assistant message in the app rather than the sentence the reader meant. Everything else under the payload is something a person or an agent wrote.
- **The case fold is ASCII-only, and that is a trade rather than an oversight.** `to_lowercase().find(…)` is the obvious spelling and cannot be used: a fold can change byte lengths (`İ` lowercases to two characters), so an index into the folded copy lands *inside* a character of the original and slicing there panics. The walk slides byte windows of the original and folds as it compares — so `über` does not find `Über`. A line over 64KB is skipped for the same kind of reason: a screenshot's base64 is one line and there is nothing in it to find, so a match inside a multi-megabyte tool result is one this misses.
- **A real `ShortcutKeys` per row**, read from the registry, so a rebinding moves the caps without the palette knowing: it cannot name a chord the key no longer fires. The kind is a word on the row rather than a heading over a run of one.

## When something breaks

**A render that throws no longer blanks the window.** React unmounts the whole tree when nothing catches, which is what the app looked like before: a white window over a perfectly alive process, no message and no way back. [RenderErrorBoundary](apps/desktop/src/components/RenderErrorBoundary.tsx) is mounted twice — around the main column's bodies, so one bad row costs one view rather than the sidebar, header and composer with it, and around `<App/>` in `main.tsx` as the floor. **It takes a `resetKey`**, and that is not decoration: a bounder latches on the error it caught, so keyed on the session and view, moving anywhere else drops it rather than leaving the pane broken for the rest of the run. The panel shows the message itself, a Reload and a clipboard copy — and **nothing goes to analytics**: an error message is arbitrary text that routinely carries a path, the same rule the `error` event states.

**A read that runs long says so, and only then.** [slow.ts](apps/desktop/src/lib/slow.ts) wraps an `invoke` at the call site — never the `invoke` helper, which would cover `send_msg`, and a send already has its own indicator. Four seconds in, one line appears bottom-left naming what is being read; it clears a beat after the read lands, or on a failure too, since the composer's error slot is then saying what actually went wrong. **One line at a time, naming the oldest read still running**: a second slow read is the same wait seen from another angle, and stacking them turns a sentence into a wall. The call sites are the reads that otherwise leave an empty pane — providers, models, the session index, the context probe.

## Composer

- **The row under the text is where *how this runs* goes, and the composer places it.** The context meter and the permission picker are `meter` and `permission` nodes rather than the toolbar's own items, because the toolbar is *above* the input before a session exists and *under* it after — so the one row that is always below the text is the row the legend sits on, and that row was most of a blank line on a wide window. They sit at its far end in the order they are read: what the agent may do, then what it has spent doing it. In a session both land in the row the toolbar is on, where the permission picker already was and the meter was its last item — so a session's composer is unchanged. **The box is as tall as its text and no taller**, which is also what keeps dictation and Send on the text's own line: they are `items-end` in that row, so any floor under the height puts them at the bottom of an empty box and reads as controls that have fallen off the message they belong to.
- **`isNewTask` is the composer's two presentations, not one flag per effect.** Before a session exists the composer stands alone mid-window, so [ChatInput](apps/desktop/src/components/ChatInput.tsx) drops the card's fill, border and padding, moves the toolbar above the input, swaps the placeholder, and replaces the send button with a "Press ⏎ to send" hint. Dropping the button is only safe because Enter-to-send lives in `onKeyDown` rather than in that button being the form's submitter — make it the submitter again and the empty state loses its send path.
- **The error slot reports the reader's own last action failing, and nothing else.** It is one `useState` for the whole app, so anything written there follows the reader to every other session and to the new-task composer. An agent `error` payload therefore is **not** mirrored into it: that error belongs to one session, is persisted, and `EventRow` already draws it as a red row in that session's transcript — mirroring it drew it twice and outlived the conversation it was about. One decision across every harness, not a patch per caller. What remains are `invoke` rejections, which the reader caused a moment ago, so both intentional selection moves (`handleNewSession`, `handleSelectSessionIndexItem`) clear the slot **on the way in** — never on the way out, since the session-not-found rollback writes its own sentence after moving the selection. **Clearing is half of it; `navGen` is the other half.** A send, an interrupt or a permission reply rejects seconds after the reader has moved on, and an unguarded catch writes the previous session's failure into the composer they moved to. So every **session-scoped** catch reports through `failUnlessLeft()`, taken at the start of the action: it captures the navigation generation and writes the slot only while no move has bumped it since. Four moves bump it — select, new task, a send minting a session, a fork opening selected — and the two that also start an action (select's read, send itself) take their `fail` *after* the bump, so their own failure still reports. **App-wide loads and actions stay on the raw setter** — the index, projects, branches, a checkout, a space retag: their failure is as true after a move as before it, and guarding them left a list stale or empty with nothing saying why.
- **A draft belongs to the session, not the composer.** [useDraft](apps/desktop/src/hooks/useDraft.ts) keys unsent text by session id, `null` for a new task. The store is **module-level, and a ref would not do**: `AppShell` renders the footer at a different position when `centered`, so moving between the empty state and a session unmounts `ChatInput` and mounts a fresh one — losing the draft on exactly the switch most likely to be made. Nothing is persisted. [useAttachments](apps/desktop/src/hooks/useAttachments.ts) is the same shape, and also because the `+` button lives in `ComposerToolbar`, which reaches `ChatInput` as an opaque `ReactNode`.
- **↑ and ↓ walk the prompts already sent, in an empty box.** Not a store — the transcript *is* the history, so a resumed session arrives with yesterday's prompts already in it, which is the visit that wants this most. `recalledPrompts` skips a relayed `user_message`, since walking back into a sentence another session sent would put it in the box as if you had written it. `recallMove` is the whole rule and it is pure: the walk engages only from an empty box or from a prompt still unedited, so **editing a recalled prompt hands it back** and the arrows go to moving the caret. ↓ past the newest clears the box, which is the only way back to a draft of your own without editing one of these. Bound *after* the picker's arrows, so an open menu keeps them.
- **⌘⇧S stashes the draft, and the stash is in memory.** [useStash](apps/desktop/src/hooks/useStash.ts) is a module store keyed by composer like the two above; [StashBadge](apps/desktop/src/components/composer/StashBadge.tsx) draws only when something is stashed, and restoring **appends** rather than assigns — a stash goes back into whatever is being written now, so it cannot destroy a sentence typed while it was away. **Not ⌘S**: that is the Docs panel's own save, and the registry test refuses two ids sharing a default chord. Not persisted, for the reason the draft is not: a stash that outlived the app would have to survive attachment paths that may not.
- **A blast of pasted text becomes a file, and a draft has a ceiling.** Over 32KiB (`pasteBecomesFile`) `onPaste` reads the clipboard, parks the text as a `.txt` under `~/.hz/pasted/` through `write_pasted_text`, and pins the resulting attachment — the bytes never reach the textarea, so the reader sees a tile in the tray rather than a wall of text they then have to undo. Everything smaller is left to the browser, which keeps undo and the spelling checker honest. Over `MAX_PROMPT_CHARS` the send button is disabled and a line under the box names the count, the limit and the way out. The limit is its own flag rather than part of `canSend`, because `stopping` reads `canSend` to choose between Send and Stop — folding it in would offer to *cancel the turn* as the way to shorten the text.
- **A quotation is prompt text, and it has no chip of its own.** Select text inside an answer → [AssistantSelectionToolbar](apps/desktop/src/components/chat/AssistantSelectionToolbar.tsx) appears over the selection (pointer selections only; a `pointerup` handler, not `selectionchange`, or the bar flickers while somebody types next door) → **Cite in composer** pins `{quote, comment}` to [useCitations](apps/desktop/src/hooks/useCitations.ts), and one effect writes the quote into the draft as a markdown blockquote with the comment under it. **That is the whole of its presence** — the text is where it lives, which is why nothing draws it. `highlightSegments` gained one block rule for it (`quote`, a line opening `> `), so the sent bubble draws a quotation instead of a row of chevrons; that is the only block construct the scanner reads, and the tests that pin headings and bullets staying literal are still there.
- **An attachment is a tile in the tray above the input, and it used to be a token in the draft.** `📎 name size`, written at the caret, painted as a pill by the mirror, deleted with backspace — on the argument that a chip inside the message beats a list beside it. It read worse than it argued: the token *is* part of the prompt, so a photo came back from the transcript as a colour emoji in the middle of a sentence, and its size rode in the text where nobody could edit it. [AttachmentTray](apps/desktop/src/components/composer/AttachmentTray.tsx) draws what is pinned instead — an image as its own thumbnail, a file as a type glyph and a name, the `×` on hover — and it is the only place attachments are drawn. What survives of the token is the **shape of one in a log already written**: the scanner and the transcript still read `📎 name size` out of a session recorded before the tray, so an old prompt draws as a chip rather than as a stray emoji.
- **The command is free, and measured so.** `/context` sent as a prompt is intercepted by the agent's own ACP layer, never reaches a model — `end_turn` in about a second — **and leaves no trace in the agent's own conversation**: the session's `messages.jsonl` in `~/.hz/agent/v2/sessions/…` is still zero bytes after one. So the cost of asking is a second of the child's CPU and no tokens, no context, no history.
- **`probe_context` swallows the turn it starts.** Every mapped event of it is dropped in the read loop while the probe flag is set, and the text deltas are what the caller gets: a reading the reader asked the panel for is not a message in the transcript. A prompt arriving behind it is *queued* by the agent, not refused (measured: both prompts answered, the second a couple of seconds later), so the probe never blocks a send.
- **The newest reading rides the session's index entry** (`SessionIndexItem::context_reading`, stamped), because only a live child can be asked and a session outlives its child. Reopening the app used to replace the agent's own rows with hz's estimate of the transcript for the ordinary act of quitting — so the panel draws the kept one instead and the footer says **when** rather than claiming it is current. The snapshot's own `live` field is the agent's word about its *runtime* and says nothing about the copy being current; the stamp is what tells the reader which moment they are looking at. A failed refresh keeps the reading and adds the reason: mid-turn the agent refuses, and with no child at all there is nothing to ask, which is its own sentence rather than the agent's "nothing to count yet".
- **`ContextMeter` is keyed by session id.** It holds what its own ask fetched, and the composer's toolbar survives a session switch — unkeyed, the reading of the session the reader just left would be drawn as current under the one they arrived at.

**A compaction is the CLI's, and the wire says nothing about it.** `/compact` is one of the agent's own ten commands, so it travels as ordinary prompt text and the runtime rewrites the conversation; hz triggers none of it. **There is no update for it on the wire** — mcode's ACP vocabulary is twelve `sessionUpdate` kinds (message and thought chunks, tool calls, plans, usage, modes, commands, session info) and a compaction is not among them, which is what its own ACP package emits and no more. What the wire does carry is the *result*: the runtime answers the command with the counts as text (`Compaction completed.` / `Messages: 42 → 11` / `Tokens: 310,442 → 12,004`), which lands in the transcript as an ordinary assistant message, and a finished compaction makes the runtime re-state its `usage_update` — which is what moves the context ring. So the numbers need nothing from hz; the *wait* does, and it is seconds to minutes with nothing else on screen. `compactingOf` derives it from the prompt hz itself sent: `/compact` is a prompt like any other and the turn stays open until the CLI has finished, so "the newest prompt names that command and the session is busy" is exactly that window. The same move `UserMessage` makes to draw a command's chip, for the same reason — the CLI never echoes a prompt back. Two blind spots, both stated in the function: the compaction the runtime runs *by itself* before an LLM call, which happens inside an ordinary turn where the working indicator is already up; and a `/compact` sitting in a *queued* prompt, which has not been sent and so is nobody's wait.

**`ContextCompactionStarted` and `ContextCompacted` are read, never produced.** They were real — Claude Code, Codex, omp and pi each had a mapper that built them from their own stream — and every one of those harnesses is gone. They stay in [events.rs](apps/desktop/src-tauri/src/events/events.rs) because a session some older build wrote still reads, and dropping a variant fails that line: the transcript row and the meter's `post_tokens` settle both still work for a replayed old session, and neither can fire on a live mcode one. The indicator was written for that pair and could not appear for the whole life of this harness; it is driven from the prompt now.

**Slash commands are prompts, not protocol.** Every one travels as ordinary prompt text and the CLI expands it, so sending one needed no new code. Two things follow: the transcript cannot tell a command from prose (the CLI never echoes the prompt back), so [UserMessage](apps/desktop/src/components/chat/UserMessage.tsx) re-parses the text with `parseSlashCommand` to draw the name as a chip; and the command *list* is the only part that needed a backend.

**The command list is pushed, never asked for — and it is the agent's, all the way to the menu.** mcode sends `available_commands_update` when a session opens and whenever it changes, carrying ten commands with their descriptions, so `commands.rs` shapes what the agent said rather than keeping a table — and the read loop **emits `slash_commands` the moment the update lands** ([mcode.rs](apps/desktop/src-tauri/src/harness/mcode/mcode.rs)), which the frontend holds per session and the composer's menu draws. There is no `invoke` for this and there was: `list_slash_commands` answered an empty `Vec` for every harness, because mcode pushes and a caller with no session has nothing to read — so the menu said *"This agent publishes no slash commands"* for the whole life of every session, while the agent's ten sat unread behind it. Three things were wrong at once, all three fixed:

- **The list crossed by request.** It cannot: the push is the only statement of it, and a request would have to guess when to repeat.
- **The copy it landed in was on `McodeSession`, and nothing read it.** Deleted — the emit *is* the record, and the frontend is the one place it lives.
- **The emit is gated on nothing.** `note_update` runs only where the read loop already holds the session, and the update arrives on the heels of `session/new` — the loop can see it before `init` hands the session over, which is exactly how the stored copy was lost in that race.

**A picker that never opened is the one empty state** — a list empty *for good* leaves `menuOpen` wanting rows, so `PickerMenu` draws one sentence instead. `null` in the frontend means "the child has not spoken yet" and keeps the menu shut; the sentence is only for an agent that published an empty list.

**No `@path` expansion, and the composer says so by naming the file in prose.** `Capabilities::expands_at_mentions` is false: mcode's prompt path has no mention parser, so `@src/lib/x.ts` would reach the model as literal punctuation it has to guess the meaning of. [mention.ts](apps/desktop/src/lib/mention.ts)'s caret arithmetic is kept for the day a harness parses one; nothing draws its picker today.

**Attachments are two features, because two kinds travel two ways.** [attachments.rs](apps/desktop/src-tauri/src/attachments.rs) decides which from extension *and* size together, so the composer's tile and the wire can't disagree. **Images** — png/jpeg/gif/webp under 5MB — become a base64 `image` content block alongside the prompt. Anything else becomes an `@/abs/path` mention appended to the prompt text, so it needs no wire surface at all; that cheapness is also why an oversized or unsupported image *degrades* to a mention rather than failing the send.

- **Only paths cross the bridge.** `read_attachments` hands the composer a thumbnail as a `data:` URL; `send_msg` takes back a path and re-reads the file.
- **Images are copied into `~/.hz/attachments/<session-id>/` before the path is recorded.** Persisting base64 instead puts megabytes into an append-only log read whole on every open; pointing at the original breaks the transcript the moment a screenshot is cleared out of `~/Downloads`. Loaded through `convertFileSrc`, hence `assetProtocol` scoped to exactly that directory. Non-image files are deliberately **not** copied — their mention has to name a real file in a real tree.
- **The drop target is the window.** Tauri intercepts the native drop before the webview sees it, so there are no HTML drag events to bind; `onDragDropEvent` reports paths, not `File` handles.
- **A queued prompt's attachments ride its queue entry**, resolved, handed over by the composer at send. `QueuedMessage.attachmentPaths` is deliberately *unresolved* so a cancel gives back what the user typed, so the row would otherwise describe them a second time — and holding them anywhere but that state gives them a lifetime free to disagree with it. Images draw through `ImageRef.url`, never `path`: the archived copy the asset scope allows is written at flush. A file draws nothing, since its `@path` mention is written at flush too and the delivered bubble has no tile for one either.

**A picture a tool hands back.** `Read` of a `.png` comes back as an `image` content block and nothing else. **The bytes arrive twice on one line**, and one copy was being persisted: the result carries an `image` block *and* the line's `tool_use_result` sidecar carries the same base64 at `file.base64`, which went straight onto `ToolResult.structured` — a screenshot session was 12MB of base64 in a 14MB log, read whole on every open and drawing nothing. The mapper now reads the block and `strip_image_bytes` drops the sidecar's copy. It mints an `ImageRef` carrying a `data:` URL, then `archive_result_images` in `read_stdout` decodes, writes and swaps the URL for a path **before emit**, so live and replayed transcripts load the same file; `read_stdout` strips the URL before both retained copies. **A call carrying a picture leaves its group** — "Read 3 files" is an honest summary of three files and no summary of three screenshots.

**The picker is one menu that must not take focus.** Every other composer control is a Radix menu focusing itself on open; this one can't, since the textarea has to stay focused so typing keeps filtering. So [PickerMenu](apps/desktop/src/components/composer/PickerMenu.tsx) is a plain positioned listbox and every key it answers to is handled by `ChatInput`'s own `onKeyDown`. Enter completes the highlighted row instead of sending — the single place the Enter-sends rule gives way. Both pickers are that one component, and they are **mutually exclusive without arbitration**, since the caret sits in exactly one token.

- **The composer's colouring overlay and the transcript share one segmenter** ([highlight.ts](apps/desktop/src/lib/highlight.ts)). A textarea cannot style part of its value, so the composer paints a mirrored overlay over transparent text, and that overlay and `UserMessage` must agree about *what is marked* or a word coloured while typing goes plain once sent. `highlightSegments` concatenates back to the input exactly, which is what keeps the overlay in register; the test asserting that round-trip is what guards against ghosting.
- Four commands are withheld from the picker in `commands.rs` — `clear`, `fast`, `model`, `rename` — because the app already owns what they do and none of their effects come back on the wire. See _Known issues_ for why hiding them is a stopgap.

## Current state

Several things are deliberately unfinished — don't mistake them for bugs.

- **Session status is a state machine in `session.rs` and it follows the turn alone.** `StatusTracker`: send or `init` → `in_progress`; `result` → `completed`, whatever background tasks are outstanding. A background subagent runs past `result` and the CLI opens a promptless `init` later to report findings, which reopens `in_progress` on its own. Holding *was* the rule and it hung every session running a dev server or `Monitor`, all `local_bash`, none of which ever end. The task set is recorded beside status for one thing only: `has_outstanding_work()` guarding child-replacing paths (effort respawn, update install) — fork is **not** among them, since it replaces no child, and **Stop is not either**. The frontend keeps tasks in a live `tasksBySession` map, not off the log, since a task outlives its turn; `read_stdout` mints an empty `background_tasks_changed` when the child exits, emitted and **never logged** (it runs after delete removed the file, where an append would recreate it). `buildTranscript` takes live task ids and keeps a spawning call pending while its task lives, joining on `SubagentRun.taskId`, since `task_id` ≠ `tool_use_id`. `completed` means finished *and unread*: the frontend clears it to `idle` on view, and a persisted `in_progress` resets to `idle` at startup. Status changes reach the frontend as `session_status` events — derived state, never written to the log.
- **mcode runs, over `mcode acp`, and the vocabulary is ACP's.** Spawn, `initialize`/`session/new`/`resume`/`fork`, prompt, cancel, and the settings that move in place. The transcript draws messages, thoughts (with their text), tool calls off ACP's `kind`, and results off `rawOutput`. The context ring fills from `usage_update`. Permissions are the agent's own options, carried back whole. **Read [harness/mcode/fixtures/README.md](apps/desktop/src-tauri/src/harness/mcode/fixtures/README.md) first** — it names what each capture pins, including the two shapes no capture has yet (a permission request, a `thinkingEffort` ladder).
- **What is not wired yet**: subagent lifecycle beyond the spawning call (mcode's `mcode/session/delegation_*` extension notifications land in `SessionUpdate::Unknown`).

- **The PR panel reads, acts, and answers.** It used to stop at reading and acting — no comment, no reply to a review, no review of its own, no reviewer request, no close. All six exist now, and what every one of them writes is the **reader's** text, passed through untouched.
- **Forks copy the conversation whole and record no lineage.** The CLI exposes no fork-at-message, and `fork_from` is cleared once the CLI carries the fork out, so nothing on disk says which session a fork came from.
- **hz writes only status and priority**, from the opened issue's header — no comment, no attachment, no assignee, no label — and there is **no issue-side project mapping**, the connection being workspace-wide. The `hz` CLI writes nothing.
- **The handoff row has no Revert, Amend or Stash** — each destroys or rewrites work, and a button that sends a prompt for one is a button whose blast radius is decided by the model. No Push either, and that one went on width.
- **The repo view reads — no fetch, no pull, no discard — and undo is the one write.** The ahead count is against the *last known* upstream, so a branch someone else pushed to reads as level until the push itself fails.
- **Sidebar PR marks say open, draft or merged; checks say running or failing.** No number, no per-check detail, no merge readiness, nothing at all for passing.
- **Spawned sessions inherit permission mode, so most block immediately.** The default stance is `auto`, so a fanned-out session stops at its first `Write` waiting for a card nobody is next to. `hz new` takes no `--permission-mode`, and adding one raises a real question: an agent in a `plan` session spawning a `bypassPermissions` child is an escalation past the stance the user set. Clamping the child to be no more autonomous than the parent is the likely shape of the fix.
- **No reading a transcript back.** Create, list and send exist; reading what another session said does not, and a parent cannot learn a child finished except by polling `hz ls`.
- **A search hit opens the session and not the sentence.** `TranscriptMatch` carries the `seq` it was found at, and nothing consumes it: the row calls the same `handleSelectSessionIndexItem` every other row does, so the reader lands at the bottom of a transcript that may be eleven megabytes long. Taking them to the line needs the transcript to scroll to a `seq` — the rail already scrolls to a *turn*, so the missing piece is the mapping rather than the mechanism.
- **An automation cannot be edited, only made and deleted.** The settings tab lists them with a switch and a delete, and the form at the bottom makes one; changing a prompt means deleting and making it again. Nothing keeps a run's history either — the row shows `lastSessionId`, so the last run is one click away in the sidebar and the ones before it are not.
- **TS event types are generated, not written.** `ts-rs` derives them into `src/types/events.ts`, checked in so the frontend build needs no Rust toolchain. `cargo test` regenerates; never edit the output. Two settings live in `src-tauri/.cargo/config.toml`: the export path, and `TS_RS_LARGE_INT = "number"`, because `u64` otherwise becomes `bigint`, which `JSON.parse` never produces.

## Known issues

Diagnosed defects, not yet fixed. Unlike _Current state_ above, these are broken rather than unbuilt. Delete an entry when you fix it.

- **"Check for Updates…" answers into a void when the sidebar is collapsed.** The verdict draws in `UpdateRow`, which lives inside `<aside>`. Fix = a surface not tied to the sidebar.
- **Quit from the Dock's context menu is unguarded.** It bypasses the menu bar, so the custom Quit item never sees it. Nothing in the Tauri API reaches it today.
- **A blocked install has no way to say when it unblocks.** It waits on any session being mid-turn but names none. That sentence sits in the button's tooltip, which is why the button carries `aria-disabled` and guards its own click instead of taking `disabled` — a disabled button fires no pointer events to open a tooltip.
- **A live background task defer that respawn silently**, since `has_outstanding_work()` guard every child-replacing path and a `local_bash` task never end on its own. The reader change effort or model, nothing happen, nothing say why. Stop used to be the way out by draining the set; it deliberately isn't any more (DRA-185), so nothing in the app can drain it. Cure = saying so, not putting the fan-out back.
- **A permission request stranded by a child dying mid-run is unanswerable.** The pending map lives in `Session`, so an effort-change respawn leaves a card whose buttons error. Restart is fine, and the CLI re-asks on resume.
- **A worktree session's first baseline is a guess, and the reflog holds the answer.** `base_ref_tree` resolves the fork point the way the CLI does, but the CLI fetches `origin/<default>` first, so an upstream commit landing in between is attributed to that turn. `git worktree add -B` writes a reflog entry naming the commit it actually used, readable lazily even after the agent commits. Take the newest "Created from"/"reset" entry, not the oldest.
- **Nothing handles a command that restarts or replaces a session.** The picker hides `clear`, `fast`, `model` and `rename` for this reason, but hiding is not solving: each is still reachable by typing it. `clear` starts a fresh conversation the index never heard of; `rename` retitles a session whose title this app owns; `model` and `fast` move the running child off what the composer displays. None come back on the wire in a form the app can reconcile. The fix is a way to notice a session was replaced and re-adopt it — the same machinery a `/clear` button would need. `commands_changed` is a related loose end: the CLI publishes it when available commands change, which would fix the restart-to-see-a-new-plugin caveat.
- **A hard kill mid-dictation leaves the output muted.** The record of what to restore lives in the process, so `SIGKILL`, a panic or a power cut get past `RunEvent::Exit`. Quit and window close are covered. The cure is durable state or a watchdog, neither of which a mute is worth today; unmuting by hand is the recovery.
- **A prompt typed during a turn runs under the *old* model, stance and fast mode.** `send_msg` records the new pick on the index before queueing, and the queue's own flush hands the prompt to the transport without passing the live controls — so the composer and the sidebar show the new setting while the turn it delivers runs on the previous one. One gap for all three rather than three, and the cure is one too: applying pending settings at the flush, or routing a queued prompt back through the settings path. Longstanding; fast mode joins it rather than adding to it.
- **A background subagent's report-back is a second `completed`**, so a session with one raises two "Task finished" notices.
- **The PR polls share one GitHub rate-limit budget with every agent in every session.** Sidebar marks ask `gh` once per repo every 30s, the panel polls again at 15s while anything is in flight — against a *per-user* budget that every agent's own `gh` call spends too. **GraphQL's budget is 5000 *points* an hour, charged on the shape asked for, not on what comes back**: nested `first`s multiply, so the panel query at `20 × 50 × 50` cost 11 points per read of a branch with *no PR at all*, and two hz instances (release beside a `tauri dev`) on one open PR tab drained the hour on their own (DRA-247). It is two aliased connections now — five open, two settled, thirty threads of fifty replies — measured at 2 points; measure any change to a query with `rateLimit{cost}` before shipping it. A second shape remains: `gh pr create` answering "API rate limit already exceeded" while `gh api rate_limit` reports the primary limit untouched is the **secondary** limit, which has no reset timestamp to wait on, and the cure at the agent's end is exponential backoff, which is GitHub's own guidance.
